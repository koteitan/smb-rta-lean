# 部屋の画面のページと、横の土管の長いタイマー

**主張.** これは部分的な結果です。部屋で最初に操作できるフレームの状態が 1 つの条件 `Room` を満たし、そこから入るまでの各フレームの各命令が条件 `SiteOK` を満たし、入るまでの各フレームがプレイヤーのルーチンで始まるとします。このとき、入るまでのどのフレームでも画面は最初のページにあり、スクロールロックはオンです。入るフレームの終わりのタイマーは長い値で、160 以上です。さらに入るフレームの終わりの 16 バイトが参照の値なら（`EntryRest`）、そこでの状態は横の土管に入るときの条件 `Entry2` 全体を満たします（[地上への切り替えの最後のフレーム](d-2-3-SideChangeEnd-ja.md)）。`Entry2` は 90 バイト（画面のバッファに記録があるときは 93 バイト）、プログラムカウンタ、スタックポインタ、フレームがアイドルループで終わることを求めます。証明は部屋の 1 フレーム全部を抽象機械で追います。フレームの部分には分けません。`Room`、`SiteOK`、ルーチンの条件、`EntryRest` は仮定です。本物のフレームで確かめました。

`m₀` は 1-1 の開始の機械です。`r` は参照の機械で、本物の走りの入る 1 フレーム前です（[横の土管から地上への切り替え](d-1-SideTransition-ja.md) の `P`）。`frame(m, i)` は入力 `i` の本物の 1 フレームです。`tr(n)` はそのフレームの `n` 命令あとの機械です。`page(m)` は `ScreenLeft_PageLoc`、`lock(m)` は `ScrollLock`、`rt(m)` は `GameEngineSubroutine`、`timer(m)` は `ChangeAreaTimer`、`x(m)` は `Player_X_Position` です。`e_s` は横の土管のルーチンの番号、`long` は `AreaChangeTimerData` のはじめの値です。`L` はフレームの終わりの 6000 ドット前です。

```
Room(m)     :=  m はアイドルループでフレームを終えている: pc と S は r と同じ、ドット ≤ 9、
                vblank と NMI のフラグはドットに合う、スプライト 0 のフラグは立つ、PPU 制御で NMI はオン、ストローブなし
                ∧  ∀ (b, k) ∈ K,  m[b] & k = r[b] & k

SiteOK(m)   :=  ( pc(m) ≠ アイドルループ          →  dot(m) ≤ L )
              ∧ ( m の命令が LDA (zp),Y            →  読む番地は RAM か ROM )
              ∧ ( pc(m) = ブロックバッファの読み   →  読むバイト ∈ T )
              ∧ ( 同じ場所で、足し算の番号が頭     →  読むバイト ∈ {0, コイン} )
              ∧ ( pc(m) = コインを消す書き込み     →  書く番地はブロックバッファの中 )
              ∧ ( pc(m) ∈ 画面のバッファの 3 か所  →  VRAM_Buffer1_Offset < 64 )
              ∧ ( pc(m) = 土管のコードの x の読み  →  x(m) & 15 ≠ 0 )

Leaves(m')  :=  page(m') = page(r) ∧ lock(m') = lock(r) ∧ rt(m') ≠ rt(r)
              ∧ ( rt(m') = e_s → timer(m') = long ∧ ∀ (v, X) ∈ V,  RoomCond(v, X ∖ R)(m') )

EntryRest(m) :=  ∃ (v, X) ∈ V,  ∀ b ∈ X ∩ R,  m[b] = v[b]
```

`K` は 83 バイトの既知のビットです。下に挙げます。`T` は `r` のブロックバッファにあるタイルと 0 です。`V` は `Entry2` の 2 つの参照の機械と、それぞれのバイトのリスト `X` です（`SideChangeEnd.refs2`）。`RoomCond(v, Y)` は、`Room` の `r` を `v` にし、バイト `Y` の全部のビットを知るものです。`R` は下の 16 バイトのリストです（`restIdx`）。

```
room_step    :  Room(m) ∧ (∀ j, SiteOK(tr(j)))  →  Room(frame(m, i)) ∨ Leaves(frame(m, i))
room_run     :  seq(n + 1) = frame(seq(n), inp(n)),  c ≤ e,  Room(seq(c)),
                ∀ n ∈ [c, e),  (∀ j, SiteOK(tr_n(j))) ∧ rt(seq(n)) = rt(r),   rt(seq(e)) = e_s
                →  (∀ n ∈ [c, e), Room(seq(n)))  ∧  timer(seq(e)) = long  ∧  page(seq(e)) = page(r)  ∧  lock(seq(e)) = lock(r)
room_keeps   :  Room(m) ∧ (∀ j, SiteOK(tr(j)))  →  page(frame(m, i)) = page(m)  ∧  lock(frame(m, i)) = lock(m)
RoomRun.screen :  同じ仮定  →  ∀ n ∈ [c, e],  page(seq(n)) = 0  ∧  lock(seq(n)) ≠ 0
RoomRun.timer  :  同じ仮定  →  160 ≤ timer(seq(e))
room_leaves  :  room_run と同じ仮定  →  (∀ n ∈ [c, e), Room(seq(n)))  ∧  Leaves(seq(e))
entry_rest   :  同じ仮定（rt(seq(e)) = e_s のかわりに EntryRest(seq(e))）  →  タイマー 160 以上の Entry2(seq(e))
entry_long   :  同じ仮定（rt(seq(e)) = e_s のかわりに、タイマーのない入るときの条件）  →  タイマー 160 以上を含む入るときの条件
screen_check（非公開）: roomCheck(sy, nm, m₀, 160, V) = true（native_decide）
```

`GameEngineSubroutine` は `R` に入っているので、`entry_rest` は `rt(seq(e)) = e_s` を `EntryRest` から出します。

Lean: `Theorems/ScreenPage.lean`（`readStep`、`writeStep`、`s_readStep`、`s_writeStep`、`SiteOK`、`preS`、`cov_preS`、`walkS`、`frame_of_walkS`、`RoomCond`、`Leaves`、`room_step`、`room_keeps`、`room_leaves`、`room_run`、`RoomRun`、`RoomRun.screen`、`RoomRun.timer`、`entry_long`、`EntryRest`、`entry_rest`）、非公開の `Proof/ScreenPage.lean`（`screen_check`、`screen_first_page`、`screen_long_timer`、`screen_entry`）。ROM のない定理が使う公理は `propext`、`Classical.choice`、`Quot.sound` だけです。

## この項目のこと

**(1) 入るフレーム.** 1 フレーム全部の確認の中に入っています。フレームの終わりの抽象状態が `rt = e_s` なら、その状態で `timer` は `long` と決まっていなければ確認は失敗します。土管のコードで `page` が 0 と知られているので、タイマーを書く枝は 1 つです。

**(2) 1 フレームで保つこと.** `K` はページとロックを全部のビットで含みます。`room_step` の両方の場合で値は変わりません（`room_keeps`）。ロックをオフにした状態、ページを 1 にした状態を参照にすると確認は通りません（下の表）。

**(3) 始まり.** 1 つの状態の条件 `Room(seq(c))` のままです。ルートでは、5 バイトを除いて部屋に入る切り替えの段から出します（[部屋で最初に操作できる状態の条件](d-2-4-1-ScreenStart-ja.md)）。

**(4) 入るときの条件.** フレームの終わりの抽象状態が `rt = e_s` なら、確認はさらに、その状態が各参照 `(v, X ∖ R)` の始まりの状態の下にあることを求めます。つまりプログラムカウンタ、スタックポインタ、ドット、フラグを知り、`X ∖ R` の各バイトを `v` の値で知っていることです。すると `Entry2` に要るのは `R` のバイトだけです（`entry_rest`）。

歩きは入るフレームを 2 つの抽象状態で終えます（ドット 0 と、ドット 1〜9）。どちらでも、歩きは `Entry2` の 90 バイトのうち 78 バイトを参照と同じ値で知っています。記録があるときは 93 バイトのうち 78 バイトです（`screen-check` で測りました）。知らない 12 バイト（15 バイト）と `GameEngineSubroutine` が `R` です。この回の前は 76 バイトでした。下のプレイヤーの 2 バイトを知らなかったからです。前の回の 79 バイトの `K` では、知らないのは 17 バイト（20 バイト）、その前の 73 バイトでは 23 バイトでした。

| `R` のバイト | 歩きが知らない理由 |
|---|---|
| `GameEngineSubroutine` | 歩きは知っています。`seq(e)` で入ったことを言うので `R` に入れました |
| `Player_Y_Position` | プレイヤーの高さ。部屋の中で変わります。歩きではタイルの読みが場所によらないので、歩きは土管の段を見分けられません |
| `VRAM_Buffer1_Offset`、`VRAM_Buffer1`（+0、+1、+2、+7） | 画面のバッファ。歩きは添字を 64 未満に分けるだけです |
| `AreaMusicBuffer`、`EventMusicBuffer`、`MusicData` (2)、`MusicOffset_Square1`、`NoiseSoundBuffer`、`EventMusicQueue`、`NoteLengthTblAdder` | 音。`K` は音のエンジンを追いません。急ぎの音楽はこれらのバイトを変えます |
| `AreaNumber` | 面の番号。部屋に入る切り替えの段は、操作のときにこれを知りません。縦の土管に入るときの条件にないからです |

これらのバイトの 1 つを `K` に足すと、歩きは失敗します（前の回に、`Player_State` と `Player_Y_HighPos` がまだ `R` にあったときに測りました）。`Player_Y_HighPos` で失敗 1、`VRAM_Buffer1_Offset` で 3、`EventMusicBuffer` で 1、`MusicOffset_Square1` で 1、`NoiseSoundBuffer` で 1、`VRAM_Buffer1` で 2 です。最後の組と `MusicData`、`EventMusicQueue`、`Player_Y_Position`、`Player_State`、`AreaMusicBuffer` は、部屋に入る切り替えの段が操作のときに参照の値を知りません（操作できる 4 つの状態のうち 0 か 2）。6 バイトは両方の確かめを通ったので `K` に入れました。`ScreenRoutineTask`、`DisableScreenFlag`、`Fireball_State` (2)、`JoypadOverride`、`GameTimerExpiredFlag` です。段は操作のときにこれらを知っていて、[部屋で最初に操作できる状態の条件](d-2-4-1-ScreenStart-ja.md) の確認はこれらを入れても通ります。

前の回、さらに 3 バイトを `K` に入れました。`AreaPointer`、`EntrancePage`、`PrimaryHardMode` で、次の面とハードモードです。部屋に入る切り替えの時間の段は、操作のときにこれらを参照の値で知っています（操作できる 2 つの状態の両方）。これらを `K` に入れても歩きは失敗 0 で、表も同じです。[部屋で最初に操作できる状態の条件](d-2-4-1-ScreenStart-ja.md) の確認も通ります。ですから `EntryRest` はもうこれらを求めません。`AreaNumber` も歩きは通りますが、段がこれを知りません。ルートのほかの部分も `AreaNumber` を追っていません。縦の土管に入るときの条件、パート a の 1 フレーム全部で保つこと、部屋に入る切り替えの段のどれにもありません。ゲームの始まりから 0 で、これらのフレームのコードはこれを書きませんが、証明していません。部屋の本物の走り（113 回、入るのは 36 回。一時的なプログラムで測り、残していません）では、この 4 バイトと `Player_Y_HighPos` と `R` の音のバイトは変わりません。音のバイトを `K` に入れると歩きは通りますが、入るフレームの終わりではこれらを知りません。探索が、これらの違う状態をまとめるからです。

項目 1-1-c-7-5-13 で、もう 1 バイトを `K` に入れました。プレイヤーの当たり判定を止める旗 `DisableCollisionDet` です。部屋に入る切り替えがこの旗を 0 にし、部屋のどの命令も書きません。切り替えの段は操作のときにこの旗を参照の値で知っていて、歩きもこの値を保ち、確認は前と同じく通ります。最初の落下の着地は、この旗の値を歩きから取ります（[最初の落下での当たり判定を止める旗と縦のページ](c-7-5-13-LandBytes-ja.md)）。

**この回: プレイヤーの状態と画面の上での高さ.** `K` は `Player_State` の上のビットだけを知り、`Player_Y_HighPos` は知りません。どちらも部屋の中で変わるからです。けれども土管に入る道では、コードがこれらを確かめます。

* 横の土管のコードは状態を `LDY`、`CPY #0`、`BNE` で確かめます。`TaintRun` の機械がバイトを分けて読むのは `LDA` のときだけなので、`Y` での分岐から歩きはこのバイトを知りませんでした。いまは、この `LDY` で状態の低い 2 ビットを分けます（`preS`、`Places.stAt`）。土管に入る道では状態は 0 です。
* 当たりのルーチンは高さの上のバイトを `LDA`、`CMP #1`、`BNE` で確かめ、1 でなければ出ます。土管のコードは当たりのルーチンの中です。いまは、この `LDA` で上のバイトの全部のビットを分けます（`Places.hpAt`）。値 1 の部分だけが当たりのコードに進みます。探索は `CMP` で部分をアキュムレータで分けたままにします（`Aids.aAt`）。そうしないとすぐにまとめてしまいます。

分けることは安全です。どの機械もどれかの部分の下にあります（`cov_preS`。`TaintRun.cov_bit` と `PipeEntryRule.cov_all` から）。新しい仮定はありません。入るフレームの終わりで、歩きはいま状態 0 と上のバイト 1 を、参照と同じ値で知っています。ですから `EntryRest` はもうこの 2 バイトを求めません。`R` は 16 バイトで、前は 18 バイトでした。探索は 208,238 ステップ（前は 210,934）、表は 9,276 個（前は 9,378）です。[部屋のブロックの地図](c-7-12-RoomMap-ja.md)（パート c）の歩きも同じ分け方を使います。その確認も通ります（`room-map-check`: `mapCheck` は true、表も同じ）。

## しくみ

**抽象機械.** [一部のバイトがわからない走り](b-2-3-TaintRun-ja.md) の機械をそのまま使います。新しくした部分はありません。その上に、3 つの歩き方を足しました。どれも 1 命令ぶんを本物の `step` に対して証明します。

* `LDA (zp),Y` でポインタがわからないとき（`readStep`、`s_readStep`）。読む番地が RAM か ROM なら、機械はほかに何も変わりません。読んだ値はわからないとします。ブロックバッファの読みでは、値を `T` の各値に分けます。
* `STA (zp),Y` でコインを消すとき（`writeStep`、`s_writeStep`）。ブロックバッファに既知のビットがないので、どこに書いても抽象状態は変わりません。
* 分けること（`preS`）。`dot ≤ L` で時間の幅を切ります。画面のバッファの添字は 64 未満の値に分けます。`x` は低い 4 ビットのどれかが立っている 4 つに分けます。プレイヤーの状態は横の土管のコードが読む場所で低い 2 ビットに、上のバイトは当たりのルーチンが読む場所で全部のビットに分けます。この 2 つは条件が要りません。

**表.** 探索が抽象状態の表を作ります。確認は表の各状態から歩き、どの道も表の状態に入るか、フレームの終わりで `Room` か `Leaves` になることを確かめます（`walkS`、`finR`）。探索が忘れるものは、確認が `AS.le` で確かめます。ですから探索は証明の一部ではありません。

**大きさ.** 探索 208,238 ステップ、8,862 の枝分かれ、失敗 0、表 9,276 個。プログラムで確認全体が約 5 秒です。

**1 フレームが閉じた理由.** 前の測定（[縦の土管に入るフレームを本物のフレームで](a-5-1-PipeEntryRule-ja.md)）で、パッドだけわからなくても失敗 179 でした。失敗の場所はポインタの読み、ジャンプ表、時間です。ここでは次の 4 つで閉じました。

* わからないポインタの読みを許す規則。条件は「レジスタを読まない」だけです。
* 読むタイルの値を分ける。旗竿、ツタ、斧、バネへの道が消えます。
* 頭の読みは 0 かコインだけ。レンガをたたく道が消えます。
* 物のバイトなどの `K`。

**ページとロックを書く命令**（ディスアセンブリから数えました）。ゼロページの添字つきの書き込み 338 個は届きません。

| 書き方 | ページ | ロック | 歩きが通った命令 |
|---|---|---|---|
| 直接 | 3 | 5 | ページ: なし。ロック: `PlayerHole` の 1 個。ここは 1 を書くので値は変わりません |
| 絶対番地の添字つき（439 個のうち届くもの） | 31 | 31 | 6 個（スプライトの番号 4 個、ジョイパッド 2 個）。どれも添字がわかっていて届きません |
| ポインタ経由 | 9 | 9 | 1 個（コインを消す）。ブロックバッファの中です |

歩きは 2,668 個の命令を通ります。`ScrollScreen`、`StartPage`、`ExecGameLoopback`、`ScrollLockObject`、`PlayerEndLevel`、`WarpZoneObject`、`FlagpoleCollision` は通りません。

* 右へ走って画面の外へ出ることはありません。スクロールロックがオンの間、`ChkPOffscr` が画面の中に戻します。土管の右に書き換えて右と B を押し続けても、位置は最大で 240 ピクセル、マリオのページは 0 のままです。

## ラウンド 26: 部屋の歩きが `SiteOK` の各部分をどこまで知っているか（測定）

項目 1-1-d-2-4-2。問い: 制御の歩きやコインのフレームの歩きのように、部屋で最初に操作できるときの段から部屋のフレームの歩きで `SiteOK` のどの部分を証明できるか。いちばん細かい部屋の歩きは [BufferEnd](d-2-5-5-3-BufferEnd-ja.md) のものです（部屋の条件、画面のバッファの制御 0 か 6、位置の区間、ラウンド 26 からはページも。[BufferPage](d-2-5-5-4-BufferPage-ja.md)）。`buffer-ctl-check FM2 4000 sites26` は、その表のすべての状態から、覆われる状態かフレームの終わりまで歩きの段を進み、各状態で、その状態だけでその部分が言えるかを調べます（証明の一部ではない）。

| 部分 | 求めること | 制御 0 から: 分かる / 分からない | 制御 6 から: 分かる / 分からない | 分からない場所 |
|---|---|---|---|---|
| `reads` | `LDA (zp),Y` が RAM か ROM を読む（ポインタの上のバイトが 0x1E 以下か 0x80 以上） | 15,007 / 294 | 15,009 / 308 | 画面の更新のバッファの読み（4 か所）、音楽のルーチン（5 か所） |
| `off` | 画面のバッファの添字が 64 未満 | 119 / 0 | 1,703 / 242 | バッファに書く 3 か所 |
| `xbit` | 横の土管の読みで位置の下のビットが 0 でない | 12 / 64 | 12 / 64 | 横の土管の読み |
| `read` | ブロックバッファのルーチンが表のタイルを読む（場所がブロックバッファの中） | 13,202 / 1,204 | 13,202 / 1,204 | ルーチンの読み |
| `erase` | コインをブロックバッファの中で消す | 0 / 310 | 0 / 310 | 消去 |
| `late` | 処理がドット `L` より前に終わる | 50,543 / 1,603,443 | 73,948 / 2,003,652 | ほとんどすべて |

分かること:

* `off` は、制御 0 で始まるフレームではどこでも分かります。制御 6 で始まるフレームは 2 つ目のバッファを描き、1 つ目のバッファの添字は戻されません。部屋の条件はそれを知りません。だから `off` には、添字を部屋の条件に入れてフレームからフレームへ保つこと（`BufferControl` が制御を保つように）と、歩きの定理を、`off` を仮定する代わりに命令ごとに証明する形にすることが要ります。
* `reads` は読みの約 2% を除いて分かります。残りは歩きの知らないポインタを通ります: ループのあとの画面の更新のバッファへのポインタと、音楽のデータのポインタです。
* `xbit`、`read`、`erase` には命令での位置（と高さ）が要りますが、部屋の条件からの歩きはそれを知りません。いくつものフレームにわたる範囲（壁、床）が要ります。
* `late`: 歩き自身のドットの上限は、ほとんどの状態で `L` を超えます。それを抑えているのは `SiteOK.late` による切り詰めです。証明には処理の各道の時間が要ります。

だから今の歩きのままでは、どの部分も切り出せません。部屋の歩きを使う定理はどれも、各命令の `SiteOK` を 1 つの仮定として受け取ります。部屋の条件を与える `RoomMap.cond_of_rows` も同じです。部分を証明するには、歩きの定理を部分ごとに分けた形にすることが要ります。`chg.roomSites` はそのままです。

## 前提（Lean では証明していない）

* **`EntryRest(seq(e))`.** 入るフレームの終わりで `R` の 16 バイトが `Entry2` の参照の値であること（(4) を見てください）。急ぎの音楽が鳴ると成り立ちません（[急ぎの音楽が鳴る走り](0-6-4-HurryMusic-ja.md)）。項目 1-1-d-2-5 です。 道筋はいまそのうち 11 バイトを求めます。音楽の 5 バイトは部屋のフレームから出ます（[部屋のフレームを通る音楽のバイト](d-2-5-1-RoomMusic-ja.md)）。
* **`Room(seq(c))`.** 部屋で最初に操作できる状態の 83 バイト。ルートでは 1 つ目の切り替えの時間の段から証明しました（[部屋で最初に操作できる状態の条件](d-2-4-1-ScreenStart-ja.md)）。以下はこのページを書いたときの説明です。走りが違っても変わらないバイトだけを `K` に残しました。ファイアマリオ（`PlayerStatus` が 2）では成り立ちません。1-1 のこの土管より前のパワーアップは 1 つです。部屋に入る切り替えの段を歩けば出るはずです。切り替えのあとの状態はほとんど知られているからです。項目 1-1-b-3-2 の段の最後の状態が `K` の値を知っていれば、`AS.le` の確認 1 つで済みます。`K` のうち面の準備が消さないバイトは `AreaType`、`CurrentPlayer`、`PlayerStatus`、`WorldNumber`、`OperMode`、`OperMode_Task`、`AreaMusicBuffer_Alt` です。その段の出口の条件がこれらを知る必要があります。ここではその段に頼っていません。動かしてもいません。
* **`SiteOK` の時間.** 部屋のフレームがはみ出さないことです。
* **読みの番地.** `LDA (zp),Y` がレジスタを読まないこと。一時的なプログラムで測りました（残していません）。この条件の代わりに [切り替えの最後のフレーム](d-2-3-SideChangeEnd-ja.md) の規則（ポインタの上のバイトが `0x1E` 以下か `0x80` 以上とわかる）を使うと、部屋の歩きは画面の更新の最初の読み `LDA ($00),Y` で失敗します。NMI はこのポインタを、`VRAM_Buffer_AddrCtrl` を位置として表から読みます。`Room` はこのバイトを知りません（コインをとると変わります）。ですから歩きには、`Room` にこのバイトのビットと、その読みの分け方が要ります。また [部屋のブロックの地図](c-7-12-RoomMap-ja.md) は、知っているポインタを通したものも含めてすべての `LDA (zp),Y` に `SiteOK` のこの部分を使います。ですから、そのページの定理に与えるものを変えずには、この部分を `chg.roomSites` から外せません。項目 1-1-d-2-4-2 です。
* **タイル.** ブロックバッファの読みが `T` の値を返すこと。読む番地がブロックバッファの中にあり、部屋のブロックバッファが初めの値かコインの消えた値であることから来ます。これは証明していません。
* **頭.** 頭の読みが 0 かコインであること。部屋では頭がレンガに届かないことから来ます。本物のフレームでは、ジャンプの高さが足りません（測定: 大きいマリオの `y` の最小は 45、頭の高さは最上段の下です）。
* **コインを消す番地、バッファの添字.** どちらも本物のフレームで成り立ちます。添字は 55 以下でした。
* **`x & 15 ≠ 0`.** [横の土管から地上への切り替え](d-1-SideTransition-ja.md) の `z` に届かないことです。この条件がないと切り替えは 378 フレームで、長くなる側ですが、`Entry2` は `timer ≥ 160` を求めます。
* **入るまでプレイヤーのルーチンで始まること.** 時間切れでこのルーチンから出ることはあります（確認には、けが、死、1 機減るルーチンで終わる道があります）。その走りは 1748 フレームよりずっと多く使っています。ルートではもう仮定ではありません。`a₂` を、`b₁` からあとでプレイヤーのルーチンを出た最初の機械と定めます。そのルーチンが横の土管のものであることは、`EntryRest` のルーチンのバイトが言います。
* フレームはエミュレータのフレームです。
