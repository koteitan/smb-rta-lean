# 触るときの旗のタイル: 当たり判定のルーチンの中で高さを守る。フレームが保つ二つのバイトから

`PoleJoin.Run` のフィールド `yKeep` をなくしました。これは、ルーチンの書き込みまで、当たり判定のルーチンの中では添え字かポインタを通した書き込みが高さを書かないことを求めていました。いまは触るフレームの歩きが、ルーチンの中のそういう書き込みをすべて確かめ、高さも、そこで守るもう二つのバイトも書かないことを示します。そのために歩きは、操作の始まりからフレームが保つ二つのバイトを使います。ブロックの物のオフセットと、プレイヤーの番号です。`yKeep` の代わりに仮定するのは新しいフィールド `keepB` です。触るフレームまでのどのフレームでも、添え字かポインタを通した書き込みはこの二つのバイトを書かない。`keep.cleanE` の守りと同じ種類の、一つずつの命令の条件です。

## なぜ歩きは `yKeep` を示せなかったか

当たり判定のルーチンの中に、歩きが行き先を高さから外せない書き込みのところが 20 ありました（第 24 回、`pole-far-stores`）。

* `X` を通したブロックの物の書き込みが 16（`STA zp,X`、`STY zp,X`、頭の突き上げとレンガ）。`X` はブロックの物のオフセットです。ゲームはこのバイトをいちばん下のビットの反転（`EOR #1`）でしか変えないので 0 か 1 ですが、歩きはそれを知りませんでした。
* ブロックバッファへの `STA (zp),Y` が 3（突き上げたブロックの空のタイル、その上のコイン、触ったコイン）。ポインタの上のバイトは二つのブロックバッファで同じですが、歩きは知らない添え字の書き込みでそれを忘れていました。
* 得点の数字の書き込み `STA abs,Y`。`Y` はプレイヤーの番号から来ます。`Y` が分からないと、行き先の範囲が一回りして高さの場所にかかります。

## 二つのバイト

ブロックの物のオフセットを `spr`、プレイヤーの番号を `cur` とします。場所はプログラムから読みます。`spr` は浮かぶ数字のルーチンの最初の `LDX abs` のオペランド（`sprI`）、`cur` は数を書くルーチンの 6 バイト前の `LDY abs` のオペランド（`curI`）です。見張るビットは次のとおりです（`watchB`）。

```
spr & 0xFE = 0,   cur = 0
```

* 操作の始まりで両方が成り立ちます。横の土管から出る切り替えの段の、操作できるどの状態でも、二つのバイトはこの値で分かっています（`PoleTileCtl.watchCheckK`。地図の確認 `mapCheckK` と一緒に段を一回たどって確かめます: `mapWatchK`）。だから `Watched(watchB, seq 0)` です（`PoleTileCtl.watch₀`）。
* 操作中のどのフレームもそれを保ちます。確認 `okSK` のついたフレームの歩き（`PoleTileWalk.keepCheckS`）を、二つのバイトを守り（`GK`）見張って（`watchY` = `FrameKeep` の見張るビットとこれら）走らせます。どの命令でも `FrameKeep` の `CleanK` と `KeepB` が成り立てば（`cleanK_GK`）、触るフレームまでのどのフレームも、地図と二つのバイトの値を持って始まります（`frames_keepY`）。この歩きは `FrameKeep` の歩きでもあるので（`walkK_of_KS`）、`FrameKeep.keep_frameW` が各フレームの終わりの見張るビットを与えます。

## 新しいフィールド

* `keepB`（`KeepB`）: 触るフレームまでのどのフレームのどの命令でも、数えるフレームかどうかによらず、添え字かポインタを通した書き込みの行き先 `t` が `t < 0x2000` なら、`t mod 2048 ∉ {spr, cur}`。

## 触るフレームの歩き

歩きは `PoleTileFar` の歩きに次の変更を加えたものです（`walkZ`）。

* 二つのバイトの見張るビットを持って始まり（`startY`）、フレーム全体でそれを守ります（`poleY`: `PoleFrame` の守りに二つのバイトを加えたもの）。
* 当たり判定のルーチンの中では、守り `GZ` が高さと、ブロックバッファのポインタの上のバイトと、物のオフセットを守ります（`zoneB`）。`PoleTileHeight` は高さだけを守っていました。
* **ルーチンの中の確認**（`zoneTest`）を、ルーチンの中で一歩が添え字かポインタを通した書き込みであるどのかけらでもします: 書き込みはこの三つのバイトのどれも書かない。歩きの書き込みの番地がそれらを避けるか（`StepWrites.keepOK`）、かけらの知っていることからの行き先の範囲がそれらを避けます（`rangeOK`、`rangeW`）。
  * `STA`/`STY`/`DEC`/`INC zp,X`: オペランド `z` に `X` を足したもので、`z + max X < 256` のとき、範囲 `[z + min X, z + max X]`。
  * `STA (zp),Y`: 範囲 `[min lo + 256·min hi + min Y, max lo + 256·max hi + max Y]`。`lo` と `hi` はポインタのバイトで、`min` と `max` は分からないビットをそれぞれ 0 と 1 にしたものです。
  * 範囲は RAM の一つの写し（`0x2000` より下で、2048 の一区切り）の中か、RAM の先にあること。

証明: `range_spec`（覆われた機械は範囲の中に書く: `RoomBlocks.writeAddr_eq`、`SideChangeEnd.ptr_toNat`）、`target_of_range`、`keep_target`（添え字かポインタを通した書き込みの歩きの番地は `PipeWrites.wTarget` のもの: `wOf_of_target`）、`zone_of_test`。これらで、`GZ` の `CleanK` が `CleanK` と `PosAt` と確認から出ます（`cleanK_GZ`）。だから歩きの一歩は `YAt` なしで機械に従います（`s_kstepZ`）。定理（`no_write_frameZ`）:

```
frameCheckZ ∧ FrameStart(s₀) ∧ Watched(watchB, s₀) ∧ ColMap(s₀) ∧ (∀ j ≤ n, s_j で CleanK ∧ PosAt ∧ HypR ∧ BufAt ∧ TileCol)
  ⇒ rt(s_{n+1}) ≠ 旗のルーチン
```

仮定に `YAt` はありません。`touch_right_of_leftZ` と `inRange_of_frameZ` は、`PoleTileFar` の定理を、`YKeep` の代わりにフレームの始まりの `Watched(watchB)` と（`CleanK` と `KeepB` からの）`GK` の `CleanK` で述べたものです。確認 `poleCheckZ` = `ptrOK ∧ frameCheckZ ∧ subsCheck ∧ keepCheckOfY` はネイティブに証明しました（非公開の `Proof/PoleTiles.lean` の `pole_check_z`。`pole_check_f` の代わり）。`PoleJoin.Run.inRange` は、フィールド `keepB`、`posKeep`、`bufAll`、`tilesCol`、`edge` と、触るフレームの始まりの地図と二つのバイト（`Run.tilesStart`）で `inRange_of_frameZ` を使います。

表を探すときは、ルーチンの中ではどの正規化でもルーチンのバイトを覚え、数を書く二つのルーチンの中ではレジスタとフラグを忘れます（`normZ`、`rangesZ`）。プレイヤーの番号が分かると、数字ごとに状態ができてしまうからです。これは探し方の選び方だけです。歩きがすべての状態を確かめます。

## 測ったこと

歩きの探索（`pole-keep search`）: 10,775,682 歩、表の状態 498,138、失敗 0（`PoleTileFar` の歩きは 9,680,248 歩、434,249 状態）。探索はネイティブで 50〜62 秒、確認 `poleCheckZ` 全体はネイティブで 77〜100 秒で真です（大きいほうは負荷約 9 のとき）。二つのバイトつきのフレームの歩き（`keepCheckOfY`）は 4〜5 秒で真です。探りの中で探索の最大は約 4.3 GB でした。非公開の `Proof/PoleTiles.lean`（`pole_check_z` と段の確認 `pole_rows`）は二回の全体の構築で 150 秒と 113 秒でした（第 24 回は `pole_check_f` で 162 秒）。

**最初は大きすぎたか偽だった**（探し方の選び方だけで、偽の主張ではありません）:

* 二つのバイトが分かると、数を書くルーチンを数字ごとにたどりました。最初の探索は 5.9 GB を超え、止めました。いまは探索が、当たり判定のルーチンの中のこの二つのルーチンでレジスタを忘れます。
* 探索はポインタの上のバイトと物のオフセットを一部の場所でしか覚えませんでした。するとその状態のうち 28 が、触ったコインを消す書き込みで確認に落ちました。いまはルーチンの中のどの場所でも覚えます。
* 最初の確認は偽でした。数を書くルーチンのくり返しの中で、歩きが状態を覆えませんでした。探索はそこでレジスタを忘れましたがキャリーは忘れず、ルーチンの中ではキャリーが表の鍵の一部だからです。表の 240 の状態が歩数を使い切りました。いまはそこでフラグも忘れます。すると表のどの状態も二つの始まりも通ります。

## 証明していないこと

* `keepB` そのもの: 添え字かポインタを通した書き込みは、ブロックの物のオフセットもプレイヤーの番号も書かない。ゲームはこれらを番地でしか書きません（オフセットは `EOR #1` で、プレイヤーの番号は二人のプレイヤーが代わるとき）。上の本物のフレームで確かめました。
* `tilesCol` と `bufAll` は変わりません。
  * `tilesCol` には、フレームをまたいだ、画面と彼に対する地形を読むルーチンの列が要ります。測りました（`pole-keep parser FM2 N`。地形を読むルーチンのバイトは `UpdScrollVar` のコードから見つけます）。操作中のフレームの始まりではいつも `16·col + 16·p(N) + S − edge = 384` です。`col` は地形を読むルーチンの列（1 ページに 16）、`N` は今の組で残っている仕事、`p(N) = [N ≥ 1] + [N ≥ 5]` はその中の列の進み、`S` は 32 px のスクロールの数、`edge` は画面の左端（px）です。また、地形を読むルーチンのブロックバッファの列は `col mod 32` です。そして、ブロックバッファへの旗のタイルの書き込みは、どれも地形を読むルーチンの列が旗の列にあるときです。`N = 400` では、操作中のフレームの始まりが 163,009（TAS、そのフレーム 900〜1089 からの自分の乱数入力 400 回で半分は Start あり、最初の操作から 1,300 フレームを 100 回で半分は Start あり）で、どれも値は 384、ブロックバッファの列は `col mod 32` でした。旗のタイルの書き込みは 620 で、どれも旗の列でした。操作の始まりでは、切り替えの段がこれらのバイトをすべて知っています（地形を読むルーチンは 2944 px、左端は 2560 px、`N = 0`、`S = 0`）。だから地形を読むルーチンが旗の列を描くのは、左端が旗の列より 384 px 以内に来たときだけで、彼は左端より右にいます。しかし歩きは一つずつのバイトの分かっているビットを覚えるだけで、このような和は覚えないので、これは証明していません。
  * `bufAll` には、ブロックバッファのすぐ下の物の表への 36 の書き込みで、物の添え字の上限が要ります。探りで測りました。物のオフセットを二つのバイトと同じように守って見張ると、フレームの歩きの表は 46,576 から 182,120 の状態に増え、その確認は偽になり、36 の書き込みでは `X` はやはり分かりません。そこで物のオフセット自身は正確に分かっている（0〜5）のにです。そこの `X` は、歩きが切れ目で忘れるレジスタを通って来ます。
