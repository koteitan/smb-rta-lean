# 部屋のフレームの時間を歩きから

**主張.** 部屋のフレームが画面のバッファのレコードのクラスで始まるなら（[画面のバッファのレコード](d-2-4-2-2-BufferRecords-ja.md)）、アイドルループ以外の命令はすべてフレームの終わりの 6000 ドット以上前に走る。ただし、音のルーチンのコードの命令がすべてドット 9,000 までに走るとする。

これは証明した。ROM の上の検査は 1 つ。ラウンド 28 まで、ルートは部屋のすべてのフレームのすべての命令で `Late`（アイドルループ以外でドットが `L` = 83,342 以下）を求めていた。今は次だけを求める。

* `Late` は部屋の最初のフレームと、画面のバッファの制御 6 で始まるフレームの次のフレーム（フレーム `U`）だけ。
* ほかのフレームでは `LateS` だけ: 音のルーチンのコード（ROM の `SoundEngine` から先）の命令はドット 9,000 までに走る。

そのフレームでは、ハンドラのほかの部分の時間は証明される: 画面の更新、パッド、ポーズ、タイマー、スプライト 0 のフラグの待ち、ゲームのルーチン、スプライト。

`tr_n(j)` はフレーム `n` の `j` 命令あとの機械。`pc`、`dot` はそのプログラムカウンタとフレームの中のドット。`idle` はアイドルループ。`snd` は `SoundEngine` のアドレス。`A.hi` は抽象状態が許す最後のドット。`Rest(Z, m)`、`U(n)`、`InPat` は [画面のバッファのレコード](d-2-4-2-2-BufferRecords-ja.md) と同じ。

## 主張の式

```
Late(m)          :=  pc(m) ≠ idle  →  dot(m) ≤ L                       （L = 83,342: フレームの終わりの 6000 ドット前）
LateS(m)         :=  snd ≤ pc(m)   →  dot(m) ≤ 9,000
timeOK(A)        :=  pc(A) = idle  ∨  A.hi ≤ L
RestS(m)         :=  LateS(m) ∧ Read(m) ∧ Erase(m) ∧ Xbit(m)

late_of_time     :  Sim(A, m) ∧ timeOK(A)  →  Late(m)
frame_of_walkST  :  歩き walkST がフレームの始めから成功し、すべての状態で chk(A) ∧ R(m) → SiteOK(m)、R → LateS、
                    ∀ j, R(tr(j))   →   (∀ j, SiteOK(tr(j)))  ∧  フレームは fin が受け入れる状態で終わる
rec_frame2T      :  recCheckT(T, L, L₆),  RoomCond(r, K_M, m),  InCls(T, m),  InPat(0, L, m),  ∀ j, RestS(tr(j))
                    →  (∀ j, SiteOK(tr(j)))  ∧  (InPat(0, L, frame(m, i)) ∨ InPat(6, L₆, frame(m, i)))
rec_frame3T      :  recCheckT(T, L, L₆),  RoomCond(r, K_M, m),  InCls(T, m),  InPat(6, L₆, m),  ∀ j, RestS(tr(j))   →   ∀ j, SiteOK(tr(j))

late_sites_of_rows :
      records_sites_of_rows の条件。ただし recCheck(T, L, L₆) のかわりに recCheckT(T, L, L₆)、
      ∀ n ∈ [b, a), ∀ j,  Read(tr_n(j)) ∧ Erase(tr_n(j)) ∧ Xbit(tr_n(j))、
      ∀ n ∈ [b, a),  U(n)  →  ∀ j, Late(tr_n(j))、
      ∀ n ∈ [b, a),  ¬U(n) →  ∀ j, LateS(tr_n(j))、
      ラウンド 28 のフィールド（U での画面の更新のポインタ越しの Reads、6 のあとの 6 での Off）
      →   ∀ n ∈ [b, a), ∀ j, SiteOK(tr_n(j))
```

`chg` の変わったフィールド（すべての `n ∈ [b₁, a₂)` とすべての `j` について）:

```
roomLate   :  U(n)   →  Late(tr_n(j))          （前はすべてのフレーム）
roomLateS  :  ¬U(n)  →  LateS(tr_n(j))          （新しい）
```

`recCheckT` は [画面のバッファのレコード](d-2-4-2-2-BufferRecords-ja.md) の `recCheck` で、歩き (ii)（パターン `L` から）と (iii)（パターン `L₆` から）を時間つきの歩きにかえたもの。歩き (i) と (iv) は、歩きが知らないバッファから始まり、前と同じ。`Run.roomTime`（動きの途中でフレームが終わらないこと。部分 c が使う）は `Run.roomSites` から出る。検査 `hR`、`hB`、`hK` を取る。

Lean: `Theorems/RoomLate.lean`（`timeOK`、`late_of_time`、`LateS`、`sclamp`、`sim_sclamp`、`walkST`、`live_stepST`、`frame_of_walkST`、`searchST`、`cfgBT`、`walkCheckST`、`STOK`、`frameST`、`fixCuts`、`chkT`、`walk2T`、`walk3T`、`recCheckT`、`rec_frame1T` から `rec_frame4T`、`late_sites_of_rows`）、非公開の `Proof/SiteMusic.lean`（`buffer_records_check` は `recCheckT` になった）。ROM を使わない定理の公理は `propext`、`Classical.choice`、`Quot.sound` だけ。

## しくみ

**歩きの中の時間.** 抽象状態は最初と最後のドット（`lo`、`hi`）を持つ。`Sim` は機械のドットがその間にあると言う。1 歩ごとに命令のサイクルを足す。画面の状態の読みは、フラグが変わるドット（vblank の終わり、スプライト 0 のフラグ）で状態を分ける。だからフラグの待ちは歩きでも終わる。

**前のクランプ.** 部屋の歩きは各歩の前に `hi` を `L` にクランプする（`ScreenPage.clampS`）。それには機械の `Late` がいる。探索も、状態が 3 回目に合わさると `hi` を `L` にする。だから歩き自身の上限はほとんどどこでも `L` だった（ラウンド 26: 1.65 M 歩のうち 1.6 M 歩で `L` を超える）。

**新しい歩き**（`walkST`）. すべての状態で `timeOK` を確かめる。状態は、`L` へのクランプなしで表の状態で覆う。音のルーチンのコードの中だけ `hi` を 9,000 にクランプする（`sclamp`）。それには機械の `LateS` がいる。表は探索（`searchST`）から来る。同じキーの状態を合わせて大きい `hi` を残す。音のルーチンのコードの中だけ、3 回目に合わさると `hi` を 9,000 にする。だから、すべての命令の `Late` は検査と `LateS` から出る（`late_of_time`）。`RoomPause.pstep` の中の `L` へのクランプは何も変えない。

**音のルーチンが仮定に残るわけ**（測った。`buffer-ctl-check FM2 N lateW`）. クランプが何もないと、歩き (ii) の探索は `hi` が 20,000 以下の状態が 93,415、`hi` が上限まで伸びる状態が 44,042。伸びる状態の最初は音のルーチンの中にあり、あとの状態はすべてそれを受けつぐ。歩きは、知らないポインタとオフセットで音楽のデータをたどる（[RoomMusic](d-2-5-1-RoomMusic-ja.md) の音楽の表は音の 9 バイトを知る）。

* `FindEventMusicHeader` は、立ったビットが出るまで音楽のキューをシフトする。歩きはイベントの音楽のバッファを勝利のビットのほかしか知らない。シフトのあと、キューが 0 と知られる部分ができ、その部分は永遠にシフトする。
* 矩形波 1 とノイズのデータの読みは、0 のバイトでループする。読むオフセットを歩きは知らない。

本当の実行では曲のデータがこれらのループを終わらせる。歩きでは終わらない。だから上限には曲の状態がいる。

**スプライト 0 の待ち**（このラウンドで見つけた）. `ScreenPage.jsrRets` はハンドラのバイト `0x20` をすべて呼び出しとみなす。画面の状態のアドレスの上のバイトも `0x20` だ。だから探索は状態の読みのすぐあとで A と Y を忘れていた。スプライト 0 のフラグの待ちの中でもそうだった。歩きはフラグを知らず、クランプなしでは待ちが永遠に続いた。証明の誤りではない（歩きは忘れるだけかを確かめる）が、精度を失っていた。`fixCuts` は、呼び出し先が ROM の中にある場所だけを残す。

**大きさ.** 時間つきの歩き (ii): 探索 137,425 状態、表 48,455、すべての状態が通る、アイドルループ以外の `hi` の最大 54,912（ネイティブで約 25 秒）。歩き (iii): 探索 725,637 状態、表 264,079、`hi` の最大 55,128（約 140 秒）。前の歩き (ii) と (iii) は 8 秒と 44 秒だった。`recCheckT` はネイティブで約 165 秒（`recCheck` は約 107 秒）、非公開の `Proof.SiteMusic` は約 180 秒（ラウンド 28: 135 秒）。

**9,000 の選び方.** 音のルーチンのあとに、パッド、ポーズ、タイマー、vblank の終わりの待ち（スプライト 0 のフラグが消える）が来る。スプライト 0 のフラグがまた立ったあと（ドット 17,732）にこの待ちに来た道は、次のフレームまで待つ。歩きでも本当の機械でもそうだ。クランプが 10,000 のとき（上の呼び出しの修正の前に測った）、歩きは遅くともドット 17,679 で待ちに来た。17,732 の 53 ドット前だ。9,000 なら検査は通る。本当の音のルーチンは、測ったすべてのフレームでドット 7,159 までに終わる。

## 本当のフレームで確かめた

`buffer-ctl-check FM2 1100 latereal`: 音のルーチンのコードの命令の最大のドットと、アイドルループ以外の命令の最大のドット。ムービーの部屋のフレームと、そこからの自前の実行（乱数の入力、小さいマリオと大きいマリオで 1,100 回ずつ、それぞれ 600 フレームまで）。

| 実行 | フレーム | 音のルーチンの最後のドット（最大） | すべての命令（最大） |
|---|---|---|---|
| 部屋のムービー | 111 | 6,491 | 41,402 |
| 自前の実行、小さい | 51,791 | 6,497 | 42,151 |
| 自前の実行、大きい | 55,755 | 7,159 | 42,437 |

だから `LateS`（9,000）は測ったすべてのフレームで成り立つ。大きいマリオでの余裕は 1,841 ドット。`Late` をまだ求めるフレーム `U` は、ムービーの 111 フレームのうち 14（ラウンド 28 の数: 最初のフレームと、制御 6 からのフレームの次の 13）。

## 仮定（Lean では証明していない）

* フレーム `U` での **`roomLate`**: 歩き (i) と (iv) は、歩きが知らないバッファから始まる。すると画面の更新のレコードのループの回数を歩きは知らない。時間つきで測った（`timecheck 3`）: 歩き (i) は 91,263 状態のうち 11、歩き (iv) は 222,570 のうち 26 が失敗し、すべて画面の更新の中。
* ほかのフレームでの **`roomLateS`**: 音のルーチンの命令はドット 9,000 までに走る。証明には各フレームの始めの曲の状態がいる（ラウンド 6 は本当の実行で 207 の曲の状態を測った。音のバイトの任意の値での音のルーチンのまとめは偽）。

## 再現

```
.lake/build/bin/smbrta buffer-ctl-check FM2 1 timecheck     # 時間つきの 2 つの歩き、ネイティブ（2 なら recCheckT も）、約 8 分
.lake/build/bin/smbrta buffer-ctl-check FM2 3 timecheck     # 時間つきの歩き (i) と (iv): 画面の更新で失敗する（測るだけ）
.lake/build/bin/smbrta buffer-ctl-check FM2 1100 latereal   # 本当のフレームのドット
.lake/build/bin/smbrta buffer-ctl-check FM2 0 late2         # クランプがまったくない歩き (ii) の探索、前の呼び出しの場所で（測るだけ）
```
