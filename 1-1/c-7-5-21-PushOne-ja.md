# 角にいるフレームのあとは 1 ピクセルまで

[ボーナス部屋をつなぐ](c-5-RoomJoin-ja.md) のフィールド `low_at` はなくなりました。ラウンド 27 からは、`C + 41` から `C + 43` までのフレームで、136 から 151 ピクセルで角かその先で終わり、`C + 40` からのすべてのフレームが角かその先のものだけを求めていました（[低いフレームごとの上限](c-7-5-20-LowBound-ja.md)）。測った走りには、このようなフレームはありませんでした。

いまは `low_by` がこれらのフレームを 3 つの事実から証明します。

1. `low_floor` と `low_jump` が証明するフレームは、角から多くて `lowT = 383/256` ピクセル先です。`S_low = 415/256` ピクセルより狭い上限です。
2. そのようなフレームが角かその先にあるとき、空中で始まる次のフレームは多くて 1 ピクセルしか右へ動きません（`push_one`）。
3. 落下のあとの床からのどのジャンプでも、フレーム `C + 40` は 152 ピクセルかそれより下で終わります（`riseCheck`。跳ぶフレームが読む保存された速さ `off_ab` を使います）。

## 命題

`P(n)`、`y(n)`、`v(n)` はフレーム `n` の終わりの位置（1/256 ピクセル単位）、高さ、速さです。`c_P` は角（51 ピクセル）です。`top` は最高速で、1 フレームで多くて `16·top = 640/256` ピクセル動きます（`move_top`）。`cy = cornerY`（136 ピクセル）で、`cy + 16` は 152 ピクセルです。`fall = 34`、`hitF = 37`、`runF = 40`、`fall + 1 + rise = 43` です。`ab(n)` はフレーム `n + 1` が読む保存された速さです。`v_A = 25` は空中の速さのしきい値です。

```
LowS(s, n)   ⇔  P(n) ≤ c_P + s ∧ (Stop(n) ∨ P(n) < c_P ∨ v(n) < 0)          LowAt(n) = LowS(S_low, n)
SlackOK(s)   ⇔  255 ≤ s ∧ 16·top − 257 ≤ s ∧ s + 16·top < 1280
lowT         =  16·top − 257 = 383                                           (S_low = 415)

RoomCore.low_floor, low_jump（証明。SlackOK(s) を満たすどの s でも）:
  落下のあとの床のフレームと、cy + 16 かそれより下で終わる間の床からのジャンプで、LowS(s, ·) が続く

RoomCore.push_one（証明、新しい）:
  C ≤ n < t₀ ∧ n < C + standF ∧ st(n) ≠ 0 ∧ (Stop(n) ∨ v(n) < 0)  →  P(n + 1) ≤ P(n) + 256

RoomCore.off_ab（証明、新しい）:
  C ≤ n < t₀ ∧ n + 1 < E ∧ jump(n + 1)  →  vs(n + 1) = jumpOff(y(n), ab(n)) ∧ ab(n) < 256

low_by（証明。これらのフレームでフィールドを使わない）:
  C ≤ n ≤ C + 43 ∧ n ≤ t₀  →  P(n) ≤ lowB(n − C)
```

ROM の確認が 2 つあり、非公開の `room_corner_facts` で `native_decide` で確かめます。

```
gainCheck:  定義域の状態 s で v(s) < 0 のもの、空中の入力 i のすべてで:  V(hstep(s, i)) ≤ g_fast        (V = 256·v + サブ速度、g_fast = 456)
riseCheck:  v < 256 のすべてと各フレームの A のすべてで:  jumpOff(groundY, v) からのジャンプのフレームは cy + 16 かそれより下で終わる。
            跳ぶフレームのあと、v < v_A なら 5 フレーム、v ≥ v_A なら 4 フレームまで
```

ほかに `CornerFacts.tight`（`255 ≤ lowT`）、`off16`（床から跳ぶフレームは 152 ピクセルかそれより下で終わる）、`floor16`（床も同じ）、`fall2`（`fall + 2 ≤ hitF`）があります。

## `low_by` が古いフィールドのフレームを証明するやり方

場合は次のとおりです。壁に触らず、`n` は `C + 41` から `C + 43` まで、`n` は床のほかで 136 から 151 ピクセルで終わり、`C + 40` から `n` までのすべてのフレームが角かその先です。`v_chain2` から、`C + 34` からのフレームはあるフレーム `T'` まで床にいて、そのあとは `T'` からのジャンプのフレームです。ジャンプの最初のフレームでは高さが増えません（`arc_down`）。

**フレーム `C + 40` が 152 ピクセルかそれより下で終わるとき。** `d` についての帰納法で、`n` までのフレーム `C + 40 + d` で 152 ピクセルより上で終わるものは次を満たします。

```
P(C + 40 + d) ≤ c_P − 1 + 16·top·d
```

- `d = 0`: フレーム `C + 40` は 152 ピクセルより上で終わりません。
- 1 つ前のフレームが 152 ピクセルより上で終わるとき: 最高速で 1 フレーム（`move_top`）。
- 1 つ前のフレーム `k` が 152 ピクセルかそれより下で終わるとき: `k` はジャンプのフレームです（床は 176 ピクセル、跳ぶフレームは 171 か 172 ピクセルで終わります）。`k` までのジャンプのフレームはすべて 152 ピクセルかそれより下で終わる（`arc_down`）ので、`LowS(lowT, k)` です（床のフレーム `T'` からの `low_jump`。`T'` は `low_floor` で `LowS(lowT)` か、角より左です）。`k` は角かその先なので、`Stop(k)` か `v(k) < 0` です。すると `push_one` で `P(k + 1) ≤ c_P + 383 + 256 = c_P − 1 + 16·top` です。

`d = n − (C + 40)` とすると、これは `lowB(n − C)` です。

**フレーム `C + 40` が 152 ピクセルより上で終わるとき: ありえません。** それは `T'` からのジャンプのフレームで、`C + 34 ≤ T' < C + 40` です。跳ぶフレーム `T' + 1` の入力にはジャンプがあります（`vfloor`: 床のフレームは床にとどまるか、跳びます）。なので `vs(T' + 1) = jumpOff(groundY, ab(T'))`（`off_ab`）で、ジャンプのそのあとのフレームは `vstep` です（`varc`）。フレーム `C + 40` は、跳ぶフレームの `C + 40 − (T' + 1)` フレームあとです。

- `T' = C + 34` なら、落下のすぐあとに跳びます。壁に触らない落下のフレームは空中のフレームなので、速さは空中のしきい値より小さいままです（`capped_along`）。跳ぶフレームが読む保存された速さもしきい値より小さいです（`ab_of`、`fall2`）。なのでフレーム `C + 40` は、遅く跳ぶ跳びの跳ぶフレームの 5 フレームあとです。
- `T' ≥ C + 35` なら、跳ぶフレームの多くて 4 フレームあとです。

どちらも `riseCheck` に入るので、フレーム `C + 40` は 152 ピクセルかそれより下で終わります。

床からのジャンプのいちばん小さい高さを、跳ぶフレームからのフレーム数ごとに示します（ROM で評価しました）。

| 跳ぶフレームのあとのフレーム数 | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|---|
| 遅い（保存された速さが 25 より小さい） | 172 | 168 | 164 | 160 | 157 | 153 | 150 | 147 | 144 |
| 速い（25 以上） | 171 | 166 | 161 | 156 | 152 | 148 | 144 | 140 | 136 |

## 余裕を変えない理由

`push_one` を使うには、1 つ前のフレームが角から `lowT = 383/256` ピクセル以内である必要があります。`low_step`（`low_floor_of` と `low_jump_of` の一歩）がこれを与えます。どの場合も、次のフレームは多くて `max(c_P + 16·top − 257, P(n))` です（角より左から最高速で 1 フレーム動いて 1 ピクセル押し戻される、左へ動く、または止まった状態から 17 より小さい速さ）。なので `low_floor` と `low_jump` は `SlackOK` のどの余裕でも成り立ちます。`lowSlack` そのものは 415 のままです。383 にすると、確認 `NumFacts.wall_low`（壁に触ったあとの低いフレーム）が 1/256 ピクセル足りません（余裕 −1。415 なら +31）。

## 測ったこと

`room-approach-check FM2 300 1`（大きいプレイヤー: 最初の操作で大きさのバイトを大きいにした、人工の状態）と `… 300 0`（小さいプレイヤー）。どちらも TAS と自分の入力 2,700 本です。

| 大きさ | ラウンド 27 のフィールドのフレーム | そのうちフレーム `C + 40` が 152 ピクセルより上のもの | `c_P + lowT` より先の `low_jump` のフレーム（バグ） | `push_one` のフレーム | そのうち 1 ピクセルより右へ動くもの（バグ） |
|---|---|---|---|---|---|
| 大きい | 0 | 0 | 0 | 86,366 | 0 |
| 小さい | 0 | 0 | 0 | 86,275 | 0 |

壁に触らない走りで、フレーム `C + 40` が 152 ピクセルより上で終わるものはありませんでした（カウンタ 33: 大きいで 1,193 本のうち 0、小さいで 1,187 本のうち 0）。`push_one` は、すべての走りで、`C + 50` より前の `t₀` までのフレームで、止まったか左へ動くフレームのあとに空中で始まるものを数えました。

## 残ること

- `low_at` で残ることはありません。
- `Approach.low` は残ります（測ったフレームは大きいプレイヤーの 3 個です。ブロックの左の列の上のコインが横の判定を取り、そのフレームは押し戻されません）。
- `stand_wall`（2 回目の立ち）、`stand_fast`、`stand_P` は、このラウンドでは変えていません。`facing` は `hstep` に従わないフレームだけに狭めました（[落下の間の向き](c-7-13-1-FallFacing-ja.md)）。

**ファイル。** `Theorems/RoomJoin.lean`: `LowS`、`SlackOK`、`lowT`、`gainCheck`、`gain_of_check`、`riseFrom`、`riseCheck`、`takeoff16`、`slack_ok`、`tight_ok`、`low_floor_atS`。`RoomCore.low_floor` と `low_jump` は `SlackOK` のどの余裕でも。新しい `RoomCore.push_one`（`RoomRun.push_one_of`）と `RoomCore.off_ab`（`RoomRun.off_ab_of`）。`CornerFacts` の新しいフィールド: `tight`、`gain1`、`gain2`、`gain3`、`off16`、`floor16`、`rise`、`fall2`。`low_by`。`RoomFields.low_at` はなくなりました。非公開: `Proof/RoomJoin.lean` の `room_corner_facts`（`native_decide` の行が 8 つ増えた）。プログラム: `room-approach-check`（カウンタ 28 から 32）。
