# 城に入ったあとの星の旗の規則

**主張.** これは部分的な結果です。城に入ったあとの最初のフレームの機械が 1 つの条件 `Good` を満たし、処理が 2 で、旗が作られた高さにあるとします。すると入力が何でも、本物の機械のカウンタは、レベルが変わるまでの全部のフレームで 1 フレームの規則に従います。レベルが変わるのは、処理 5 で始まるフレームです。ポーズで終わるフレームはカウンタを変えません。これは `lag` のフレームです。ほかのフレームは `FlagRun` に従います。これで [城から 1-2 まで](g-1-CastleToLevel-ja.md) の `Flag` のフィールド `step`、`task_E`、`y_E`、`task_L` が定理になります。条件 `Good` は、城に入ったときの 1 つの状態についての仮定として残ります。確認がポーズをどう扱うかは [城に入ったあとのポーズ](g-2-5-FlagPause-ja.md) にあります。

`seq(n)` はフレーム `n` が始まるときの機械、`inp(n)` はその入力です（[1-1 全体](0-1-Route-ja.md) の `Changes`）。`seq(n + 1) = frame(seq(n), inp(n))` です。`m[b]` は `m` のバイト `b` です。`E` は城に入るフレームです。`r` は基準の機械です。自分の道筋（`CastleWalk`）で遅れなしに城に入り、タイマーは本物のままです。`lim`、`w₀` は [城から 1-2 まで](g-1-CastleToLevel-ja.md) と同じです。

## 文

```
x(m)       = (task, t, y, w, ph)    m のカウンタ（flagOf）。旗は最初の敵スロット
paused(m)  = (m[GamePauseStatus] &&& 1 ≠ 0)

After(seq, inp, E, T, c, L) :
  Good(seq(E + 1))
  task(seq(E + 1)) = 2,   y(seq(E + 1)) = y(r)
  t(seq(E + 1)) = T,      ph(seq(E + 1)) = c
  E < L
  level(seq(L + 1))                         レベルの番号か面の番号が 0 でない
```

定理です。

```
flagCheck(C, d) = true  →  Checked(C, d)                         checked_of_check

Checked(C, d),  Good(m),  どんな入力 i でも  →
  frame(m, i).frame = m.frame + 1
  ¬ level(m),  ¬ level(frame(m, i))
  paused(frame(m, i))    →  x(frame(m, i)) = x(m)  ∧  Good(frame(m, i))
  ¬ paused(frame(m, i))  →  FlagRun(lim, w₀, x(m), x(frame(m, i)))  ∧  (task(frame(m, i)) = 5  ∨  Good(frame(m, i)))
                                                                  frame_step

Checked(C, d),  ∀ n, seq(n + 1) = frame(seq(n), inp(n)),  After(seq, inp, E, T, c, L)  →
  Flag(lim, w₀, E, T, c, L)                                        flagOf_after
```

`flagCheck` は ROM の確認です。非公開の証明で `native_decide` が示します（`flag_check`）。`C` は確認の文脈（`r`、知っているバイト、名前）、`d` はそこから計算する抽象状態です。

`flagOf_after` が作る `Flag` では、`x(n)` は最初の処理 5 のフレームまでは `seq(n)` のカウンタです。そのあとは最初の処理 5 のフレームの値で止めます。`lag` のフレームは次のとおりです。

```
lag(n)  =  E < n  ∧  (task(x(n)) = 5  ∨  paused(seq(n + 1)))
```

最初の処理 5 のフレームからあとは、止めた値を保ちます。ポーズで終わるフレームは `frame_step` によりカウンタを保ちます。`lag` のフレームはレベルの変化を遅らせるだけです（`Flag.hL` はどの `lag` でも成り立ちます）。

## 条件 `Good`

`Good(m)` は次のことです。

* `m` は 240 個の抽象状態 `B₀` のどれかに含まれます。パッドは知りません。
* `ph < 21`、`task ∈ {2, 3, 4}`。
* タイマーの 3 つの数字は、ある `t ≤ tmax` の数字です。`tmax` は 1-1 が始まるときのタイマーの値に 1 を足したものです。
* マリオの数 `(v, F, f, A, C, s)` は集まり `Q` に入ります。`v` は速さ、`F` と `f` は 2 つの力の端数、`A` は速さの大きさ、`C` は当たりのビット、`s` は横に当たってからのタイマーです。`Q` は、壁に当たったときの数から 1 フレームずつたどった 6714 個です。壁に当たったときは `v = 0`、`s` は当たったときの値、`F` は 4 の倍数、`f` は 16 の倍数です。
* `RunningSpeed` と `Player_MovingDir` は `r` と同じです。
* `task ≠ 4  →  lim − 1 ≤ y ≤ y(r)`、`task = 4  →  w ≤ w₀`。

`B₀` は ROM と `r` から計算します。`B₀` の状態は次のことを知っています。

* フレームは待ちの繰り返しで終わっています。プログラムカウンタ、スタック、PPU のフラグ、ドットの範囲です。
* 345 バイトのほとんどが `r` と同じ値です。`knownNames` の名前のバイトと、1 つ目のブロックバッファの全部です。モード、面と面の番号、マリオの状態と大きさと位置、ゲームのタイマーの制御、音の一部、スプライトの割り当て、浮かぶ数字の制御、大砲のバイトなどです。
* ポーズのバイトは一部だけ知っています。`GamePauseStatus` は 0、1、0x80、0x81 のどれかです。`PauseModeFlag` と `PauseSoundQueue` は 3 以下です。`GamePauseTimer` は何でもかまいません。
* 星の旗は最初の敵スロットにあります。ほかの 4 つのスロットは空か、全部が花火です。
* `EventMusicBuffer` は `r` の値か 0 です。画面の左と右の x と `ScrollThirtyTwo` は上のビットだけ知っています。

ほかのバイトは何でもかまいません。スコア、コイン、乱数、フレームカウンタ、`HorizontalScroll`、音楽の位置（四角波 1 は値ごとに分けます）、花火の状態、カウンタの値、ポーズの音です。

## 確認のしくみ

1 フレームを 13 の名前のある場所で切ります。`SoundEngine`、`MusicHandler`、`ReadJoypads`、`DecTimers`、`NoDecTimers`、`PlayerEndLevel`、`PlayerSubs`、`GetXOffscreenBits`、`GetPlayerOffscreenBits`、`RunStarFlagObj`、`FloateyNumbersRoutine`、`FlagpoleRoutine`、`RunGameTimer` です。最後はフレームの終わりです。機械が最初にその段の場所のどれかに来たときを次の段とします（`Next`、`Arr`）。ポーズのために 2 つの段は 2 つ目の場所を持ちます。音の段は `SkipSoundSubroutines` で終わることがあり、パッドのあとの段は `SkipMainOper` で終わることがあります。その場所から始まる段が 2 つ増えます（段 14 と 15）。[城に入ったあとのポーズ](g-2-5-FlagPause-ja.md) を見てください。

各段で、[抽象機械](b-2-3-TaintRun-ja.md) の歩きを 3 種類確かめます（`Checked`）。

* 覆う: 段の状態から、次の場所で、そこから始まる段の状態に来ます（`CoverP`、`nextIdx`）。
* 事実: ある値なら、次の場所でどれかの値です（`FactP`）。位相、インターバルタイマー、横のタイマー、マリオの動き（4844 通り）、壁、タイマーの数字、旗の高さ、花火の数、最後の待ちです。
* 保つ: ある条件のもとで、バイト `b` は変わりません（`KeepP`）。値が 2 以上のときは `b` をカウンタにした歩き（`Env.rkI`）です。0 と 1 は値を知った歩きです。

`frame_step` はこれらを順につなぎます。カウンタが規則どおりに変わり、マリオの数が `Q` に戻り、フレームの終わりで `B₀` に戻ります。

## 測ったこと

入ったあとの状態から 1 フレーム（カウンタは知らない、ほかは知っている）:

```
処理  ステップ  失敗
2     5173      0
3     3669      0
4     3942      0
5     2836      0
```

音楽と花火のバイトも知らないと、40 万ステップで 84 の失敗です。最初の失敗は四角波 1 のデータを読む繰り返しです。位置を知らないと 0 のデータで終わりません。なので四角波 1 の位置は、その場所で値ごとに分けます（`splitAt`）。

確認の時間（ネイティブ、`flag-rule-check`）は、ポーズのための変更の前で約 34 秒です。状態を作るのに 6 秒、ほかのスロットの段に 16 秒、音楽の段に 3 秒です。変更のあとは、ほかの作業者が 5 人同時にビルドしているとき（28 コアで負荷平均 15〜20）、2 回で 56 秒と 61 秒でした。このとき、変えていない、ほかのスロットの段は前の 1.6 倍と 1.9 倍でした。この倍率で割ると確認は 33〜35 秒です。ポーズの 2 つの段は数ミリ秒です。非公開の証明 `flag_check` のビルドは、ほかの作業者がいるときで 95 秒でした（前は 47 秒）。時間のほとんどは「保つ」の歩きです。バイト 15 個 × 歩き 3 本 × 表の状態（ほかのスロットの段で 2562 個）です。抽象機械が一度に追えるカウンタは 1 バイトだけです。

## 証明していないこと

* `Good(seq(E + 1))`、`task = 2`、旗の高さは仮定です。城に入るまでのフレームからは証明していません。上の走りで確かめました。
* `Good` の外は扱いません。大きいマリオ、ほかのスロットにある旗、花火でない物のあるスロット、`Q` の外のマリオの数、`tmax` より大きいタイマー、`B₀` と違うバイトです。
* `t(seq(E + 1)) = T`、`ph(seq(E + 1)) = c` は `Frames` とつなぐフィールドのままです。
* `GMerge`（1-1-g-2-3）はここでは扱いません。
