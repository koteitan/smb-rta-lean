# 旗のタイル: 解析が遅れていないフレームの制御バイト 6

31 回目のラウンドはフィールド `ctlU` を残しました（[各フレームの厳しい規則](f-6-17-12-PoleStrict-ja.md)）。これは、触るフレームより前の、プレイヤーのルーチンに来る各フレームの各 `UpdScrollVar` で、画面のバッファの制御バイトが 6 でないことを求めていました。このラウンドは、そこでエリアの解析が遅れているときだけ、これを求めます。ほかのフレームでは、制御バイトが 6 のフレームも `JV` を保ちます。

## 言葉

`N` はエリアの解析の残りのタスクの数、`S` は 32 px のスクロールのカウンタ、`ctl` は画面のバッファの制御バイト。`m` からのフレームについて、`k₂` はスクロールの処理のあとの `UpdScrollVar`、`e` はフレームの終わり。`k₂` で、カウンタにはもうスクロールの量が足されています。

```
JV(v)    :=  N ≤ 7  ∧  S + 3·N < 32
late(k)  :=  S(k) + 3·N(k) ≥ 32
```

## コードが制御バイトを書くところ

コードから（コミュニティの逆アセンブルの名前で）:

* 各フレームの始まりの画面の更新が 0 にします。
* ゲームの中心の処理で、`UpdScrollVar` より前では、`RemoveCoin_Axe` だけが書き、6 にします。これが走るのは、マリオが頭か足か横でコインを取るとき（`HandleCoinMetatile`）、斧に触るとき（`HandleAxeMetatile`）、下からたたいたブロックの上にコインがあるとき（`CheckTopOfBlock`）です。
* `UpdScrollVar` のあとでは、解析のタスクが、次のフレームの画面の更新のために 6 にします。

なので `ctl(k₂) = 6` となるのは、マリオがコインを取るフレームだけです。そのとき `UpdScrollVar` はタスクを走らせません: `N` と `S` は `k₂` での値のままです。

## 1 フレーム（`Theorems/PoleLate.lean`、`Theorems/PoleStrict.lean`）

`PoleParser.frame_six` は、`ctl` のどの値でも、フレームの終わりの弱い形を出します: `N ≥ 1` なら `N(e) = N` か `N(e) = N − 1` で、`S(e) = S(k₂)`（列の進みには `colEnd_n`）。`N = 0` なら、バイトを保つか、新しい列を始めます。新しい列には `S(k₂) ≥ 32` が要ります。

`jv_weak`: `N ≤ 7`、`S(k₂) + 3·N < 32`、`N(e) ≤ N`、`S(e) = S(k₂)` から

```
N(e) ≤ 7   ∧   S(e) + 3·N(e) < 32
```

`N = 0` なら `S(k₂) < 32` なので、新しい列は始まりません。そこで `step_strict` は、いま、各 `UpdScrollVar` `k` で次を受け取ります:

```
ctl(k) ≠ 6   ∨   S(k) + 3·N(k) < 32
```

`ctl(k₂) ≠ 6` なら、証明は 31 回目のラウンドのもの（厳しい形）です。そうでなければ `S(k₂) + 3·N < 32` で、`jv_weak` が `JV(e)` を出します。`invJ_onFrames` は、プレイヤーのルーチンに来る各フレームで、同じ条件を受け取ります。

## フィールド

前（31 回目のラウンド）、触るフレームより前の、プレイヤーのルーチンに来る各フレーム `n` で:

```
ctlU :  その各 UpdScrollVar k で、  ctl(trace(all n, k)) ≠ 6
```

いま:

```
ctlU :  その各 UpdScrollVar k で、  ctl(trace(all n, k)) ≠ 6   ∨   S(trace(all n, k)) + 3·N(trace(all n, k)) < 32
```

`S` は `PoleJoin.parSOf`、`N` は新しい `PoleJoin.parNOf`（`UpdScrollVar` のタスクの数の読み込みのオペランド）。新しいフィールドは前のものより弱いです: 解析が遅れていないところでは何も求めません。1 つの状態の条件のままです。定理の型で変わったのは、`PoleStrict.step_strict` と `PoleStrict.invJ_onFrames` の `hk6` の型だけです。`route_1_1` の結論は `1748 + j ≤ L` のままです。

## 測ったこと

`pole-keep parser FM2 96`（30 回目のラウンドと同じラン: TAS、TAS のフレーム 900 から 1089 からの自分の乱数の入力、最初の操作からの自分の乱数の入力。1 分 31 秒、73 MB）。操作で始まるフレームの各 `UpdScrollVar` で:

| | TAS | 乱数 900–1089 | 最初の操作からの乱数 |
|---|---|---|---|
| 地上 | 608 | 10,086 | 18,682 |
| そのうち遅れている（`ctlU` が `ctl ≠ 6` を求める） | 40 | 242 | 205 |
| そのうち新しい `ctlU` が偽 | 0 | 0 | 0 |
| 遅れているもののうち `N = 0`（新しい列が始まる） | 40 | 242 | 205 |
| どのエリアでも、`ctl = 6` | 13 | 0 | 0 |
| そのうち遅れている | 0 | 0 | 0 |
| 地上で `RemoveCoin_Axe` にいる命令 | 0 | 0 | 0 |
| どのエリアでも、`RemoveCoin_Axe` にいる命令 | 13 | 0 | 0 |
| ブロックのバッファにコインのタイルがある、地上のフレームの始まり | 0 | 0 | 0 |
| 地上で、コインのタイルをブロックのバッファに書く書き込み | 0 | 0 | 0 |

なので地上で、フィールドが制御バイトを求めるのは、TAS の 608 回のうち 40 回になりました。遅れているところは、どれも解析が新しい列を始めるフレームでした。TAS で `ctl = 6` の 13 回は地下の部屋で、そこでマリオはコインを取ります（`RemoveCoin_Axe` が 13 回走る）。そのどれも遅れていません。（`RemoveCoin_Axe` はコードから見つけます: `HandleAxeMetatile` の終わりのジャンプの行き先。コインのタイルはシンボル `CoinTile`。）

この数から、`ctlU` をなくす道は次のとおりです: 「ブロックのバッファにコインのタイルがない」という地図を、操作の始まりで切り替えの行から出し（`PoleTileCtl.colMap₀` と同じ）、`PoleTileWalk.frames_colMap` が旗の地図を運ぶようにフレームからフレームへ運び（`bufAll` の場所での書き込みの条件で）、そのあと、コインの枝を切ってフレームの中で `ctl` を追う歩きをする。

## 証明していないこと

* `ctlU`: 解析が遅れている地上のフレームで、マリオがコインを取らないこと。証明には、各フレームのマリオの読みでのブロックのバッファの中身（そこにコインがない）が要ります。これは `TileSlot` の (slot) と同じ種類の事実です。
* フレームの始まりから `UpdScrollVar` まで `ctl` を追う歩きは、「フレームがコインを消さなければ `ctl = 0`」しか出しません。それには、添え字かポインタを通した書き込みが書いてはいけないバイトに `ctl` を入れる必要があります（ポインタを通した書き込みが `UpdScrollVar` より前に走る。たとえばブロックのオブジェクトの更新）。すると `guardE` が変わり、パート a と b の合わせたガードも変わります。していません。
* `TileSlot`（slot、near、旗のページの 2 つ前のページでの read）、`bufAll`（7 か所）、`keepB`（66 か所）: 変えていません。
