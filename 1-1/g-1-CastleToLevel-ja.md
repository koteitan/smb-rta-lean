# 城に入ってから 1-2 が始まるまで

**主張.** レベルが変わるのは、`E + T + D + 107` 以後で最初の、21 フレームの格子の点です。走りのどの部分も TAS 以上に長くかかり、ゲームのタイマーが規則どおりに動き、格子が走りのフレームで決まる位置にあるなら、1748 より前にレベルは変わりません。

量はすべてフレームで数えます。

```
E            城に入るフレーム（StarFlagTaskControl が立つ）。フレーム 0 は 1-1 の最初の操作
T            E でのゲームのタイマー
D            33。T の一の位で 1 → 34、3 → 98、6 → 194
c            E でのインターバルタイマーの位相
wait         (c − T − D) mod 21
L            レベルが変わるフレーム
P1, P2, P3   プレイのフレーム数: 1-1、地下の部屋、地上で触るまで
X1, X2       2 回のエリアの切り替え
W            触ってから E まで
j            タイマーが動かないフレーム数。切り替えごとの 1 フレームは除く
q, t0        タイマーの周期と、最初に減る前の値
```

定理です。

```
level_ge:
  hq   :  2 ≤ q
  ht0  :  t0 = 370 + ⌈368/q⌉ + ⌈111/q⌉ + ⌈240/q⌉
  hP1  :  368 ≤ P1            hX1 :  91 ≤ X1
  hP2  :  111 ≤ P2            hX2 :  282 ≤ X2
  hP3  :  (234 ≤ P3 ∧ 132 ≤ W) ∨ (240 ≤ P3 ≤ 241 ∧ 126 ≤ W) ∨ (242 ≤ P3 ∧ 125 ≤ W)
  hE   :  E = P1 + X1 + P2 + X2 + P3 + W + j
  hT   :  t0 ≤ T + ⌈P1/q⌉ + ⌈P2/q⌉ + ⌈P3/q⌉
  hD   :  33 ≤ D
  hc   :  (c + E) mod 21 = (3 + j) mod 21
  hL   :  E + T + D + 107 + wait ≤ L
  ⟹  1748 + j ≤ L
```

ゲームのタイマーの値を入れると `hq` と `ht0` は計算で決まります。残りの行だけが仮定です（非公開の `level_ge_rom`）。

TAS の値は動画を走らせて読みました。`P1 = 368`、`X1 = 91`、`P2 = 111`、`X2 = 282`、`P3 = 240`、`W = 126`、`j = 0`、`E = 1218`、`T = 370`、`D = 33`、`c = 3`、`wait = 20`、`L = 1748` です。なので `E + T + D + 107 = 1728` で、格子の点は 1727 と 1748 です。この値が仮定を満たすことを Lean で確かめました（非公開の `level_ge_tas_numbers`）。このページ自身の道筋の値も満たします（非公開の `level_ge_own_numbers`）。なので仮定は矛盾していません。

算術の部分のほかの定理です。

```
level_next    :  S ≤ S + wait < S + 21,  (S + wait) mod 21 = (c + E + 107) mod 21,   S = E + T + D + 107
level_mono    :  (c + E) ≡ (c' + E') mod 21  ∧  E + S ≤ E' + S'  ⟹  E + S + wait(c, S) ≤ E' + S' + wait(c', S')
sum_mono      :  Pi ≤ Pi'  ⟹  P1 + P2 + P3 + T(P) ≤ P1' + P2' + P3' + T(P'),    T(P) = t0 − Σ⌈Pi/q⌉
playN_t       :  サブカウンタ 0 からプレイ p フレームで、タイマーは ⌈p/q⌉ 減る
level_ge_of_late :  E = P1 + X1 + P2 + X2 + P3 + W + F,  20 ≤ F,  と hq ... hP3, hT, hD, hL  ⟹  1748 ≤ L    （格子は要らない）
```

`hE`、`hT`、`hc`、`hD`、`hL` は 1 フレームごとの規則から証明します。次の 2 つの節です。

本物のフレームでの確認が示すことです。挙げた状態だけです（非公開の `castle_to_level`、`native_decide`）。`0^k` は入力なしの `k` フレーム、`I` は [城までの歩き](f-4-CastleWalk-ja.md) の 64 通りの入力です。

```
phases    :  T = 125、土台の横で 21 通りの遅れ d:  1 ≤ k ≤ T + 33 + 107 + wait について level(run(E_d, 0^k)) ↔ k = T + 33 + 107 + wait;  (c + E) mod 21 = 3
real      :  道筋のタイマーそのままで同じ。歩きで T は変わらない
values    :  T = 200 で同じ
fireworks :  T = 131, 133, 136 で、D = 34, 98, 194 として同じ
slide     :  ほかの高さで触っても同じ
allInputs :  GMerge  →  ∀ w ∈ I^148:  level(run(E*, w)) ∧ ∀ k, 1 ≤ k < 148 → ¬level(run(E*, w[..k]))
runs      :  3 つのエリアに空のフレームを入れた本物の走り 6 つ:  全部のフレームが Step と plan に従う、
             T + Σ⌈Pi/q⌉ = t0、タイマーが動かないフレームは 2 つ、最後に (c + f) mod 21 = 3
pauses    :  5 つの区間それぞれにポーズを入れた本物の走り 1 つ:  同じ。j = 252、タイマーが動かないフレームは 2 + j
starts    :  タイトルで 5 通りのフレームに Start を押す:  フレーム 0 の位相、タイマー、サブカウンタは同じ。
             フレーム 0 の前は s(0) = (t0, 0)、ph(0) = 2
flags     :  phases、real、values、fireworks の城に入った状態:  レベルが変わるまでの全部のフレームが FlagStep に従う、
             task(E + 1) = 2、lim + 30 ≤ y(E + 1)、task(L) = 5、early(L) = T + D
flagPauses:  T = 125、処理 2、処理 3、処理 4、レベルが変わるフレームにポーズ:  同じ。L は式より前にならない
```

`E*` は本物の城に入った状態で、チェーンを短くするためにタイマーを 8 に書き換え、音楽を止めたものです。

Lean: `Theorems/CastleToLevel.lean`（`level_ge`、`Frames`、`Flag`）、非公開の `level_ge_rom`、`castle_to_level`、`castle_level_formula`、`castle_level_inputs`、`castle_level_timer`、`castle_level_flag`。

## 1 フレームごとの規則

走りのフレームは 1 つの列です（`Frames`）。`n` はすべてのフレームを数えた番号です。フレーム `n` には種類 `k(n)` があり、`s(n) = (t, sub)` と `ph(n)` はフレーム `n` が始まるときのカウンタです。

```
k(n)     (t, sub) → (t', sub')                                       ph → ph'
play     sub − 1 = 0 なら (t − 1, q)、それ以外は (t, sub − 1)         (ph − 1) mod 21
auto     t' = t,  sub' ≤ sub − 1                                     (ph − 1) mod 21
setup    t' = t,  sub' ≤ sub                                         ph' = ph
lag      t' = t,  sub' = sub                                         ph' = ph

はじめ   s(0) = (t0, 0),  ph(0) = 2
```

`play` はプレイのフレームです。`auto` はタイマーは動くがプレイのルーチンは動かないフレームです。切り替えと、触ってから城までです。`setup` は切り替えごとに 1 つある、タイマーが動かないフレームです。`lag` はそれ以外のタイマーが動かないフレームです。ポーズと、処理が間に合わないフレームです。

どのフレームがどの区間かは、`lag` を除いて数えた番号 `r(n) = #{i < n : k(i) ≠ lag}` で決まります。

```
n ≤ E  →  k(n) = lag  ∨  k(n) = plan(r(n))

plan(r) = play    r < e₁
          auto    e₁ ≤ r < c₂,  r ≠ z₁      （r = z₁ で setup）
          play    c₂ ≤ r < e₂
          auto    e₂ ≤ r < c₃,  r ≠ z₂      （r = z₂ で setup）
          play    c₃ ≤ r < g
          auto    g ≤ r

k(E) ≠ lag,  r(E) = last
```

定理です。順序 `e₁ ≤ z₁ < c₂ ≤ e₂ ≤ z₂ < c₃ ≤ g ≤ last` と、`e₁ + q < c₂`、`e₂ + q < c₃` を使います（`Segs.Ok`）。

```
j = #{i < E : k(i) = lag},   T = t(E + 1),   c = ph(E + 1)

Frames.hE :  E = last + j
Frames.hT :  t0 ≤ T + ⌈e₁/q⌉ + ⌈(e₂ − c₂)/q⌉ + ⌈(g − c₃)/q⌉
Frames.hc :  (c + E) mod 21 = (3 + j) mod 21
```

証明は次のとおりです。

* `hE`: どのフレームも `lag` か、そうでないかです。なので `n = r(n) + #{i < n : k(i) = lag}` です。
* `hT`: 区間のプレイは `play` と `lag` だけなので、`playN` です（`play_stretch`）。切り替えでは数字は変わりません。`auto` のフレームごとにサブカウンタは 1 減り、切り替えは `q` より長いので、終わりには 0 です（`change_stretch`）。あとは `playN_t` です。
* `hc`: `(ph(n) + n) mod 21 = (2 + #lag + #setup) mod 21` です（`phase`）。`E` までに `setup` は 2 つです（`setups`）。

本物のフレームでは、種類は位相と操作で読みます（`kindOf`）。位相が動かなければ `lag` か `setup`、動いて操作できれば `play`、動いて操作できなければ `auto` です。Lean の確認 `runs`、`pauses` はこの規則そのもの（`Step`、`Segs.kind`）を全部のフレームで調べます。

フィールドは矛盾していません。どの区間についても、`lag` のない列があります（`Frames.noLag`）。

TAS と、1 フレーム遅く触る走りと、TAS の 36 か所に 45 から 66 フレームのポーズを入れた走りでも、全部のフレームが規則に従い、3 つの式が成り立ちました（`frames-check`）。死ぬ走りは `plan` に従いません。

**処理が間に合わないフレーム.** ハンマーブロス 5 つを近くに書き換えると、処理が次のフレームまで続くことがあります。フレームの境目でメモリを読むと、タイマーが減るのが 2 フレームに分かれます。`(t, 1) → (t, 0) → (t − 1, q)` か `(t, 1) → (t, q) → (t − 1, q)` です。2 つ目のフレームで位相は動きません。動くフレームとそのあとの動かないフレームをまとめると、規則どおりです。1500 フレームずつ 3 回で、境目で読むと規則に合わないフレームが 28 ありました。まとめると 0 です。なので `s(n)` は、その前のフレームの処理が終わったときの値です。書き換えていない走りでは、境目で読んだ値と同じです。

## 城に入ったあとのフレーム

フレームの列は `E` のあとも、レベルが変わる `L` まで続きます（`Flag`）。`Frames` は変えません。`x(n) = (task, t, y, w, ph)` はフレーム `n` が始まるときのカウンタです。星の旗の処理の番号、ゲームのタイマー、旗の画面での高さ、旗のインターバルタイマー、位相です。旗が上がると `y` は減ります。`lim` は旗が上がる高さ、`w₀` はその処理がセットする値です。どちらも ROM のコードから読みます。

動かないフレームは、カウンタを全部そのままにします。動くフレームでは `ph' = (ph − 1) mod 21` です。インターバルタイマーは位相が一周すると減ります。`ph = 0` なら `tick = w − 1`（0 で止まる）、それ以外は `tick = w` です。

```
処理 2,  t ≠ 0      task' = 2,  t' = t − 1,  y' = y,      w' = tick
処理 2,  t = 0      task' = 3,  t' = 0,      y' = y,      w' = tick
処理 3,  lim ≤ y    task' = 3,  t' = t,      y' = y − 1,  w' = tick
処理 3,  y < lim    t' = t,  y' = y,  (task' = 3 ∧ w' = tick) ∨ (task' = 4 ∧ w' = w₀)
処理 4              t' = t,  y' = y,  w' = tick,  task' = 4 ∨ (task' = 5 ∧ w' = 0)
```

処理 3 で `y < lim` のフレームは、処理 3 にとどまれます。花火です。処理 4 のフレームは、処理 4 にとどまれます。音楽です。なのでこの 2 つは遅らせるだけです。処理 5 で動くフレームはレベルを変えます。これがフレーム `L` で、規則には入れません。

`E < n < L` のどのフレーム `n` もこの規則に従います（`FlagStep`）。ほかのフィールドです。

```
t(E + 1) = T,  ph(E + 1) = c       Frames の T と c
task(E + 1) = 2
lim + 30 ≤ y(E + 1)                E での旗の高さ
E < L,  task(L) = 5
```

定理です。

```
early(n) = #{i : E < i < n, フレーム i は動く, task(i) ≤ 3}
D        = early(L) − T

Flag.hD :  33 ≤ D
Flag.hL :  6 ≤ w₀  →  E + T + D + 107 + wait(c, T + D) ≤ L
```

証明は次のとおりです（`Flag.Inv`、`inv_step`）。

* `hD`: 処理 2 で `r = t + (y + 1 − lim) + 2`、処理 3 で `r = (y + 1 − lim) + 1` とします。動くフレームで `r` は高々 1 減ります。`E + 1` で `r ≥ T + 33` です。処理 4 では使い切っています。なので `early ≥ T + 33` です。
* `hL`: 処理 3 までは動くフレームを全部数えるので、`(ph + early) mod 21 = c mod 21` です。`w` をセットするフレームのあと `ph = wait(c, T + D)` です。そのフレームの番号は `E + T + D` 以上です。処理 4 で `21 w + ph` は 1 フレームに高々 1 減ります。はじめは `21 w₀ + wait` です。処理 5 には `w = 0` が要るので、そのとき 20 以下です。`w₀ ≥ 6` なら `106 + wait` フレームです。フレーム `L` でもう 1 つです。

`D` は動かないフレームを数えません。なのでポーズで変わりません。ポーズは `L` を動かし、`D` と `wait` を変えません。

`6 ≤ w₀` はフィールドではありません。`route_1_1` が ROM から計算します（`by decide`）。

本物のフレームでは、カウンタをメモリから読みます（`flagOf`）。星の旗の敵スロットは名前で探します。位相が動かないフレームは動かないフレームです（`flagLag`）。

何も書き換えていない本物の走りです（`frames-check`）。全部のフレームが規則に従い、`hD` と `hL` は真です。`lag` は `E` のあとの動かないフレーム数です。

```
走り                                      E     T    c   D    lag  L     L − (E + T + D + 107 + wait)
TAS                                       1218  370  3   33   0    1748  0
TAS、フレーム 1089 のあと入力 02 80 80 80  1219  369  2   33   0    1748  0
TAS、最初に空のフレーム 96                 1314  366  12  194  0    2000  0
TAS、最初に空のフレーム 168                1386  363  3   98   0    1958  0
TAS、最初に空のフレーム 216                1434  361  18  34   0    1937  0
```

最後の 3 つでは本物の花火が上がります。`E` のあとの `d` フレームのポーズで `lag = d` になり、`L` は `d` 動きます。`D` は同じです。フレーム 1219、1300、1450、1590、1600、1625、1700、1747、1748 で、`d` は 45 から 66 で試しました。処理 2、3、4 とレベルが変わるフレームです。`E` の前のポーズ（フレーム 100 と 1100）は `j = 45`、`lag = 0`、`L = 1793` です。`E` のあとに Start を含む乱数の入力を入れた走りも規則に従います。6 回で、レベルが変わった 5 回は動かないフレームが 751 から 788 です。残りの 1 回は入力が終わるときポーズのままです。Start なしの 6 回は `L = 1748` です。

タイマーを入ったときに書き換えた `T` = 0、60、100、120 では、音楽のためレベルは `E + 265` まで変わりません。そこでも規則と `hL` は成り立ちます（`castle-level-check`）。

フィールドは矛盾していません。`1 ≤ lim` のどの数についても、`lag` のない列があります（`Flag.noLag`）。`lim = 0` だと `y − 1` は 0 で止まり、処理 3 が終わりません。

## しくみ

**入ったあとのフレーム**（コードから。1 フレームごとの規則は `FlagStep` です）。フレーム `E` で、星の旗の処理がタイマーの一の位を読みます。1、3、6 なら花火が決まります。続く `T` フレームでタイマーが 1 ずつ減ります。1 フレームでその処理が終わり、31 フレームで旗が上がります。その次のフレームで、インターバルタイマーが切れたときだけ減るタイマーをセットします。なので `D = 33` です。花火があると、このフレームが遅れます。花火 1 つで 1 フレーム、そのあと 1 つごとに 32 フレームです。そのあとインターバルタイマーの 6 段階に、106 フレームと次の段階までの遅れがかかります。その次のフレームでレベルの番号が変わります。合わせて `L = E + T + D + 107 + wait` です。

**音楽.** 最後の処理は、ファンファーレが終わるのも待ちます。この道筋の 21 の位相では、`T ≥ 125` なら音楽は終わっています。`T` が小さいと終わっていません。そのときレベルは格子の外で、式より遅く、`E + 265` で変わります。測ったどの場合も式は下界なので、`hL` は不等式です。

**入力.** A、B、上、下、左、右は無視されます。城へ歩くルーチンがボタンを上書きするからです。`allInputs` では、すべてのフレームで 64 通りの入力が同じ状態を与えます。本物の入った状態から `T = 360`、513 フレーム全部をプログラムで動かしても同じでした。

**タイマーの規則.** プレイのフレームでサブカウンタが 1 減ります。0 になるとタイマーが 1 減り、サブカウンタは `q` に戻ります。なのでタイマーはプレイの 24 フレームごとに 1 減ります。エリアの切り替えのあいだ、サブカウンタは 1 フレームに 1 ずつ減って 0 で止まり、タイマーの数字は変わりません。切り替えは `q` より長いので、終わりにサブカウンタは 0 です。なので、どのエリアも最初のプレイのフレームで 1 減り、プレイ `p` フレームでタイマーは `⌈p/q⌉` 減ります。そのため、`P1`、`P2`、`P3` が同じ走りでサブカウンタが違うことはありません。土管に入ったときの値は 0 まで減るからです。TAS は `⌈368/24⌉ + ⌈111/24⌉ + ⌈240/24⌉ = 31` 回減ります。最初の 1 回はフレーム 0 です。タイマーはフレーム 0 で 400、触るときに 370 です。TAS の触ったフレームでサブカウンタは 0 ですが、触ったことでルーチンがもう変わっているので、減りません。

**遅く着く場合.** `p` が増えても `p − ⌈p/q⌉` は減りません。なので走りの一部が長くなっても `E + T` は減りません（`sum_mono`）。同じになることはあります。`P3 = 241` は 1 フレーム多く 1 回多く減るので、和は同じ 1728 です。全部の部分で見ると、和が最小なのは `(368, 111, 240)` と `(368, 111, 241)` です。`hP3` の 3 つの場合は [操作から城まで](f-5-PoleJoin-ja.md) の `touch_castle` です。ほかの触り方で `P3 = 234`、`W = 132` だと、和は 1728 で TAS と同じです（測った最小は `W = 153`）。`P3 = 241` で `W = 125` だけが和を 1727 にします。なので `hP3` は `P3 ≤ 241` まで `W ≥ 126` を求めます。`P3 ≥ 242` では `W = 125` でも和は減りません。これには `2 ≤ q` を使います。

**格子.** タイマーが動くフレームごとに、位相は 21 を法として 1 減ります。位相はフレーム番号だけでは決まりません。エリアの切り替えごとに、タイマーが動かないフレームが 1 つあります（エリアの準備が 1 フレームを超えるからです）。TAS ではフレーム 418 と 732、このページの道筋では 490 と 862 です。なので位相は 1-1 で `(1 − f) mod 21`、2 回の切り替えのあとで `(3 − f) mod 21` です。1-1 の最初の操作の位相は、タイトルで Start を押した時刻によりません。35 通りの押し方で同じでした（Lean ではそのうち 5 通り）。コードでは、1-1 の前の画面はインターバルタイマーの段階で終わります。タイマーが動かないフレームがあると、全部が 1 遅れます。プレイのフレームと格子が一緒に動きます。`hE` と `hc` の `j` がこれです。結論も同じ `j` だけ動きます。

**花火と遅いフレーム.** `L` は和以後で最初の格子の点です（`level_next`）。フレームが増えて早い点になることはありません（`level_mono`）。花火があると `D` が大きいので、`L` は早くなりません。測ると `T = 360` と `T = 361` で `L` は同じです。

**ポーズ.** 本物の入った状態、`T = 360` で測りました。Start を押し、`k` フレーム後にもう一度押すと、`L` はちょうど `k` 動きます。ポーズのあいだ `c` は止まっています。2 回目の押しが効くのは `k = 45` からです。なのでポーズは `j ≥ 45` です。触る前のプレイのフレームでも、`j` = 45, 46, 47, 50, 66 で `(c + E) mod 21 = (3 + j) mod 21` を測りました。`T` が小さいと、音楽の再開がゲームより遅いので、もっとかかります。`T = 140` で 25 フレーム多くかかりました。

**ゲームは動くのにタイマーが動かないフレーム** があると、和を動かさずに格子だけが動きます。そういうフレームが 1 つあれば `L = 1728` になります。ゲームが動くのにタイマーが止まるのは、パワーアップ、敵に当たる、死ぬ、のときだけです。小さいマリオは、まずパワーアップが要ります。そのときゲームは 59 フレーム止まります（ルーチンとタイマーの制御を書き換えて測りました。本物のパワーアップではありません）。なので和は 20 フレームより多く遅れ、格子なしで `L ≥ 1748` です（`level_ge_of_late`）。

もう 1 つの場合はフレームの処理が間に合わないときです。入った状態でハンマーブロス 5 つを近くに書き換えると（星の旗は残す）、タイマーが動かないフレームが 60 あり、レベルはそれがないときよりちょうど 60 フレーム遅れました。

`E + T + D + 107` を TAS より小さくする方法は見つかりませんでした。和を動かさずに格子を動かす方法も見つかりませんでした。

## 前提（Lean では証明していない）

`level_ge` は数についての定理です。本物の走りがこの性質の数を与えることは仮定です。

* `hP1`、`hP2`、`hP3`: 道筋の各部分です。[道筋](../docs/route-1-1-ja.md) のほかの定理から来ます。それらをつなぐのは [1-1 全体](0-1-Route-ja.md) です。この 2 つの土管を通らない走りは含みません。
* `hX1`、`hX2`: [2 回の切り替え](b-1-PipeTransition-ja.md) です。挙げた入る状態について証明されています。処理が間に合わないフレームは `j` に数えます。
* `hE`、`hT`、`hc`: [1-1 全体](0-1-Route-ja.md) では `Frames` から証明します。仮定は `Frames` のフィールドです。各フレームが `Step` と `plan` に従うこと、`s(0)`、`ph(0)`、`E` の番号です。本物の走りがこれを満たすことは証明していません。このページの本物の走り 7 つの全部のフレームと、TAS で確かめました。パワーアップ、当たる、死ぬ、のフレームはこの形ではありません。パワーアップには `level_ge_of_late` を使います。死んでやり直す走りは含みません。
* `hD`、`hL`: [1-1 全体](0-1-Route-ja.md) では `Flag` から証明します。仮定は `Flag` のフィールドです。各フレームが `FlagStep` に従うこと、`task(E + 1) = 2`、`E` での旗の高さ、`task(L) = 5` です。本物の走りがこれを満たすことは証明していません。挙げた走りの全部のフレームで確かめました。旗がどの走りでも同じ高さから始まることは、まだコードから読んだものです。確かめたのはこれらの走りだけです。
* `T` と `c` で `Flag` と `Frames` を数としてつなぎます。`L` は処理 5 で始まるフレームです。レベルの番号がほかのフレームで変わらないことは、コードから読み、挙げた走りで見ました。フィールドではありません。
* `E` のあとの処理が間に合わないフレーム: 入ったときにハンマーブロス 5 つを書き換え、旗を最初のスロットと最後のスロットに置いた場合だけ測りました（そういうフレームが 26 と 66。リポジトリに入れていない作業用のプログラム）。境目で読んで `FlagStep` に合わないフレームはありませんでした。ほかの場合の証明ではありません。
* フレーム 0 の前のカウンタは、Start の 5 通りで確かめました。
* 等号としての式: 挙げた状態で、入力なしで、1 つの道筋から確かめました。全部の入力は 1 つの状態だけで、`GMerge` を仮定し、タイマーと音楽を書き換えています。本物の入った状態ではプログラムの結果で、定理ではありません。下界にはこれを使いません。
* 旗のところの状態は、[城までの歩き](f-4-CastleWalk-ja.md) と同じく、本物の走りの最後を書き換えたものです。ほかの走りの敵、スコアなどのバイトは含みません。
* Start と Select は定理の入力に含めていません。ポーズは測っただけで、証明していません。Select を押し続けても何も変わらないことを測りました。
