# 一部のバイトがわからない走り

**主張.** 地下への切り替えの最後の 41 フレームは、走りごとに違うバイトのすべての値で同じ長さです。条件は 3 つです。マリオの大きさが 0 か 1 です。ゲームタイマーが 000 ではありません。220 バイトのリストがフレーム 50 で基準の値です。これで[地下への切り替えの長さを決めるもの](b-2-1-PipeTransitionAll-ja.md)の前提 (H4) がなくなります。切る場所はフレーム 48 からフレーム 50 に動きます。ですから、フレーム 49 と 50 は前提 (H1)、(H2)、(H3) の側に入ります。

**フレーム 48 では「すべての値」は成り立ちません.** `T = run(E, 0^48)` で、エミュレータは 2 つの場合を示します。

* 音楽の状態の 9 バイトを同時に変えると、400 フレームのあいだ操作できません。音楽のポインタが 0 の並ぶ場所を指し、矩形波 1 の読み出しが終わりません。1 バイトずつでは何も変わりません。
* ゲームタイマーが 000 だと操作できません。

ですから、フレーム 48 の `Rvar` のすべての値で成り立つ定理はありません。フレーム 50 では、フレーム 49 の RAM の消去で音楽のポインタと位置が 0 になっていて、この繰り返しは動きません。

`m₀`、`run`、`ctl`、`0^k`、`E`、`core`、`entries` は[地下への切り替えの長さを決めるもの](b-2-1-PipeTransitionAll-ja.md)と同じです。`T = run(E, 0^50)` です。`T` の*位置* `v` は、ドット `d ≤ 9`、2 つの偶奇、PPU 制御のミラーの 1 ビットを決めた `T` です。`K` は動かして求めた 220 バイトのリストです。`sz` は `PlayerSize`、`g` は `GameTimerDisplay` です。

```
Cond(t)     :  ∃ 位置 v :  dot(t) = dot(v) ≤ 9  ∧  core(t) = core(v)  ∧  (∀ i ∈ K, t[i] = v[i])
               ∧  t[sz] ∈ {0, 1}  ∧  (t[g], t[g+1], t[g+2]) ≠ (0, 0, 0)

decided     :  ∀ t,  Cond(t)  →  ∀ k, 1 ≤ k ≤ 41 → ( ctl(run(t, 0^k)) ↔ k = 41 )
entryStates :  ∀ m ∈ entries :  (∀ k, 1 ≤ k ≤ 50 → ¬ctl(run(m, 0^k)))  ∧  Cond(run(m, 0^50))
every_entry :  ∀ M,  (∀ k, 1 ≤ k ≤ 50 → ¬ctl(run(M, 0^k)))  ∧  Cond(run(M, 0^50))
               →  ∀ k, 1 ≤ k ≤ 91 → ( ctl(run(M, 0^k)) ↔ k = 91 )
```

`decided` では、`K ∪ {sz, g, g+1, g+2}` の外のバイトは何でもかまいません。フレームタイマー、乱数、数字、`PlayerStatus`、音楽の状態の残り、そのほかすべてです。タイマーの 3 桁には、3 桁を合わせた条件だけがあります。

Lean: `Theorems/TaintRun.lean`（`ctl_of_check`、`decided_of_run`、`Statement`、`statement_of_check`、`every_entry`。[地上への切り替えのはじめのフレーム](d-2-2-SideChangeBound-ja.md)が使う `frame_of_live`、`frame_of_walk`、`inv_step` もここにあります）、非公開の `taint_checks`（`native_decide`）、`taint_run`、`taint_entries`。`ctl_of_check` と `every_entry` が使う公理は `propext`、`Classical.choice`、`Quot.sound` だけです。

## しくみ

**抽象機械.** 機械の集合をまとめて追います。各バイトには、わかっているビットとわからないビットがあります。フレームの中のドットは区間です。わからないフラグの分岐では両方に進みます。同じ場所に来た 2 つの道は 1 つにまとめます。違うビットはわからないビットになります。

**健全性.** `Sim A m` は、抽象状態 `A` が機械 `m` を含むことです。256 個の命令、NMI、PPU の時間、バス、DMA、コントローラのそれぞれに補題があります。`m` の 1 ステップを抽象機械の 1 ステップが追います。抽象状態の*表*はステップで閉じています（`walkF`）。道はフレームの終わりで止まり、そこの状態を調べます。ここで調べるのは、操作できるかどうかがわかることと、状態が表にあることです（`finCtl`）。`ctl_of_check` はこう言います。表が閉じているなら、開始状態のどの機械も同じフレームで操作できます。この証明に ROM は出てきません。

**時間.** 道によってサイクル数が違います。スプライト 0 のフラグはドットの関数です。ですから、PPU の状態を読むときは、状態をその時刻で 2 つに分けます。分けたそれぞれでフラグがわかります。ですから、フラグを待つ繰り返しのあとで区間は小さくなります。サイクルの偶奇とフレームの偶奇は追いません。フレームが終わってよいのは待ちの繰り返しの中だけです。新しいドットは `0..9` で、`T` の位置と同じです。フレームの終わりの近くでほかの命令が動くと、確認は失敗します。フレーム 51 から 91 にはありません。

**分け方.** 状態は、それを覆ういくつかの部分に分けてかまいません。タイマーの数字は最後のフレームで分けます。どれかの桁のどれかのビットが 1 です。マリオの大きさは最初に分けます。大きいマリオと小さいマリオでは当たり判定が違うからです。

**ここでは使わない部品.** 同じ機械を[地上への切り替えのはじめのフレーム](d-2-2-SideChangeBound-ja.md)でも使います。そちらは次の 3 つの部品を使います。パッドのビットがわからないこと（ここではボタンなしとわかっています）。追うカウンタ（ここでは使いません）。いくつかのビットで分けて読むバイト（ここではありません）。

**確認** は 412,456 個の抽象ステップ、3,350 回の分岐を追います。表の状態は 1,352 個です。プログラムで約 3 秒（77 個の入る状態を含む）、証明のビルドで約 4 秒です。

**測ったけれど定理にしていないこと.** `Cond` を満たす乱数の状態 300 個は、ちょうど 41 フレームで操作できます。TAS の入る状態は `Cond` を満たし、50 フレームのあいだ操作できません。`K` の外の 22 バイトが `T` と違います。

## 前提（Lean では証明していない）

* フレーム 50 での (H1)、(H2)、(H3): 50 フレームのあいだ操作できないことと `Cond` です。フレーム 49 と 50 と RAM の消去を含みます。77 個の入る状態では成り立ちます（`entryStates`）。すべての走りでは証明していません。
* フレーム 50 より前の音楽の状態。上のとおり、値によってはゲームが止まります。本物の走りすべてを示すには、音楽の状態についての事実が要ります。たとえば、音楽のポインタが 0 か、音楽のヘッダの表の値であることです。
* フレーム 50 の `t[sz] ∈ {0, 1}` と、タイマーが 000 でないこと。状態から読むだけです。本物の走りがこの値であることは証明していません。
* 待ちの繰り返しの外で終わるフレームは、この道具では扱いません。
* 入力なしだけです。
