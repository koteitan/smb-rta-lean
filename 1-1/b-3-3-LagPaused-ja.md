# 部屋への切り替えの `lag` のフレーム

**主張.** 部屋への切り替えで、ポーズの状態で終わるフレームは `left` を減らしません。これで[ルート全体](0-1-Route-ja.md)の仮定 `keep₁` がなくなります。代わりに `Changes` にはフィールド `paused₁` が入ります。切り替えの `lag` のフレームは、どれもポーズの状態で終わる、というものです。これは 1 つの状態、フレームの終わりの機械の、1 ビットについての条件です。

記号は [`fall` なしの部屋への切り替え](b-3-2-PipeChangeEnd-ja.md)と同じです。`Paused(m)` は、`m` で `GamePauseStatus` の最下位ビットが立っていることです。

```
Paused(m)  :  m[GamePauseStatus] & 1 = 1
```

**定理.** `EndStatement` に新しい部分が 2 つあります。どちらも確認 `pipe_end_checks` から出ます。

```
paused :  ∀ m, During(m) → ∀ i, (∀ j, Places(trace(m, i, j))) → Paused(frame(m, i)) → left(m) ≤ left(frame(m, i))
rowsGo :  ∀ m, InRows(m) → ¬Paused(m)
```

`PipeRun` のフィールドで、`Changes` の 1 つめの切り替えのフィールドです。

```
lagPaused (chg.paused₁) :  ∀ n, a ≤ n < b,  lag(n)  →  Paused(seq (n+1))
```

これが次のものに代わります。

```
lagKeeps (chg.keep₁)    :  ∀ n, a ≤ n < b,  lag(n)  →  left(seq n) ≤ left(seq (n+1))
```

`PipeRun.bound` と `Changes.bound₁` の結論は変わりません。`cnt(a) + 91 ≤ cnt(b)` と `e₁ + 91 ≤ c₂` です。証明では、`During` の状態からの `lag` のフレームは `paused` で `left` を保ちます。表の行の状態からの `lag` のフレームはポーズの状態で終わるので、`rowsGo` から行の中では終わりません。すると `rows` から、`left` はもう 0 です。

Lean: `Theorems/PipeChangeEnd.lean`（`notPausedK`、`not_paused_of`、`finRkP`、`finXP`、`z_step`、`not_paused_rows`、`Paused`、`EndStatement.paused`、`EndStatement.rowsGo`、`PipeRun.lagPaused`、`PipeRun.bound`）、`Theorems/Route.lean`（`Changes.paused₁`、`Changes.run₁`）。ROM を使わない定理が使うのは `propext`、`Classical.choice`、`Quot.sound` だけです。

## しくみ

**ゲーム.** NMI はポーズのルーチンのあとで `GamePauseStatus` を読みます。最下位ビットが立っていると、NMI はタイマーとゲームのルーチンをとばします。だから土管のタイマーは進みません。`GamePauseStatus` に書くのはポーズのルーチンだけです。出口のあとの RAM の消去はここまで届きません。

**確認.** 抽象機械は、もともと `GamePauseStatus` を最下位ビットの値ごとに 2 つに分けて読みます（`Env.splits`）。ところが表を作る探索は、次の命令でその 2 つをまとめていました。2 つが違うのはアキュムレータとキャリーだけで、これらは探索のキーに入っていないからです。それで表の状態はこのビットを知りませんでした。いまは `GamePauseStatus` の最下位ビットがキーに入ります（`zskey`、`kb`）。分けた 2 つは別のままです。

| フレーム | 探索のステップ | 表の状態 | 前 |
|---|---|---|---|
| タイマー ≥ 2 | 902,238 | 36,062 | 35,607 |
| タイマー = 1 | 527,799 | 23,135 | 23,111 |

確認は、土管の各フレームの終わりでさらに 2 つを調べます。

* タイマー ≥ 2: そのフレームでカウンタが減ったなら、状態は最下位ビットが 0 だと知っています（`finRkP`）。だから、ポーズの状態で終わるフレームはタイマーをそのままにします。
* タイマー = 1: そのフレームが出口なら、状態は最下位ビットが 0 だと知っています（`finXP`）。だから、出口のフレームはポーズの状態では終わりません。

出口のあとの行についても 1 つ調べます。どの行のどの状態も、最下位ビットが 0 だと知っています。出口ではこれは 0 です（`ExitCond`）。ゲームコアのフレームで Start を押さなければ、ポーズのルーチンはこれを 0 のままにします。

確認全体はプログラムで約 23 秒です（前は 21 秒）。

**はみ出すフレーム.** `Frames` では、はみ出したフレームの次のフレームも `lag` のフレームにできます。そのフレームはポーズの状態では終わりません。だから、そういう `lag` のフレームが切り替えの中にある走りは、いまは定理の外です。本物の走りでは、部屋への切り替えの中でこれは起きません。

* 土管のフレームは待ちの繰り返しの中で終わります。確認が `Places` のもとでこれを証明します。
* 出口のあとで 1 つのフレームがはみ出します。RAM を消すフレームです。その次のフレームは `setup` のフレームです。これは数えるフレームで、そこで `left` が減ります。

## 測ったこと

ここで `lag` のフレームとは、切り替えの中で、インターバルタイマーの位相が変わらず、`left` が減らないフレームです。

* `pipe-end-check`: 入る状態は 15 個です（`E`、TAS の入る状態、本物の入る状態 13 個）。入力なしでは `lag` のフレームは 0 です。Start なしの乱数の入力でも 0 です。土管のフレームだけで Start を押す乱数の入力では 995 です。995 のすべてがポーズの状態で終わります。
* 14 個の入る状態と同じ 3 種類の入力では、どの走りでも 1 つのフレームが待ちの繰り返しの外で終わります。RAM を消すフレームで、入ってから 48 フレームめか、ポーズのあとならもっとあとです。その次のフレームはいつも `setup` のフレームです。823 の `lag` のフレームのすべてがポーズの状態で終わります。
* TAS での `changes-check`: 切り替えの中に `lag` のフレームはありません（exit 0）。フレーム 450 から 50 フレームのポーズでは、`lag` のフレームは 50 で、すべてポーズの状態です（exit 0）。フレーム 380 か 416 から 60 フレームのポーズでは、`lag` のフレームは 60 で、すべてポーズの状態です。この 2 つの走りは、この変更の前と同じく `quiet₁` を満たしません（出口にポーズの音があります。exit 1）。

## 仮定（Lean では証明していないこと）

* `paused₁`: 切り替えの `lag` のフレームは、どれもポーズの状態で終わる。Lean では、`Frames` の種類 `lag` と機械をつなぐものはありません。このフィールドが、部屋への切り替えについてそれをつなぎます。
