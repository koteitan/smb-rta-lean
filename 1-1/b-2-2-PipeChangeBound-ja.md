# 部屋への切り替えの下限を 1 フレームずつの事実から出す

**主張.** これは部分的な結果です。数 `left` が、走りの各フレームで高々 1 しか減らないとします。すると、その走りは入ったあと 90 フレームのあいだ、どの入力でも操作できません。`left` は少しのバイトから計算します。高々 1 しか減らないことは、すべての状態については証明していません。切り替え全体についての仮定の代わりに、1 フレームごとの仮定になります。

`m₀`、`run`、`ctl`、`0^k`、`E` は[地下への切り替えの長さを決めるもの](b-2-1-PipeTransitionAll-ja.md)と同じです。`w[..j]` は `w` のはじめの `j` 個の入力です。

**数 `left`.** ゲームコアで土管のルーチンが動いているあいだは `left(m) = timer(m) + 43` です。そのほかでは 43 行の表から読みます。表は `E` を入力なしでフレーム 48 から 90 まで動かして作ります。各行はキーと残りのフレーム数で、フレーム `48 + i` は `43 - i` です。キーは `OperMode_Task`、`ScreenRoutineTask`、`GameEngineSubroutine`、`DisableScreenFlag` です。ゲームコアではこれに `Player_State` と、縦の位置、端数、速さが加わります。表にないキーは `left = 0` です。

```
EntryCond(M)  :  routine(M) = 土管のルーチン  ∧  task(M) = ゲームコア  ∧  48 ≤ timer(M)

fall(M, w)    :  ∀ j < |w| :  left(run(M, w[..j])) ≤ left(run(M, w[..j+1])) + 1

no_control_entry :  ∀ M, EntryCond(M) → ∀ w, fall(M, w) → ∀ j ≤ |w|, j < 91 → ¬ctl(run(M, w[..j]))
left_zero_of_ctl :  ctl(m) → left(m) = 0                                  （表に操作できる状態がないことは確認ずみ）
entries_ok       :  ∀ m ∈ {E, 本物の入る状態 13 個} :  left(m) = 91  ∧  ∀ j < 91, ¬ctl(run(m, 0^j))     （各フレームで fall を確認）
Change.bound     :  E ≤ C  ∧  (∀ j, E ≤ j < C → left(f j) ≤ left(f (j+1)) + 1)  ∧  91 ≤ left(f E)  ∧  left(f C) = 0  →  E + 91 ≤ C
```

`EntryCond` のほかのバイトは何でもかまいません。それらについて言うのは `fall` だけです。

Lean: `Theorems/PipeChangeBound.lean`（`low_of_fall`、`no_ctl_of_fall`、`change_ge`、`no_control`、`no_control_entry`、`left_zero_of_ctl`、`entries_ok`、`Change`、`Change.bound`）、非公開の `pipe_bound_checks`（`native_decide`）、`pipe_bound_keys`、`pipe_bound_entries`、`pipe_no_control`。ROM のない定理が使う公理は `propext` と `Quot.sound` だけです。

## しくみ

長くかかるフレームは `left` を変えません。ですから操作を遅らせるだけです。ポーズと、終わらないハンドラも同じです。操作できるのは `left = 0` のときだけで、`left` は 91 から始まります。ですから 91 フレームが必要です。これは式で、探索ではありません。非公開の確認は約 3 秒です。

## 測ったけれど定理にしていないこと

プログラムで本物のフレームを動かしました。基準の入る状態、TAS の入る状態、本物の入る状態 13 個、乱数の走り 60 回の入る状態の合計 75 個です。それぞれ入力なし、Start なしの乱数入力、乱数入力、Start を押し続ける入力で動かしました。合計 140,160 フレームです。

* `left` が 2 以上減るフレームはありません。操作できるのは `left = 0` のときだけです。どの入る状態でも `left` は 91 です。
* いちばん短い切り替えは 91 フレームです。Start を含む乱数入力では 181 から 199 フレームです。Start を押し続けると 1,500 フレームのあいだ操作できません。
* 前のページの 77 個の入る状態（書き換えた状態を含む）に、悪いフレームはありません。
* 6 個の物が近くにある状態: 92 から 96 フレームで、悪いフレームはありません。
* ゲームを止める音楽の状態をフレーム 48 から動かすと、400 フレームのあいだ操作できず、悪いフレームはありません。

`fall` が成り立たない書き換えた状態: `HalfwayPage ≠ 0`（75 フレームで操作できる）、`WarpZoneControl ≠ 0` と `GameTimerExpiredFlag ≠ 0`（228 と 229 フレーム。途中で `left` が落ちる）、ゲームタイマー 000（フレーム 331 で `left` が落ちる。操作はできない）。ですから `fall` は `EntryCond` を満たすすべての状態では成り立ちません。本物の走りについての命題でなければなりません。

## 抽象的な走りを試したが、閉じなかった

パッドがわからない、区間への読み書き、どこでも終わるフレーム、タイマーが自由、物の枠ごとの値の集合を持つ抽象機械を、土管のルーチンの 1 フレームで動かしました。閉じませんでした。敵のバイトが自由だと、抽象状態が 300,000 個を超え、失敗が数百個あります。フレーム 48 から音楽の状態を自由にすると、8,000,000 ステップで 2,000,000 個を超え、フレームごとに増えます。原因は、土管のあいだも画面がスクロールを続けて動く面の解析、ステータス行と VRAM バッファの位置、音楽のエンジンです。この定理にはこの部分は入っていません。

## 前提（Lean では証明していない）

* 走りの各フレームの `fall`。これが主な前提です。前のページの (H1)、(H2)、(H3)、(H4) を 1 フレームごとの命題に置き換えます。
* `Change` のフレームは `pipe.E` と `room.C` と同じように数えます。
* 乱数の走りはパワーアップを取っていません。大きいマリオは書き換えた状態でだけ動かしました。
