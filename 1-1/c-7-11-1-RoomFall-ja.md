# 部屋でのジャンプの各フレームは着地まで `vstep` のとおり

**主張.** 隠し部屋で入るフレームより前の、空中で始まるフレームは、着地まで `vstep` のとおりです。`t` を、フレームの始まりの縦のバイトの `vstep` とします。プレイヤーのルーチンの機械の上で、そのフレームの A と、覚えている速さ 0 で計算します。すると `t` は空中（状態 1 か 2）です。フレームの終わりの縦のバイトは `t` か、または `t` は落下中で、終わりの縦のバイトは `t` の着地です。床からのジャンプでは、この `vstep` は [部屋をつなぐ](c-5-RoomJoin-ja.md) の `vstep` と同じです。ですから床からのジャンプの各フレームは、着地まで `vstep` のとおりです。

[ジャンプの最初のフレーム](c-7-5-1-RoomVert-ja.md) は、床からのジャンプの最初の 8 フレーム（上昇中）でこれを証明しました。このページは落下中のフレームと、ジャンプのすべての状態を加えます。これは床からのジャンプの各フレームでの項目 1-1-c-7-11（`vert_air`）です。空中では上下の動きは横の動きに左右されません。覚えている速さを読むのは跳ぶときだけです。

フィールド `stand_row`（項目 1-1-c-7-5）も証明します。空中から立つと、高さは段ちょうどで、縦の速さは 0 です。もう仮定ではありません。

`V` は `vsOf` が読むバイトです。高さ `y` とその端数、縦の速さ `vy` とその端数 `mf`、2 つの力、ジャンプの始まりの高さ、状態 `st`、A と B です。`V'` は `V` から `y`、`vy`、`mf`、`st` を除いたものです。`Q` はスクロールの処理（`PlayerSubs`）、`tr(j)` はフレームの `j` 命令目の機械、`end` はフレームの終わりの機械、`rt` はルーチンのバイトです。「落下中」は、状態が 1 か 2 で `vy` のビット 7 が 0 のことです。

```
land(s)      =  s の  y := y & F0,  vy := 0,  mf := 0,  st := 0

after_QC  :  RoomCond(M),  各命令が SiteOK
             →  pc(tr(j)) = Q となる j はフレームに高々 1 つ,
                かつ  pc(tr(j)) = Q,  落下中(tr(j)),  rt(end) = rt_部屋  →
                  V(end) = V(tr(j))
                  ∨  ( V'(end) = V'(tr(j))  ∧  st(end) = 0  ∧  vy(end) = 0  ∧  mf(end) = 0  ∧  y(end) = y(tr(j)) & F0 )
jump_frame:  RoomCond(M),  SiteOK,  AtV(R),  st(M) ∈ {1, 2},  (st(M) = 1 → DTHJ(M) = 1),  PrevA(M) & 80 = A_B(M) & 80,  rt(end) = rt_部屋,
             アイドルループ以外の各命令はフレームの終わりより 64 ドット以上前
             →  t.st ∈ {1, 2}  ∧  ( vs(end) = t  ∨  (落下中(t)  ∧  vs(end) = land(t)) )        t = vstepV(vs(M), A(R), 0)
bridgeAll :  床からのどのジャンプのどの状態 u でも:  u.st ∈ {1, 2};  u が地面にない  →  ∀ a,  vstepV(u, a, 0) = vstep(u, a, 0);
             ジャンプはフレーム 80 までに地面に着く
vair_of   :  C ≤ n < t0,  n + 1 < E,  st(n) ≠ 0
             →  t.st ∈ {1, 2}  ∧  ( vs(n + 1) = t  ∨  (落下中(t)  ∧  vs(n + 1) = land(t)) )            t = vstepR(vs(n), a(n + 1))
varc_all  :  C ≤ n < t0,  n + 1 < E,  OnArc(T, n),  ¬(落下中(vs(n)) ∧ y(vs(n)) ≥ y_地面)
             →  vs(n + 1) = vstep(vs(n), a(n + 1), 0)  ∨  (落下中(vstep(…))  ∧  vs(n + 1) = land(vstep(vs(n), a(n + 1), 0)))
arc_step_all: OnArc(T, n),  ¬(落下中(vs(n)) ∧ y(vs(n)) ≥ y_地面),  vs(n + 1) = vstep(vs(n), a(n + 1), 0)  →  OnArc(T, n + 1)
stand_row_of: C ≤ n,  n + 1 < t0,  st(n) ≠ 0,  st(n + 1) = 0  →  y(n + 1) mod 16 = 0  ∧  W(n + 1) = 0
```

`vstepV` と `vstepR` は機械 `vmach`（ジャンプを止める値 1、プレイヤーのルーチンのスタックポインタ）の上の `vstep` です。`W = 256·vy + mf` です。

Lean: `Theorems/RoomFall.lean`（`phC`、`finC`、`piecesC`、`yPieces`、`after_QC`、`at_Q`、`jump_frame`、`FChecks`、`jump_room`）、`Theorems/VertAir.lean`（`goalVA`、`vert_air`、`land`、`bridgeAll`、`bridgeAll_of`）、`Theorems/RoomVert.lean`（`keyV`）、`Theorems/RoomJoin.lean`（`vstepR`、`InRoom.air`、`RoomRun.vair_of`、`RoomRun.stand_row_of`、`RoomRun.varc_all`、`arc_step_all`、`RoomCore.stand_row`）、`Theorems/RoomPair.lean`（`RoomWalks.fall`）、`Theorems/Route.lean`（`Run.roomAir`、`Run.inRoom`）。非公開の `Proof/RoomFall.lean`。

## 方法

**空中の移動のルーチン.** `vert_air` は、ルーチンが状態を 1 か 2 のままにすることも言うようになりました。ルーチンの歩きは戻るところでの状態を知っています。2 つの機械で同じです。確認はそれが 1 か 2 であることを求めます（`goalVA`）。

**1 フレーム全体の 3 つ目の歩き（`walkC`）.** [ブロックの地図](c-7-12-RoomMap-ja.md) の歩きを、[RoomVert](c-7-5-1-RoomVert-ja.md) のフレームで使います（`walkV`、`frame_of_walkV`）。`Q` で空中を落下中の状態を状態（1 か 2）で分け、ビットを立てます。`Q` でのほかの状態には `[2]` の印をつけます。ビットは、`Q` から後のどのステップも `V'` を書いていないことを表します。リストは着地の 4 バイト（`y`、`vy`、`mf`、`st`）に何があったかを表します。

| リスト | 意味 |
|---|---|
| `[3]` | 書いていない |
| `[5, h]` | 書いていない。`y` の上の 4 ビットは `h` |
| `[1, h, 0]` | そのあと書いた |
| `[6]` | 着地した。`st`、`vy`、`mf` は 0、`y` は `h` と分かっている。そのあと `y` を忘れた。そのあと `V` のどのバイトも書いていない |
| `[4, 4, 4]` | リストが許さないステップが `V` を書いたかもしれない（ビットを落とす） |

`[3]` の状態は、`y` との `AND` のところで `y` の上のビットで分けます。着地はこうして `y & F0` を作ります。歩きはその結果を知ります。`[1, h, 0]` か `[4, 4, 4]` の印の状態は、部屋のルーチンの外でフレームを終えなければいけません（`finC`）。これは時間切れで、`walkB` と同じです。ですから部屋のルーチンで終わるフレームは、`Q` から `V` を保つか、`[6]` に来ます。

最初の試みは、`Q` ですでに `y` を 16 個に分けました。探索は 638,074 状態で、73 秒かかりました。`AND` でだけ分けると、増えるかけらは着地の少しの命令の上だけです。

**探索のキー.** 探索はキーが同じ状態をまとめます。`h` の違うかけらは分けておく必要があります。`keyV` は、2 つ以上の項目のリストの 2 つ目をキーに入れるようになりました。ほかの歩きのリストは高々 1 項目なので、キーは前と同じです。（最初の試みは `y` をキーのバイトに入れました。探索の順が変わり、`Q` より前の表の 2 つの状態で燃料が切れました。）

**フレーム.** `at_Q`: プレイヤーのルーチンに最初に来たところ（`before_R`）、そこでの `vert_air`、`FrameModel.trace_inFrame` から、縦のバイトが `t` で `t.st ∈ {1, 2}` のまま `Q` に来ます。そのあと `t` は上昇中（`walkB`、`RoomVert.after_Q`: `V` は保たれる）か、落下中（`walkC`、`after_QC`: `V` は保たれるか、着地する）です。`jump_frame` は 2 つを合わせます。

**床からのジャンプのすべての状態.** `bridgeAll` は床からのどのジャンプのどの状態も確かめます（`Jump.arcCheck`）。状態は 1 か 2 です。地面より前では、A の 2 つの値で `vmach` の上の `vstep` はレベルの始まりの機械の上の `vstep` と同じです。ジャンプはフレーム 80 までに地面に着くので、見落とす状態はありません。`bridgeAll_of` は、跳んでから届くそれぞれの状態でこれを出します。

**`RoomJoin` で.** `InRoom.air` は、入るより前の部屋のフレームでの `jump_frame` です（`Route.Run.roomAir`。フレームの始まりのプレイヤーの状態は `RoomPair.quad_run` から 0、1、2 のどれか）。`RoomRun.vair_of` はそれを `read_vs`、`clean`（来たところでの `AtV`）、`InRoom.pair` で読みます。フレームの A は、どちらの場合もフレームの終わりの縦の状態の A です。着地は A を書かないからです。`RoomRun.varc_all` は、床からのジャンプで `bridgeAll` を使った `vair_of` です。

**`stand_row`.** `t0` より前で空中から立つフレームは、`vair_of` から `t` の着地です（もう一方の場合は状態 1 か 2 のまま）。ですから `y` は `t.y & F0` で段ちょうど、`vy = mf = 0` です。フィールドは `C + 51` より前で求めていました。使うのは落下中の `t0` より前のフレームだけです。そこで `RoomCore.stand_row` は `t0` より前で求め、`toCore` がそれを証明します（`stand_row_of`）。

| ROM の確認 | 状態 | プログラムでの時間 |
|---|---|---|
| `checkC`（`walkC`） | 探索 105,068（表 27,492） | 9.9 秒（探索 5.2 秒）。ビルドで 13 秒 |
| 床からの `bridgeAll` | 4,765（いちばん長いジャンプは 57 フレーム） | 0.4 秒 |
| `goalVA` での `vertAirOK` | 16 の場合 | 0.1 秒 |

`checkC` は数秒より長くかかります。それだけの非公開のファイル `Proof/RoomFall.lean` に置きました。

## 本物のフレームで確かめた

プログラム `room-fall-check FM2 [N]`: 確認のあと、最初の操作からの部屋の各フレームを命令ごとに走らせます。ムービーと、自分の入力の 5 種類それぞれ `N` 回（160 フレームまで。種類 4 は A をでたらめな長さで押す）です。

| 走り | フレーム | 空中で始まる | `Q` で `vstepV` でない | `Q` で落下中 | そのうち `V` を保つ | 着地（どれも `land` の形） | `Q` で上昇中、`V` が変わる | `stand_row` が成り立たない |
|---|---|---|---|---|---|---|---|---|
| ムービー | 111 | 105 | 0 | 72 | 68 | 3 | 0 | 0 |
| 自分の入力、5 種類 × 100 回 | 80,000 | 68,767 | 0 | 46,259 | 43,641 | 2,618 | 0 | 0 |

2,621 回の着地のうち 2,595 回は床の上でした。空中のどのフレームでも、`vstepV` はレベルの始まりの機械の上の `vstep` と同じで、`Q` での状態は 1 か 2 でした。プログラムは、かたまりの横の 2 つの高さと、かたまりの上からの `bridgeAll` も確かめます（5,537、6,305、7,069 状態、それぞれ 0.5〜0.6 秒）。どれも真です。Lean が使うのは床からのものだけです。

## 仮定（Lean で証明していないもの）

* 部屋のフレームの各命令の `SiteOK`。[ブロックの地図](c-7-12-RoomMap-ja.md) と同じです。
* 新しい仮定はありません。`stand_row` はなくなりました。

## 項目 1-1-c-7-11 にまだ要るもの

`varc_all` は床からのジャンプの各フレームを着地まで出します。[部屋をつなぐ](c-5-RoomJoin-ja.md) の証明は、まだジャンプを全体として、フィールド `way` の中で述べています（`Approach.reach`、`Over.reach`、`Off.jump.reach`）。

* 跳ぶフレーム: ジャンプの入力のある床のフレームが `arcStart` の状態を出すこと（`vfloor`、仮定）。かたまりの横とかたまりの上からも同じこと（高さからの `Over`、`Off.jump`）。それらの高さからの `bridgeAll` はプログラムでは真ですが、`OnArc` と Lean は床からだけを使います。
* どのフレームで着地するか: `varc_all` は着地が `vstep` の状態の `land` であることを言いますが、どのフレームで着地するかは言いません。`Approach` の窓（かたまりの上に着地する）と `Off` のフレーム `F`（床に着く）には、ブロックの地図の上での当たり判定の足の確かめが要ります。
* 地面かそれより下で落下中に始まるフレーム（`varc_all` はそこにいないことを求めます）。
* 空中のフレームの入力（`air_in`、`Approach.air`）。
* 最初の操作からの落下（状態 2、ジャンプなし）は `vstepR` で `vair_of` に入りますが、`RoomJoin` はそこで `vfall` の不等式を使います。これは仮定のままです。どんな状態 2 でも成り立つ `vstep` の和が要り、有限の確かめではありません。

