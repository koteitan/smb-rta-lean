# 旗のタイル: `keepB` と `bufAll` がまだ言っている書き込み

`PoleJoin.Run` の二つのフィールドは、触るまでのどのフレームでも、添え字かポインタを通したどの書き込みにも条件を置きます。

* `keepB`: そのような書き込みは、ブロックの物のオフセットもプレイヤーの番号も書かない（`PoleTileKeep.KeepB`、[当たり判定のルーチンの中で高さを守る](f-6-17-6-PoleTileKeep-ja.md)）。
* `bufAll`: そのような書き込みは、旗のタイルをブロックバッファの旗の列にだけ置く（`PoleTileWalk.BufAt`、[触るときの旗のタイル](f-6-17-2-PoleTileWalk-ja.md)）。

この書き込みの多くは、添え字が何であっても、条件が禁じることをできません。いま、それらについてはこれを証明しました。二つのフィールドは残りの書き込みにだけ求めます。一つの命令については、新しい条件は古い条件と同じことを言います（`keepB_of_R`、`bufAt_of_V`。逆向きはそのまま）。新しいのは、フィールドがまだどの書き込みについて言っているかを、フィールド自身が述べることです。測った本物のフレームでは、`keepB` は 66 か所、`bufAll` は 7 か所です。

## プログラムで決まる書き込み

命令のオペコードを `op`、オペランド（もとの番地）を `b`、RAM の番号の並びを `P` と書きます。`farStore P m` は、`m.pc` の命令とそのオペランドのバイトが ROM にあり、次のどちらかのときに成り立ちます。

* `op` が絶対番地と `X` か `Y` を通した書き込みで、0 から 255 のどの添え字でも `b` は `P` のバイトに届かない（`PositionKeep.absFarAt`、パート e から）: `∀ x < 256, (b + x) mod 2¹⁶ < 0x2000 ⇒ (b + x) mod 2048 ∉ P`。
* `op` がゼロページと `X` を通した書き込み（`STA`、`STY`、`INC`、`DEC`）で、`P` のどのバイトも 256 以上: 書く先は `(b + X) mod 256` で、ゼロページにある。

`far_target` が示すこと: `farStore P m ⇒ ∀ t, wTarget(op, m) = t ∧ t < 0x2000 ⇒ t mod 2048 ∉ P`。読むのは ROM のバイトだけで、添え字は知りません。

ブロックバッファについては、`farBuf Q m` は二つのバッファの全部のバイトの `farStore` で、しかもバッファはスタックより後ろにあります（`far_locs`: そのような 1 歩は、NMI の積みも含めて、バッファのバイトを変えない）。だから `farBuf Q m ⇒ NoTile Q m`（`noTile_of_far`）。

## A の書き込み

ROM から、NMI が待っていないときに実行する `STA abs,X`、`STA abs,Y`、`STA (zp),Y` は、RAM のバイトを A にだけ変えます（`sta_step`。`wr_val`、`sta_val` と、RAM と A を変えない三つの番地の求め方 `abx_state`、`aby_state`、`izy_state` から）。だから A が旗の二つのタイルのどちらでもなければ、その 1 歩はどこにも旗のタイルを置きません。

## フィールド

```
KeepR(m) :=  farStore(bI, m) = false  ⇒  KeepB(m)
BufV(m)  :=  farBuf(Q, m) = false  ⇒  (NMI なし ∧ 止まっていない ∧ pc, pc+1, pc+2 ≥ 0x8000 ∧ op ∈ {STA abs,X, STA abs,Y, STA (zp),Y}  ⇒  A ∈ {ball, shaft})  ⇒  BufAt(Q, m)
```

`bI` は `PoleTileKeep` の二つのバイト、`Q` は旗の場所、`ball` と `shaft` は旗の二つのタイルです。

* `keepB : ∀ n < ix(g), ∀ k, KeepR(trace(all n, inp n, k))`（前は `KeepB`）
* `bufAll : ∀ n < ix(g), ∀ k, BufV(trace(all n, inp n, k))`（前は `BufAt`）

`keepB_of_R : KeepR(m) ⇒ KeepB(m)`、`bufAt_of_V : BufV(m) ⇒ BufAt(m)`。これらを使うのは `Run.tilesStart`、`Run.keepB₁`、`Run.bufAt₁` です。ほかの定理は変わらず、`route_1_1` の結論は今も `1748 + j ≤ L` です。

## 測ったもの

`pole-keep check FM2 96`（最初の操作からのどのフレームのどの命令も。数は操作できる状態で始まるフレームでのもので、フィールドが言うのはそのフレームです）:

| | 決まる書き込み | まだ求める書き込み | まだ求める場所 | 条件が偽 |
|---|---|---|---|---|
| `keepB`（`farStore`） | 4,769,204（177 か所） | 1,331,301 | 66 | 0 |
| `bufAll`（`farBuf`、次に `STA` のバイト） | 5,867,858 + 231,685 | 962 | 7 | 0 |

走りは [当たり判定のルーチンの中で高さを守る](f-6-17-6-PoleTileKeep-ja.md) と同じで `N = 96` です: TAS、TAS のフレーム 1089 からほかの入力、自分の乱数の入力。操作できる状態で始まるフレームは 41,021、命令は全部で 167,758,026。`N = 16` では 66 か所と 5 か所でした。`bufAll` の「偽」は、本物の 1 歩が旗のタイルを旗の列でないブロックバッファに置いた数です。

`bufAll` がまだ求める場所は、エリアの解析がブロックバッファにメタタイルを置く書き込みと、物とその当たりの箱の表への六つの書き込みです。六つでは A がたまたま旗のタイルの値でした。その書く先はブロックバッファではありません。`keepB` がまだ求める場所は、画面のバッファ、メタタイルのバッファ、ブロックの物・敵・スプライトの物の表、コントローラーの覚えたビット、ポインタを通したブロックバッファ、数の桁への書き込みです。

そこで歩きが知らなければならないもの（同じ走りで見た添え字の最大）: 画面の一つ目のバッファで 65、二つ目のバッファで 29、スプライトのデータのオフセットで 14、メタタイルのバッファで 12、エリアの物の表で 2、ブロックの物の表とコントローラーの覚えたビットで 1、敵の表で 5、スプライトの物の表で 6、数の桁で 42。ポインタを通した四つの書き込みでは、ポインタの上のバイトはいつもブロックバッファのページでした。`bufAll` の、物と当たりの箱の表への六つの書き込みでは、添え字は多くて 0 と 69 でした。

**試したが、しなかったこと。** これらの書き込みで添え字を知っているフレームの歩き。`PoleTileKeep.keepCheckOfY` の歩きは、ほとんどの場所で `X` を知りません。一部だけ分かる `X` の `INX` や `DEX` は分からない `X` になり、添え字はよく、歩きが覚えていないバイト（大砲のオフセット、画面のバッファのオフセット）から来ます。この歩きでは「1 歩はブロックバッファのバイトを書かない」の確かめが 38 か所で、「書き込みは二つのバイトを書かない」の確かめが 111 か所でだめでした。`keepB` の本物の 66 か所のうち、歩きで決まるのは 12 か所だけです。物のオフセットを守り、操作の始まりの値（5）で見張ると、表は 46,486 から 183,335 状態に増え、オフセットは多くの場所でちょうど分かりますが、書き込みで `X` はやはり分からず、オフセット自身を守るにはさらに 361 か所が要ります。だからこれはしていません。

## 証明していないこと

* 66 か所での `keepB`: そこでの書き込みは、ブロックの物のオフセットもプレイヤーの番号も書かない。
* 7 か所での `bufAll`: エリアの解析は旗のタイルを旗の列にだけ描き、ほかの六つの書き込みはブロックバッファに届かない。33 回目のラウンド: 同じ書き込みで、`bufAll` は、フレームの始まりの解析の列が旗の列まで来てから旗のタイルをブロックのバッファに書くことも求めます（`PoleSlot.BufVS`、[エリアの解析の場所は定理になった](f-6-17-14-PoleSlot-ja.md)）。34 回目のラウンド: その部分は、解析の列が旗の列まで来ているか、書き込みが解析の列の輪の列にあることだけを求めます（`PoleRing.BufVM`、[解析は列を輪の中の自分の場所に書く](f-6-17-16-PoleRing-ja.md)）。
* `tilesCol` は変わりません。
