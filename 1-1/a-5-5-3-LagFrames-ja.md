# 土管までの数えないフレーム

**主張.** アイドルループで始まるフレームは、モードのルーチンを呼ぶか、または速さ、端数、位置を始まりのまま終わります。
ただし、その呼び出しまでの各命令が `Clean` を満たすときです。ポーズのフレームはこの呼び出しをしません。なので縦の土管まで、数えるフレームの終わりは
そのフレーム自身の機械から読みます。2 つの数えるフレームのあいだの数えないフレームは、3 つの値を変えません。これは 1 フレームごとの条件から出ます。
[土管までのフレームを機械から読む](a-5-5-PipeFrames-ja.md) の `Reads` が仮定していたことは、この条件からの定理になりました。

記号. `fm(t)`、`inp(t)` は数えるフレーム `t` の機械と入力です。`seq(n)`、`sin(n)` は、全部のフレームを数えたときのフレーム `n` の機械と入力です。
数えるフレーム `t` はフレーム `ix(t)` です。`tr(m, i, k)` は、入力 `i` での `m` のフレームの `k` 命令あとの機械、`frame(m, i)` はその終わりの機械です。
`c` はモードのルーチンの呼び出しで、`SkipMainOper` の前の命令です。`V(m) = (v(m), f(m), P(m))` は速さ、端数、位置です。
`FrameStart₀(m)` は、わかっているバイトのない `PipeWrites.FrameStart` です。`m` はアイドルループにいて、スタックポインタはそこでの値、フレームの始まりで、NMI が有効です。
`FrameStart(m)` は、操作できるときのルーチン、モード、タスクもわかっているものです。ここの `Clean` は `V` の 5 バイトも守ります。`Clean_G` は `PipeWrites.guardOf` の `Clean` で、5 バイトは守りません。

```
keeps_frame   :  lagCheck,  FrameStart₀(m),
                 (∀ k,  frame(tr k) = frame(m)  ∧  (∀ j ≤ k,  pc(tr j) ≠ c)   →   Clean(tr k))
                 →   (∃ k,  frame(tr k) = frame(m)  ∧  pc(tr k) = c)   ∨   V(frame(m, i)) = V(m)

Lags          :  seq(n + 1) = frame(seq n, sin n),   seq(ix t) = fm t,   sin(ix t) = inp t,   ix t < ix(t + 1)
                 そして操作から入るまでの各フレーム  ix 1 ≤ n < ix E  で:
                   ctl   :  seq(n + 1) は操作できる
                   clean :  ∀ k,  Clean_G(tr k)              （G = guardOf、5 バイトは守らない）
                 そして数えないフレーム  1 ≤ t < E,  ix t < n < ix(t + 1)  で:
                   store :  ∀ k,  frame(tr k) = frame(seq n)  ∧  (∀ j ≤ k,  pc(tr j) ≠ c)  ∧  tr k の書き込みの行き先が a   →   a は 5 バイトのどれでもない
                   game  :  (∃ k,  frame(tr k) = frame(seq n)  ∧  pc(tr k) = c)   →   V(seq(n + 1)) = V(seq n)

lagStart      :  walkCheck,  Lags,  FrameStart(fm 1)   →   FrameStart₀(seq n)                                    （StartRun）
lagClean      :  Lags   →   ∀ k,  frame(tr k) = frame(seq n)  ∧  (∀ j ≤ k,  pc(tr j) ≠ c)   →   Clean(tr k)
lags_keep     :  lagCheck,  walkCheck,  Lags,  FrameStart(fm 1)   →   ∀ t ∈ [1, E),   V(fm(t + 1)) = V(frame(fm t, inp t))
ReadsOwn      :  ∀ t ∈ [1, E],  fr(t) の始まりは V(fm t);   ∀ t ∈ [1, E),  fr(t) の終わりは V(frame(fm t, inp t))
reads_of_lags :  lagCheck,  walkCheck,  ReadsOwn,  Lags,  FrameStart(fm 1)   →   Reads
Pipe.reads    :  前のフィールド reads を定理として（Route）
```

`lagCheck` は ROM での確認で、非公開の `lag_check` が `native_decide` で示します。ROM のない定理が使う公理は `propext`、`Classical.choice`、`Quot.sound` だけです。

Lean: `Theorems/LagFrames.lean`、`Theorems/PipeFrames.lean` の `ReadsOwn`、`Lags`、`lags_keep`、`reads_of_lags`、`Theorems/Route.lean` の `Pipe.own`、`Pipe.lags`、`Pipe.reads`、
非公開の `Proof/PipeWrites.lean`。

## しくみ

* **歩き.** `TaintRun` の抽象機械で、[1 フレーム全部](a-5-2-PipeWrites-ja.md) と同じです。RAM のどのバイトもわからない状態で、アイドルループから始めます。
  1 つのバイトを `TaintRun` のカウンタ（`Env.rkI`）として追います。そこへの書き込みがあると、歩きは失敗します。フレームの終わりでもそのバイトを追えているので、値は始まりのままです。
  `V` の 5 バイトそれぞれに 1 つの歩きがあります。
* **打ち切り.** 歩きは呼び出し `c` で止まります。ポーズのバイトはわからないので、歩きはポーズの道とポーズでない道の両方をたどります。ポーズでない道は `c` に来ます。
  ポーズのフレームは `c` を飛ばして終わります。そのあいだに画面、音、パッド、ポーズの処理が動きますが、どれも 5 バイトを書きません。
* **行き先のわからない書き込み.** `Clean.store` は、そういう書き込みが `prot` のバイトに触れないと言います。5 バイトを `prot` に入れたので、追っているバイトには触れません。
  このため `PipeWrites.aforget` は、カウンタのバイトが `prot` にあるときはカウンタを追い続けるようにしました（`AS.forgetK`）。`PipeWrites` の歩きにはカウンタがないので、変わりません。
* **カウンタの値.** `TaintRun` がカウンタの `DEC abs` を追うのは、カウンタが 2 以上のときだけです。ここのバイトは 0 や 1 のこともあります。そこで 1 歩の定理を言い直しました
  （`s_astep1L`）。下限のかわりに、その命令がそのバイトの `DEC abs` でないことを条件にします。歩きはこの条件を各段で確かめます。
* **フレームの列.** `lags_keep` はフレーム `ix(t) + 1` から `ix(t + 1)` までをたどります。各フレームで、`keeps_frame` が `V` は変わらないと言うか、フレームが `c` を呼びます。呼ぶときは `game` を使います。
* **数.** 5 バイトのどれも、2,540 段、分かれ 318、失敗 0、表は 241 状態です。確認はネイティブで約 10 ms です。

## 本物のフレームで確かめたこと

プログラムです（`lag-check`）。インターバルタイマーが動かないフレームを数えないフレームとします。そのフレームごとに、`FrameStart₀`、呼び出しまでの各命令の `Clean`、
`c` を呼ぶか、`V` が変わるかを調べます。走りは、入ったところか、操作できない状態で終わる最初の数えるフレームで止めます。

| 走り | 数えるフレーム | 数えないフレーム | ポーズで終わる | `c` を呼ぶ | `FrameStart₀` でない | `Clean` でない | `V` が変わる |
|---|---|---|---|---|---|---|---|
| TAS の操作から入るまで | 368 | 0 | 0 | 0 | 0 | 0 | 0 |
| Start のある乱数の入力、小さい・大きい（240 回） | 73,757 | 76,542 | 76,542 | 0 | 0 | 0 | 0 |
| スーパーの状態の大きいマリオ、乱数の入力（240 回） | 74,974 | 76,589 | 76,589 | 0 | 0 | 0 | 0 |
| 入る前にポーズ、そのあと TAS の入力（200 回、入るのは 40 回） | 1,480 | 14,140 | 14,140 | 0 | 0 | 0 | 0 |
| 操作できない数えるフレームのあとも続けた走り（240 回、確認には入れない） | 79,764 | 88,236 | 83,778 | 4,449 | 9 | 9 | 23 |

* 操作できない最初の数えるフレームで止めた走りでは、数えないフレームはどれもポーズで終わり、`c` を呼ぶものはありません。なので、そこでは `game` を使いません。
* **けがのあとでは `game` は成り立ちません.** 最後の行は、けがや死のあとも走りを続けたものです。けがのあとの点滅（ルーチン 10）のあいだ、ゲームはプレイヤーのルーチンを動かし、
  タイマーの制御がタイマーを止めます。なので数えないフレームで動きます。`c` を呼ぶ 4,449 フレームのうち 14 です。たとえば `(v, f, P) = (3, 108, 78720) → (2, 156, 78752)` です。
  前の `reads` もそこでは成り立っていませんでした。ほかの 9 フレームはアイドルループで始まりません。死んだあとのメモリの消去がフレームの終わりを越えるからです。どの走りも、入る前に
  操作できない数えるフレームを持ちます（けがか死）。定理の外です（項目 1-1-0-6-2、1-1-0-6-3）。

## 前提（Lean では証明していない）

* **前の `start`、`clean` は定理になりました**（`Lags.lagStart`、`Lags.lagClean`）: [操作から土管までの各フレームはアイドルループで始まる](a-5-5-3-2-StartRun-ja.md)。
  かわりに、操作から入るまでの各フレームの `ctl` と `clean`、数えないフレームの `store` があります。上の表は前のフィールドを測ったものです。新しいフィールドは `start-check` で測ります。
* **`game`**: モードのルーチンを呼ぶ数えないフレームは `V` を変えません。土管まででは、タイマーの制御のフレームです（大きくなる、けが、死）。
  けがのあとの点滅では成り立ちません（上）。コードから読んだこと: タイマーの制御が 0 でない値になるのは、ルーチンが変わるときだけです（`SetPRout`）。なので、数えるフレームが
  どれも操作できる状態で終わるなら、`c` を呼ぶ数えないフレームはないはずです。これは証明していません。いまは `ctl` が、入るまでのどのフレームも操作できる状態で終わることを求めます。
  しかし `ix` はインターバルタイマーとつながっておらず、歩きはタイマーの制御を追いません。
* **この項目でないもの.** 数えるフレームが `clock` のものであること（前と同じく、フレームの番号だけでつながります）。数えるフレームが `Frame` であること（項目 0-0-0-3-1）。
