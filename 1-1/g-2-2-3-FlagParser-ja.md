# 面の読み込みが動いている城の入り

**主張.** これは部分的な結果です。`After` はいま、条件 `Good` をフレーム `E + 1` ではなく、城に入ったあと面の読み込み（area parser）が終わった最初のフレーム `G` で求めます。`E + 1` から `G − 1` までのフレームでは、カウンタが 1 フレームの規則に従うことを、各フレームについての仮定にします（`pre`）。`E + 1` で読み込みが動いていない走りでは `G = E + 1` で、`pre` は何も言いません。これは前の `After` です。`E + 1` で読み込みが動いている走りが、いま定理に入ります。`G` からは、規則は前と同じく証明されます（[城に入ったあとの星の旗の規則](g-2-1-FlagRule-ja.md)）。`pre` は証明していません。試したことと数は下にあります。

## ゲームがすること

ゲームコアの終わり、ゲームタイマーのあとで、`UpdScrollVar` が面の読み込みを動かします。読み込みの処理の番号（`AreaParserTaskNum`）が 0 でないとき、または画面が 32 ピクセルの倍数をまたいだときです。読み込みはメタタイルの新しい 2 列を 8 つの処理で描きます。動くフレームごとに 1 つの処理です。描く処理（`RenderAreaGraphics`、`RenderAttributeTables`）は 2 つめの画面のバッファを書き、`VRAM_Buffer_AddrCtrl` を 6 にします。次のフレームで画面の処理は 1 つめでなく 2 つめのバッファを描きます。1 つめのバッファは待ち、そのフレームはその中身のあとに書きます。

城に入る直前に画面が進むと、フレーム `E + 1` の始めにまだ読み込みが動いています。このとき機械は、`Good` の状態 `B₀` にないバイトを持ちます（読み込みの処理の番号、描くバッファ、PPU の制御の 1 ビット、`ObjectOffset`）。測った走りでは、ポーズで終わらないフレームが 9 つ以下で読み込みは終わり、機械は `Good` に戻ります。

## 主張の式

```
After(seq, inp, E, T, c, L) :   数 G があって
  E < G,   Good(seq(G))
  pre:  ∀ n, E < n < G  →  FlagStep(lim, w₀, paused(seq(n + 1)), x(seq n), x(seq(n + 1)))
  task(seq(E + 1)) = 2,   y(x(seq(E + 1))) = y(r)
  t(seq(E + 1)) = T,      ph(seq(E + 1)) = c
  G ≤ L
  level(seq(L + 1))

Checked(C, d),  ∀ n, seq(n + 1) = frame(seq(n), inp(n)),  After(seq, inp, E, T, c, L)  →
  Flag(lim, w₀, E, T, c, L)                                        flagOf_after
```

`x(m)` は星の旗のカウンタ、`paused(m)` はポーズの状態のビット 0 です。`G` の前のフレームでも、ポーズで終わるフレームは `lag` のフレームです。`y(x(seq(E + 1)))` は旗のスロットから読む旗の高さです。18 回目までは最初のスロットから読みました。それは `E + 1` の `Good` が与えました。`Route.Run` のフィールド `flag` の型が変わりました。`Run` のフィールドは増えも減りもしません。

## 本物の走り

`castle-after-check` は `castle-rule-check` の走りを使います。地上で操作できるところ（`b₂`）から、Start ありとなしの乱数の入力と、ポーズです。各走りで `G`（`E + 1` から `E + 40` までで最初に `Good` のフレーム）を見つけ、`pre` と、`E + 1` の処理 2 と高さを確かめます。`rule` をつけると、`G` からレベルが変わるまでのフレームも確かめます。

```
種             城に着く走り   G = E + 1   G があと（G − E − 1）   G なし   pre に反する   処理か高さが違う
1〜1000        200            183         17（1〜9）               0        0              0
1001〜3000     384            364         20（2〜9。53、54）       0        0              0
```

`G − E − 1` が 53 と 54 の 2 つの走りでは、そのうち 46 のフレームがポーズで終わります。ポーズで終わるフレームでは読み込みは動きません。

`rule` をつけると、`G` からレベルが変わるか走りが終わるまでのどのフレームも `Good` にあり、規則に従います（ポーズで終わるフレームはカウンタを保ちます）。`Good` の外のフレームも、規則に反するフレームも、583 の走り（動画は両方の組にあります）のどれにもありません。

## `pre` を証明していない理由

`B₀` が読み込みの動いている状態を持てば、`pre` は ROM の確認から出ます。2 つのやり方をプログラムで試しました。

1. **読み込みの状態を `B₀` に入れ、どの場所でも分けて保つ**。処理の番号、列、描くバッファで分けます。状態は 16 の機械から作ります。城までの歩きの最後の読み込みの回と、城に入ったところから画面を 32 ピクセル押した回です。`B₀` は 1008 の状態です（前は 240）。各段は 204 の状態で（前は 12）、当たりの段の探索は上限の 300 万歩を超えます。
2. **画面の段のあと読み込みのバイトを忘れ、読み込みでまた取る**。フレームを `UpdScrollVar` でも切り、新しい最後の段が、16 の機械が持つ処理の番号、列、ブロックの列、メタタイルの各値から読み込みを動かします。`UpdScrollVar` までの段はこの 16 バイトを保ちます（バイトを数として持つ歩き）。この確認の Lean の証明（新しい段での `frame_step`）はコンパイルしました。この回のファイルには入れていません。ROM の上では閉じませんでした。
   * 抽象機械は、バイトの読み出しを `LDA` のときだけ分けます。読み込みはメタタイルを `LDA abs,X` で読むので、メタタイルは知っていなければなりません。
   * 花火が 4 つある状態では、抽象的なフレームが 1 つめの画面のバッファに 75 バイトを書けます（1 フレームに 500 点の爆発が 4 つ）。バッファの終わりを越え、`VRAM_Buffer2_Offset` に書きます。これらの状態に読み込みの値をあてはめてはいけません（状態が持ちうる値で選びます）。
   * 段で読み込みの処理の番号を分けないと、処理の順が失われ、1 つめのバッファが限りなく伸びます。`B₀` の閉包の 2 回目で新しい状態が 5040 できました。
   * 処理の番号を分けると、閉包は 6 回で 3336 の状態で終わります（129 s）。しかし各段は 324 の状態（前の 27 倍）で、画面の外のビットの段の探索は 300 万歩を超えます。

なので証明には、読み込みの処理の順を、1 つめのバッファの位置といっしょに、ゲームコア全体で保つ必要があります。状態は約 27 倍になります。これはしていません。

## 証明していないこと

* `E + 1` から `G − 1` までのフレームの `pre`（測った走りでは 9 フレーム以下）。各フレームについての仮定です。
* `Good(seq(G))`、`E + 1` の処理 2 と旗の高さは、1 つの状態についての仮定のままです。
