# 城に入ったときの条件を広げる

**主張.** 城に入ったときの条件 `Good` は、いくつかのバイトに基準の機械 `r` と同じ値を求めていました。ほかの高さで旗竿に触る走りや、少し遅れて城に着く走りでは、そのうちのいくつかのバイトが違います。なので `E + 1` で `Good` が偽でした。いまの `Good` は、これらのバイトにこれらの走りでの値を許します。

* 旗の点数の浮かぶ数字の高さ（`FlagpoleFNum_Y_Pos`）は何でもよく、旗の点数の番号（`FlagpoleScore`）は 8 より小さければよい（12 回目）。
* フレームの始めのマリオの `x` は `x0` か `x0 + 1`（`x0` は `r` の値）。
* 画面の左と右の `x`（`ScreenEdge_X_Pos`、`ScreenRight_X_Pos`）は 0 から 127（前は 0 から 63）。

[城に入ったあとの星の旗の規則](g-2-1-FlagRule-ja.md)の ROM の確認はそのまま通ります。なので、これらの走りでも城に入ったあとの規則が証明されます。城に入ったときの `Good` は仮定のままですが、弱くなりました。城に着く乱数の入力の走り 193 のうち、176 がいま `E + 1` で `Good` に入ります。残りの 17 では、フレーム `E + 1` の始めに面の読み込み（area parser）が動いています。19 回目に、これらはあとのフレーム `G` とその前のフレームの規則で入りました（[面の読み込みが動いている城の入り](g-2-2-3-FlagParser-ja.md)）。

## 本物の走りで見つけたこと

`castle-rule-check` は、地上で最初に操作できるフレーム（`b₂`）から、乱数の入力とポーズで動画を動かします。`touch-end-check` と同じです。種は 1 から 1000 です。乱数の走りのうち 193 が城に着きます。動画を入れて、旗竿に触る高さは 37 から 164 までの 51 通りです。

```
城に着く走り                              数     E + 1 で Good
動画と、触る前にポーズのある 6 つの走り    7      7
乱数の入力、種 1〜1000                     193    176
```

`Good` に入る 183 の走りでは、`E + 1` で処理 2 と旗の高さも成り立ちます。`E` のあとの各フレームで、レベルが変わるか走りが終わるまで、機械は `Good` にあり、数は規則に従います（`Good` の外のフレームは 0、規則に反するフレームは 0）。乱数の走りのうち 109 はレベルが変わります。残りは走りの終わりでポーズのままです。

`touch-end-check` の 100 の種（触ったあとのポーズの走りを入れて 31 の走り）では、`E + 1` で `Good` なのは、この回の前は 25、いまは 29 です。

### マリオの `x`

フレーム `E` で、マリオは城の壁に 2 ピクセル入ります。`x0` から `x0 + 2` です。壁は 1 押し戻します。なのでフレーム `E + 1` は `x0 + 1` で始まります。速さは 0 で、横の当たりのタイマーはぶつかったときの値です。フレーム `E + 1` では、移動のあとも `x0 + 1` です（速さ 0）。壁が `x0` に押し戻します。そのあとのフレームはすべて `x0` で始まります。最初の 100 の種のこのような 4 つの走りで測りました。`r` と違うのは `x` だけでした。

### 画面

いくつかの走りでは、旗竿から城まで歩く間に画面が進み、`r` より右で止まります。このような走りで、`E + 1` の画面の左の `x` は 79 と 83 でした。画面が進むのは、画面の上のマリオの位置がスクロールの処理の決まった値以上のときだけです。`x0` から、画面の左の `x` は 128 より小さいままです。

### 外に残るもの

`Good` の外の乱数の走り 17 はどれも、フレーム `E + 1` の始めに面の読み込みが動いています。`E` の直前に画面が 32 ピクセルの倍数をまたぎ、読み込みはこのあとのフレームでメタタイルの新しい 2 列を描きます。`B₀` のいちばん近い状態と違うのは、読み込みの処理の番号（`AreaParserTaskNum`、1〜7、14 の走り）、画面の処理が次に描くバッファ（`VRAM_Buffer_AddrCtrl` が 6、6 の走り）、PPU の制御の列を書くビット（`Mirror_PPU_CTRL_REG1`）、`ObjectOffset` です。17 とも、読み込みは城の先の隣り合う 5 つの列のどれかを描き、面のデータは終わりにあります（`AreaDataOffset` はすべて同じ）。機械はフレーム `E + 1 + k` から `Good` に戻ります。`k` は 1 から 9 です。

## 変えたところ

`B₀` は種から作ります。種は `r` の状態で、いくつかのバイトを一部だけ知っています（`FlagRule.partials`）。種からの 1 フレームの終わりも、`x` を種と同じにして `B₀` に入ります（`FlagRule.wideX`）。

```
FlagpoleFNum_Y_Pos               何でもよい
FlagpoleScore                    8 より小さい     （ビット 3〜7 が 0）
SprObject_X_Position             x0 か x0 + 1     （ビット 0 を知らない）
ScreenEdge_X_Pos                 0〜127           （ビット 7 が 0）
ScreenRight_X_Pos                0〜127           （ビット 7 が 0）
```

マリオの数はいま `x` を持ちます。`(v, F, f, A, C, s)` だったものが `(v, F, f, A, C, x, s)` です（`q6`）。移動の歩きは知っている `x` から始まります（`moveIn`）。当たりのあと、`x` はどちらの場合も `x0` です。立っているか、壁が `x0 + 1` から押し戻すかです（`collFacts`、`nextMario`）。城に入ったときの始まりは `x0` と `x0 + 1` を持ちます（`marioStarts`）。ほかの段は、数を保つのと同じように `x` を保ちます（`x` は `Ctx.mario` にあります）。ただし画面の外のビットの段は `x` を読み、`x` をその事実から得ます（`Ctx.ruledNoX`）。

## 測ったこと

ROM の確認（`flag-rule-check`）。2 つは同時に動かしました。28 コアで負荷は約 4 です。

```
           データ   段       画面の外のビット   マリオの数   移動    B₀
12 回目    6.1 s    33.1 s   0.8 s              6714         4844    240
いま       6.9 s    34.5 s   1.7 s              8762         6892    240
```

画面の外のビットの段は 2 倍かかります。この段は画面の 2 つのバイトを値で分けます。いまそれらは 128 の値を持ちます。非公開の証明 `flag_check` は `prove.py` の中で 61 s でビルドしました（12 回目は、機械が空いているとき 47 s、負荷があるとき 95 s）。

## 証明していないこと

* `Good(seq(E + 1))`、処理 2、旗の高さは仮定のままです（1-1-g-2-2）。
* `E + 1` で面の読み込みが動いている走りは、`E + 1` では `Good` の外です（測った乱数の走り 193 のうち 17）。`After` はいま、`E` のあと読み込みが終わった最初のフレーム `G` で `Good` を求め、`G` の前のフレームの規則を仮定にします（[面の読み込みが動いている城の入り](g-2-2-3-FlagParser-ja.md)）。そのフレームを証明するには、`B₀` が読み込みのバイト（処理の番号、列、ネームテーブルの番地、メタタイルのバッファ、属性のバッファ、2 つめの画面のバッファ）を約 45 通りの組で知り、各段がそれらを分けて保つ必要があります。ほかのスロットの段は 240 の状態で 18 s かかるので、試していません。
