# 触るときの旗のタイル: 旗の近くの読みはブロックバッファにある

`PoleJoin.Run` のフィールド `tilesRead` をなくしました。これは、ルーチンの書き込みまでの横の判定の各読みで `ReadPre` を求めていました。読みは RAM にあり、ブロックバッファにあり、旗の列の旗のタイルを読むのはページが旗のページの一つ前以上のときだけ、という条件です。はじめの二つは、旗の近くの全部の読みで証明しました。代わりに小さいフィールドが二つあります。どちらも一つの状態の条件です。

## 新しいフィールド

`y` は高さ、`page` は彼のページ、`pg` は旗のページ、`tile(v)` は「バイト `v` は旗の二つのタイルの一つ」、`idx` は横の判定の四つの読みの添字とします。`h` は当たり判定のルーチン自身の高さの確認の境です（高さとの最初の比較。ROM から読みます）。

* `ySide`（`YSide`）: 書き込みまで、横の判定の始まりで `y < h`。
* `tilesFar`（`TileFar`）: 書き込みまで、横の判定の読みの直後（`pc = read + 2`、`save ∈ idx`）で、`page + 1 < pg` なら `¬ tile(A)`。

本物のフレームでどちらも成り立つ理由は簡単です。当たり判定のルーチンは `y ≥ h` ならすぐ戻ります。その確認から横の判定までの間に高さを書くのは着地だけで、それは下の 4 ビットを 0 にします。歩きはこれを示しません（このページの終わり）。旗のページの二つ以上前にいるときは、旗の列はまだ描かれていません（下の「測ったこと」）。

## 証明したこと

定理 `no_write_frameU`（ファイル `Theorems/PoleTileRead.lean`）は、`PoleTileWalk.no_write_frameP` の `ReadPre` を `YSide` と `TileFar` に変えたものです。

```
frameCheckU ∧ FrameStart(s₀) ∧ ColMap(s₀) ∧ (∀ j ≤ n, s_j で CleanK ∧ PosAt ∧ HypR ∧ BufAt ∧ YSide ∧ TileFar)
  ⇒ rt(s_{n+1}) ≠ 旗のルーチン
```

その帰納法の中で、すべての `j ≤ n` で `ColMap(s_j)` が成り立ち、歩きの生きた状態 `A_j` があって `TR(A_j, s_j)` です。`TR` は「`A_j` が読みの直後（`pc = read + 2`）にあり、添字が `idx` のどれかだと知っているなら `TileRead(s_j)`」です。歩きが `TileRead` を使うのはここ（読みのあとの分け方、`PoleFrame.zoneT`）だけなので、`cov_zoneTW` と `cov_preTW` は `PoleFrame` の補題の `TileRead` を `TR` に変えたものです。一歩の前のかけらは RAM を変えないので（`preK_same`）、添字について `A_j` と同じことを知っています。

歩きは `PoleTileWalk` の歩きに、分け方を二つと確認を一つ加えたものです（`walkU`）。

* 横の判定の始まりで、ページが旗のページかその一つ前でありうるとき（`nearP`）: 高さを、上のビットが分かっている 7 個のかけらに分けます（`yPieces`、`splitY`）。かけらは `[0, h)` を覆います。かけらの切れ目は横の判定自身の高さの比較の切れ目なので、どのかけらでも各比較の結果は一つです。かけらが `y < h` を覆うことは確認 `yCover` で、そこで `y < h` であることは `YSide` で分かります（`cov_splitY`）。
* ブロックバッファのルーチンで高さに足し数を足すところで、旗の近くの横の判定なら: アキュムレータを 1 ビットずつ分けます（`fullA`、`cov_fullA`）。抽象的な足し算は両方が分かっているときだけ結果が分かるので、これで和と行が分かります。
* かけら `A` から状態 `B` への一歩で（`readP`）: `B` が読みの直後にあって添字が `idx` のどれかだと知っていて、`A` でページが旗のページかその一つ前でありうるなら、`A` でポインタと `Y` が分かっていて、`pointer + Y < 0x2000`、`(pointer + Y) mod 2048 ∈ B`。読みの直後の状態は表の状態で覆わないので、そこでの次の生きた状態は `B` そのものです。

すると読みの直後の `TileRead` が出ます（`tileRead_afterU`）。`m` を読みのときの機械、`m'` をその次の機械とします。

* `page + 1 < pg` なら、`TileFar(m')` によりそのバイトは旗のタイルではありません。
* そうでなければ、`A` でページは旗のページかその一つ前でありえます。だから `readP` でポインタと `Y` が分かります。読みは RAM と `B` にあります。読んだバイトは `i = (pointer + Y) mod 2048` として `m.ram[i]` です（`RoomBlocks.step_lda_izy`、`readVal_eq`）。旗のタイルなら `ColMap(m)` から `col(i)` が出ます。`pg ≤ page + 1` はこの場合そのものです。

確認 `poleCheckU`（`PoleFrame` の歩きの前の確認、`yCover`、この歩き、読みの ROM の事実、`SubsOnce` の確認、`PoleTileWalk` のフレームの歩き）はネイティブに証明しました（非公開の `pole_check_u`）。`touch_right_of_leftU` と `inRange_of_frameU` は、`PoleTileWalk` の定理を新しい条件で述べたものです。`PoleJoin.Run.inRange` は `inRange_of_frameU` を使います。

表を探すときは、横の判定の間ずっと高さのかけらを覚えます。横の和を書くところと高さを読むところでは、`PoleFrame` が和の切り落としのところでするように、ポインタに要るもの（和の上の 4 ビット、位置のかけら）だけを覚えます。ただし和が旗のページの旗の列にあるときは全部覚えます。切り落としのところではアキュムレータの下の 4 ビットを忘れます（切り落としで 0 になるので）。これは探し方の選び方だけです。歩きがすべての状態を確かめます。

## 測ったこと

`pole-read-check FM2 96`（最初の操作から、操作中かどうかによらず、各フレームの各命令）:

| 実行 | フレーム | 命令 | 横の判定の始まり（最大の高さ） | 旗の近くの横の読み（RAM か `B` の外） | 旗から遠い横の読みの直後（旗のタイル） | `B` に書かれた旗のタイル（最小のページ、最小の `P − left`） |
|---|---|---|---|---|---|---|
| TAS、最初の操作のあとのフレーム 1〜1239 | 1,239 | 5,561,241 | 871 (176) | 1,048 (0) | 2,326 (0) | 10 (11, −230 px) |
| TAS のフレーム 1089 から、別の入力 | 20 | 79,380 | 20 (176) | 77 (0) | 0 | 0 |
| TAS のフレーム 900〜1089 からの自前の乱数入力、48 回、Start なし | 6,917 | 30,419,655 | 6,861 (176) | 24,832 (0) | 2,124 (0) | 90 (11, −238 px) |
| Start ありの自前の乱数入力、48 回 | 7,680 | 23,030,036 | 3,222 (176) | 10,481 (0) | 2,136 (0) | 60 (11, −230 px) |

`YSide` と `TileFar` はどこでも成り立ちました（bad 0）。境 `h` は 207 px で、横の判定の始まりの高さは最大 176 px でした。

ページの部分（`TileFar`）について: `B` に旗のタイルが書かれたのは、いつも彼が旗のページの一つ前かそれより右にいるときで、旗の範囲の左端から最大 238 px 左でした。彼が旗のページの二つ以上前で始まった 2,770 フレームのどれでも、`B` のどこにも旗のタイルはありませんでした。遠い横の読み 6,586 回のどれでも、`B` のどこにも旗のタイルはありませんでした。だから、遠い読みが `B` にあると分かれば、もっと小さい事実「旗のページの二つ以上前では、フレームの始まりに `B` に旗のタイルはない」で足ります。歩きは遠い読みの番地を知らない（そこでは位置を分けない）ので、これは使っていません。

歩きの探索: 7,681,437 歩、表の状態 345,444、ネイティブで約 42 秒（`PoleTileWalk` の歩きは 8,490,979 歩、352,579 状態、約 46 秒）。

**歩きの中で偽だったもの:** 読みの確認の最初の形は、添字が `idx` のどれかでありうる全部の読みでポインタと `Y` を求めました。これは 454 回の訪問で失敗しました。ほかの物（敵の横の判定、つる）のためのブロックバッファのルーチンの読みで、歩きは添字もページも知りません。探索で添字を覚えると 89 回になりました。残りは敵の横の判定のループで、歩きはその数え役を忘れます。いま確認は、歩きが `TileRead` を使うところ（読みの直後で、添字を知っているかけら）だけで求めます。これで失敗は 0 です。また、旗の近くのブロックバッファのルーチンで位置と和を全部覚える最初の探索は 5.4 GB と 2700 万歩を要しました。上の探索は 2.7 GB です。

## 証明していないこと

* `ySide`: 歩きでは、歩きが知らない添字での書き込みは、ガードが守らないバイトを全部忘れます。高さは守られていません。頭の当たりのルーチンにはそういう書き込みがあります（ブロックの物の番号、画面のバッファの位置）。測ったこと: 当たり判定のルーチン自身の最初の高さの読みで高さを分け（9 個のかけら、仮定なし）、横の判定まで覚える歩きでは、旗の近くの横の判定の始まり 315 回で高さが分からず、読みの訪問 10,368 回で確認が失敗しました（表は 764,530 状態、5.1 GB）。だから `ySide` はここでは残りました。そのあとなくしました: [横の判定の高さ](f-6-17-4-PoleTileHeight-ja.md) の歩きが高さを守ります。新しい条件は一つの命令の条件 `yKeep` です。
* `tilesFar`: 旗のページの二つ以上前にいる間に旗の列が描かれない理由には、フレームをまたぐ画面のスクロールとエリアの解析が要ります。（第 24 回で `tilesFar` はなくなりました。旗から遠い読みもブロックバッファにあり、仮定として残るのは旗の列での読みだけで、`tilesCol` になりました: [旗から遠い読みはブロックバッファにある](f-6-17-5-PoleTileFar-ja.md)。）
* `bufAll` は変わりません。

**ファイル:** `Theorems/PoleTileRead.lean`。非公開の `Proof/PoleTiles.lean`（`pole_check_p` の代わりに `pole_check_u`: ネイティブで探索が約 45 秒、歩きが約 50 秒、2.8 GB。ファイル全体は 104〜123 秒で、前とほぼ同じ。23 回目からはこのファイルは `pole_check_u` の代わりに[横の判定の高さ](f-6-17-4-PoleTileHeight-ja.md)の `pole_check_h` を持ちます）。プログラム `pole-read-search`（探索と確認）と `pole-read-check FM2 [N]`（上の本物のフレーム）。
