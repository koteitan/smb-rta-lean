# 縦の土管に入るときの状態を、タイトルから出す

**主張.** これは部分的な結果です。`Entry` は、縦の土管に入るフレームの終わりの状態についての条件です（[`fall` なしの部屋への切り替え](b-3-2-PipeChangeEnd-ja.md)）。フレームが待ちの繰り返しの中で終わっていて、土管のタイマーが 48 以上で、97 バイトとマスクつきの 12 バイトが基準の入る状態の値です（12 回目の前は 115 と 13）。ここでは、待ちの繰り返し、土管のタイマー、この 109 のうち 73 を、タイトルで Start を押したことと、操作できるときから入るまでのフレームから出します。[ルート全体](0-1-Route-ja.md)のフィールド `entry₁` はなくなりました。代わりに `Changes` には次の 2 つのフィールドが入ります。

* `entryRest₁`: 残りの 36 バイトだけについての `Entry` の条件（`Rest`）。1 つの状態についての条件です。
* `upClean₁`: 操作できるときから入るまでのフレームの各命令は `Clean` を満たす。ここでは、インデックスやポインタを通す書き込みが触らないバイトに、`held` の 71 バイト、土管のタイマー、ポーズの 6 バイトが入ります。14 回目からは、1 つのフィールド `chg.upCleanU` からの定理 `Run.upClean₁` です（[土管までの各命令に 1 つの条件](a-5-10-UpClean-ja.md)）。

10 回目に、項目 1-1-b-3-4-2 は 61 バイトとタイマーから 56 バイトに減りました。フレームが保つバイトが 4 つ増え（敵の枠 4 の種類、大砲 0 の場所の 3 バイト）、入るフレームの歩きがもう 1 バイト（左右のボタン）とタイマーを出します。残るバイトのそれぞれに、測ったわけを下に書きます。

**11 回目.** 2 つ変わりました。(1) ポーズのバイト（`GamePauseStatus`、マスク `0x7E`）のビット 1〜6 は、もう `restNames` にありません。`TitleStart` の近い状態がポーズのバイトを知るようになり（押したときの条件が 5 回目から知っています）、操作できるときからのフレームの歩きがこのビットを保つからです。ポーズのルーチンはこのバイトを、ビット 0 を反転してビット 7 を立てるか、ビット 7 を消すかでしか書きません。ですから `Rest` は 55 バイト、`atEntry` は 73、`held` は 71、`kept` は 70 です。(2) 守りはポーズの 6 バイトも挙げ（`pauseSix`）、`Checks` には[入るときのポーズ](b-3-7-3-EntryPause-ja.md)のための確認が 2 つ加わりました。フレームの歩きはほとんど変わりません。1,176,671 歩、表は 53,438 状態です（前は 53,437）。

**12 回目.** `Entry` は 19 バイトをもう求めず、それらは `Rest` から出ました。土管のフレームの歩きがそれらを使わないからです（`PipeChangeEnd.entryDropped`）。ですから `Rest` は 36 バイト、`Entry` は 97 バイトとマスクつきの 12 バイトです。`atEntry`、`held`、`kept`、守り、このページの歩きは変わりません。19 バイトはどれも `Rest` にあったからです。19 バイトは、上下のボタン、敵のページ、画面のタイマー、デモのタイマー、メニューのワールドの番号のあとの 3 バイト、モードのあとのバイト、その他の物 8 の高さ、マリオの状態、敵の枠 5 の状態、2 つめの矩形波の効果音のキュー、旗の数、つるの高さ、最初の大砲のオフセット、複製、色、ループ、新しいゲームタイマーのフラグです。見つけ方: `Rest` の各バイトを 1 つずつ、[`fall` なしの部屋への切り替え](b-3-2-PipeChangeEnd-ja.md)の歩きの始まりの状態から外し、古い歩き（`zcheck`）、ポーズのクラスを横に運ぶ歩き（`pcheck`、[b-3-7-2](b-3-7-2-PipePause-ja.md)）、`leftCheck` をもう一度走らせました（`entry-need`）。1 つずつなら 20 バイトが通ります。そのうち 19 は合わせても通り、表は古い歩きで 38,253 と 23,238 状態（前は 36,062 と 23,135）、`pcheck` で 58,850 と 43,229 状態（前は 56,816 と 43,120）です。20 番目は 1 つめの矩形波の効果音のキューです。それがなくても歩きは通りますが、`pcheck` の表が 156,721 と 143,033 状態に増えます（19 とも外すと 158,808 と 143,194。プログラムで 27 秒の代わりに約 63 秒）。だからそれは残します。新しい `Entry` で歩きが通ることの確認は、非公開の `Proof/PipeChangeEnd.lean` のビルドです。

それらの各フレームが待ちの繰り返しの中で操作できる状態で始まること（`FrameStart`）も証明しました（項目 1-1-b-3-4-3）。Start を押したところから、`upClean₁` のもとで帰納法で出します。フィールド `upStart₁` はなくなりました。そのため、入るとき `a₁` は、操作できるときから見て最初の操作できない機械のフレームにしました（`a₂` と `b₂` が最初のフレームであるのと同じです）。`Changes` には数 `a₁` の代わりに上限 `dA` が入ります。

記号です。`seq n` はフレーム `n` が始まるときの機械で、`seq (n+1) = frame(seq n, inp n)` です。フレーム 0 は操作できる前のフレームなので、`seq 1` は操作できます。`ctl(m)` は `m` が操作できることです: モードがゲーム、タスクがゲームコア、ルーチンがプレイヤーのもの。`a` は `a₁`、入るフレームのあとの機械です。

```
a₁ = upEnd(seq, dA) = 1 ≤ n ≤ 1 + dA で (¬ctl(seq n) または n = 1 + dA) となる最小の n
```
`e` は基準の入る状態です。見張るバイトは `(i, k, v)` で、番地、条件にするビット、`e` での値です。

```
Watched(W, m)  :  ∀ (i, k, v) ∈ W,  m[i] & k = v & k
atEntry        :  Entry の 109 バイトのうち restNames 以外             (73)
held           :  atEntry のうち OperMode と OperMode_Task 以外         (71)
kept           :  held のうち endNames（左右のボタン）以外              (70)
rt(m)          :  m[GameEngineSubroutine]
IdleAt(m)      :  m は待ちの繰り返しの中でフレームを終えていて、pc とスタックは e と同じ
Rest(m)        :  restNames の Entry のバイトは e の値      (36)
T(m)           :  48 ≤ m[ChangeAreaTimer]                    （土管のタイマー）
```

**定理.** `starts_of_title` と `entry_of_title` です。確認は `hB`（`TitleStart.check`）と `hK`（`EntryKeep.Checks`）です。

```
∧ ∀ n, 1 ≤ n < a → ∀ j, Clean_G(trace(seq n, inp n, j))

```

`Route` では、`Changes.upStay` が `a₁` の選び方から `1 ≤ n < a₁` で `ctl(seq n)` を出します。`Run.upStart₁` が `title` と `upClean₁` から `1 ≤ n < a₁` で `FrameStart(seq n)` を出します。`Run.entry₁` が `title`、`Run.upStart₁`、`upClean₁`、`entryRest₁` から `Entry(base.seq a₁)` を出します。`Changes.run₁` はそれを引数にとります。`Run.change₁`、`Run.change₂`、`Run.start`、`Run.roomStart`、`level_ge_of_parts` は 2 つの確認をとります。`route_1_1` の結論は `1748 + j ≤ L` のままです。

## しくみ

**フレーム 0.** `TitleStart` は、押してからフレーム 0 までのすべての機械をおおうフレームの始まりの状態の集まりを作ります。フレーム 0 は、その近い状態か止まった状態で始まります。`nearCheck`（`TitleStart.frame0Check`）はそこからフレーム 0 を Start も含めてどの入力でももう一度歩き、操作できる各終わりで、速さ 0 のほかに、保つ 69 バイトが `e` の値で分かっていることと、状態が操作中のフレームの始まりのとおり待ちの繰り返しの中にあること（`FrameKeep.endOK`: プログラムカウンタとスタック、ドットとそのフラグ、NMI が有効、ストローブなし）を調べます。タイトルのプログラムが操作できるときからのフレームのプログラムと同じことも調べます。近い状態はこれらのバイトを知っています。押してから操作できるまでに、ゲームが分かる値を書くからです。

**操作できるときからの 1 フレーム.** 歩き方は [FrameKeep](f-6-19-FrameKeep-ja.md) と同じです。フレームは待ちの繰り返しで、プレイヤーのルーチン、モード、タスクが分かっていて、保つバイトが分かっている状態で始まります。ほかのバイトは分かっていません。インデックスやポインタを通す書き込みは、ガードのリスト（`held` と `PipeWrites` のリスト）にないバイトをすべて忘れます。`Clean` は、その書き込みがリストのバイトに触らないことです。フレームの終わりは、ルーチンが分かっていて次のとおりなら合格です。

* プレイヤーのルーチンなら、保つバイトがその値で分かっていて、状態は操作中のフレームの始まりのとおり待ちの繰り返しの中にある（`FrameKeep.endOK`）。
* 土管のルーチンなら、`atEntry` のバイトがその値で分かっていて、状態は `IdleAt` のとおり待ちの繰り返しの中にある（ドット、フラグ、`e` のプログラムカウンタとスタック）。左右のボタンはフレームの始まりでは分かっていませんが、このような終わりへのどの道も 0 を書きます。
* ほかのルーチン（死ぬ、パワーアップ、旗、横の土管、…）なら、それ以上はいらない。

表を作る探索は、ルーチンとして書かれる直前のアキュムレータを分けたままにします。そうしないと、死ぬときのルーチンとパワーアップのときのルーチンがまとめられて、110 の終わりでルーチンが分かりませんでした。

**`a₁` が最初の操作できないフレームであるわけ.** 歩きは終わりでモードとタスクを求めません。操作できるときの値を求めると、1 つの終わりで失敗します。ルーチンはプレイヤーのものですが、モードは 2、タスクは 0 です。これは城の終わりの斧です（`HandleAxeMetatile` はモードとタスクを書き、ルーチンはそのままです）。歩きは地図を知らないので、これを除けません。だから帰納法は、`seq (n+1)` で操作できることを `a₁` の選び方からとり、歩きは待ちの繰り返しだけを求めます。

**36 バイトが残るわけ**（12 回目）. 36 バイトのそれぞれで、次の 2 つが成り立ちます。

(1) 土管のフレームの歩きがそのバイトを使う。入るときにそのバイトが分からないと、`zcheck` と `pcheck` が失敗します（`entry-need`）。面の音楽のキューとイベントの音楽のキューでは、探索が 10 分で終わりませんでした（分かっていれば 2 つの歩きで約 40 秒です）。1 つめの矩形波の効果音のキューは上に書いた例外です。使いませんが、それなしの歩きは約 3 倍の大きさです。

(2) Start を押したことと操作できるときからのフレームは、そのバイトを出さない。各バイトを 1 つずつ測りました（`entry-widen`、`entry-writers`、`entry-stores`、exit 0。12 回目にもう一度）。操作できるときから入るまでの本物のフレーム（TAS の 368 フレーム、基準の 440、操作できるときからの乱数の入力 60 走り 25,238 フレーム）で調べ、そのバイトも保つとした歩きの探索と、そのバイトを土管の終わりでだけ求める探索をしました。下のバイトはどれも、このどれかで失敗します。フレームが保つバイトは、どのフレームの始まりでも `e` の値で、1 フレームの歩きで保たれ、フレーム 0 で分かっていて、本物のフレームでインデックスを通して書かれない（書かれると本物のフレームで `upClean₁` が成り立たない）ものでなければなりません。

**土管のタイマー.** 入るフレームはタイマーを書きます: 縦の土管のコードは 48 を書きます。いくつかの終わりでは、同じフレームでそのあとに横の土管のコードも動き、表から読んだ値でタイマーを書き直します。表のどちらの場所を読むかは分かれ道で決まり、タイマーは 160 か 52 になります。前回までは探索がこの 2 つの道をまとめたので、歩きはタイマーのいくつかのビットしか知らず、値は 32、36、48、52、160、164、176、180 のどれかでした。今回は、タイマーのために表を読むところで番号を分けたままにし、タイマーをガードのバイトに入れ、ルーチンが土管のものである状態をタイマーについて知っていることで分けて表に入れます。すると土管のルーチンで終わるどの終わりも、タイマーのビットを 48 以上になるだけ知っています（`timerOK`: 分かっているビットとほかのビット 0 で 48 以上。するとそのビットをもつどの値も 48 以上）。

## 第 13 回に測ったこと: これらのフレームとパート a の条件を 1 つに

`upClean₁` と、パート a の 2 つの条件は、操作から入口までの同じフレームについて述べます。`pipe.lags.clean`（ポーズのバイトも守る `Clean`。入るフレームの前の、数えるものも数えないものも全部のフレーム）と、`pipe.opening.cleanK`（`FrameKeep.guardF` の `CleanK`。数えるフレーム 1〜32）です。`pipe.clean`（入るフレームの、ルーチンの書き込みまでの `Clean`）が 4 つ目です。4 つのガードはどれも `PipeWrites` のガードに守るバイトを足したもので、アイドルループ、`late`、跳ぶ表は同じです。なので 1 つの条件で置き換えられます。

```
GU        :=  PipeWrites のガードで、EntryKeep.guardOf、LagPause.guardP、FrameKeep.guardF の守るバイトを守るもの      （128 バイト）
q         :=  移動のルーチンの端数の書き込み  （FrameKeep.spotOf.store）
upCleanU  :   ∀ n, 1 ≤ n < a₁ → ∀ j,  CleanK(GU, q, trace(seq n, inp n, j))
```

2 つの小さな事実を証明すれば（していません）、ここから 4 つが出ます。

* `FrameKeep.cleanK_sub` は `GU` の `CleanK` から `guardF` の `CleanK` を出します。これが `opening.cleanK` です。
* ガードの `Clean` はどの書き込みにも `Plain` を求め、`CleanK` は `q` での添字 0 の書き込みを除きます。その書き込みはプレイヤーの端数に書きます。`EntryKeep` のガード、`guardP`、`PipeWrites` のガードはこれを守りません（ROM から読む: `q` の `STA abs,X` の `X = 0` での行き先）。この 1 命令についての補題があれば、`upCleanU` から `upClean₁`、`lags.clean`、`pipe.clean` が出ます。
* フレームが同じでなければなりません。入るフレームはフレーム `a₁ − 1` なので `pipe.lags.ix pipe.E + 1 = a₁` です。これは帰納法になります。`ix E` までのフレームは操作できる状態で終わり（数えるフレームは `Lags.ctl`、ほかは `LagFrames.keeps_frame`。こちらはそのフレームの `Clean` が要るので、先に `n < a₁`）、入るフレームは土管のルーチンで終わり（`pipe.enter`）、`Rest` は `seq a₁` が土管のルーチンだと言います。
