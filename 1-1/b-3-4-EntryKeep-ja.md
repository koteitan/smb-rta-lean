# 縦の土管に入るときの状態を、タイトルから出す

**主張.** これは部分的な結果です。`Entry` は、縦の土管に入るフレームの終わりの状態についての条件です（[`fall` なしの部屋への切り替え](b-3-2-PipeChangeEnd-ja.md)）。フレームが待ちの繰り返しの中で終わっていて、土管のタイマーが 48 以上で、115 バイトとマスクつきの 13 バイトが基準の入る状態の値です。ここでは、待ちの繰り返し、土管のタイマー、この 128 のうち 72 を、タイトルで Start を押したことと、操作できるときから入るまでのフレームから出します。[ルート全体](0-1-Route-ja.md)のフィールド `entry₁` はなくなりました。代わりに `Changes` には次の 2 つのフィールドが入ります。

* `entryRest₁`: 残りの 56 バイトだけについての `Entry` の条件（`Rest`）。1 つの状態についての条件です。
* `upClean₁`: 操作できるときから入るまでのフレームの各命令は `Clean` を満たす。ここでは、インデックスやポインタを通す書き込みが触らないバイトに、`held` の 70 バイトと土管のタイマーが入ります。

項目 1-1-b-3-4-2 は、今回 61 バイトとタイマーから 56 バイトに減りました。フレームが保つバイトが 4 つ増え（敵の枠 4 の種類、大砲 0 の場所の 3 バイト）、入るフレームの歩きがもう 1 バイト（左右のボタン）とタイマーを出します。残る 56 バイトのそれぞれに、測ったわけを下に書きます。

それらの各フレームが待ちの繰り返しの中で操作できる状態で始まること（`FrameStart`）も証明しました（項目 1-1-b-3-4-3）。Start を押したところから、`upClean₁` のもとで帰納法で出します。フィールド `upStart₁` はなくなりました。そのため、入るとき `a₁` は、操作できるときから見て最初の操作できない機械のフレームにしました（`a₂` と `b₂` が最初のフレームであるのと同じです）。`Changes` には数 `a₁` の代わりに上限 `dA` が入ります。

記号です。`seq n` はフレーム `n` が始まるときの機械で、`seq (n+1) = frame(seq n, inp n)` です。フレーム 0 は操作できる前のフレームなので、`seq 1` は操作できます。`ctl(m)` は `m` が操作できることです: モードがゲーム、タスクがゲームコア、ルーチンがプレイヤーのもの。`a` は `a₁`、入るフレームのあとの機械です。

```
a₁ = upEnd(seq, dA) = 1 ≤ n ≤ 1 + dA で (¬ctl(seq n) または n = 1 + dA) となる最小の n
```
`e` は基準の入る状態です。見張るバイトは `(i, k, v)` で、番地、条件にするビット、`e` での値です。

```
Watched(W, m)  :  ∀ (i, k, v) ∈ W,  m[i] & k = v & k
atEntry        :  Entry の 128 バイトのうち restNames 以外             (72)
held           :  atEntry のうち OperMode と OperMode_Task 以外         (70)
kept           :  held のうち endNames（左右のボタン）以外              (69)
rt(m)          :  m[GameEngineSubroutine]
IdleAt(m)      :  m は待ちの繰り返しの中でフレームを終えていて、pc とスタックは e と同じ
Rest(m)        :  restNames の Entry のバイトは e の値      (56)
T(m)           :  48 ≤ m[ChangeAreaTimer]                    （土管のタイマー）
```

**定理.** `starts_of_title` と `entry_of_title` です。確認は `hB`（`TitleStart.check`）と `hK`（`EntryKeep.Checks`）です。

```
∧ ∀ n, 1 ≤ n < a → ctl(seq n)
∧ ∀ n, 1 ≤ n < a → ∀ j, Clean_G(trace(seq n, inp n, j))
```


`start_up` は `n` についての帰納法です。フレーム 1 は `Begin.start` から出ます。フレーム `n` が保つバイトをもって `FrameStart` で始まるなら、終わりのルーチンがプレイヤーのものであるとき、歩きはそのフレームを保つバイトをもって待ちの繰り返しの中で終えます（`keep_start`）。`seq (n+1)` で操作できることから、ルーチン、モード、タスクが出ます。それから `Watched(atEntry, seq a)`、`IdleAt(seq a)`、`T(seq a)` です（`pipe_end`、`watched_entryT`）。`seq a` のルーチンは `Rest` から土管のものです。`a = 1` なら、`seq 1` は操作できるのでルーチンはプレイヤーのもので、`Rest` と食い違います。

`Route` では、`Changes.upStay` が `a₁` の選び方から `1 ≤ n < a₁` で `ctl(seq n)` を出します。`Run.upStart₁` が `title` と `upClean₁` から `1 ≤ n < a₁` で `FrameStart(seq n)` を出します。`Run.entry₁` が `title`、`Run.upStart₁`、`upClean₁`、`entryRest₁` から `Entry(chg.seq chg.a₁)` を出します。`Changes.run₁` はそれを引数にとります。`Run.change₁`、`Run.change₂`、`Run.start`、`Run.roomStart`、`level_ge_of_parts` は 2 つの確認をとります。`route_1_1` の結論は `1748 + j ≤ L` のままです。

## しくみ

**フレーム 0.** `TitleStart` は、押してからフレーム 0 までのすべての機械をおおうフレームの始まりの状態の集まりを作ります。フレーム 0 は、その近い状態か止まった状態で始まります。`nearCheck`（`TitleStart.frame0Check`）はそこからフレーム 0 を Start も含めてどの入力でももう一度歩き、操作できる各終わりで、速さ 0 のほかに、保つ 69 バイトが `e` の値で分かっていることと、状態が操作中のフレームの始まりのとおり待ちの繰り返しの中にあること（`FrameKeep.endOK`: プログラムカウンタとスタック、ドットとそのフラグ、NMI が有効、ストローブなし）を調べます。タイトルのプログラムが操作できるときからのフレームのプログラムと同じことも調べます。近い状態はこれらのバイトを知っています。押してから操作できるまでに、ゲームが分かる値を書くからです。

**操作できるときからの 1 フレーム.** 歩き方は [FrameKeep](f-6-19-FrameKeep-ja.md) と同じです。フレームは待ちの繰り返しで、プレイヤーのルーチン、モード、タスクが分かっていて、保つバイトが分かっている状態で始まります。ほかのバイトは分かっていません。インデックスやポインタを通す書き込みは、ガードのリスト（`held` と `PipeWrites` のリスト）にないバイトをすべて忘れます。`Clean` は、その書き込みがリストのバイトに触らないことです。フレームの終わりは、ルーチンが分かっていて次のとおりなら合格です。

* プレイヤーのルーチンなら、保つバイトがその値で分かっていて、状態は操作中のフレームの始まりのとおり待ちの繰り返しの中にある（`FrameKeep.endOK`）。
* 土管のルーチンなら、`atEntry` のバイトがその値で分かっていて、状態は `IdleAt` のとおり待ちの繰り返しの中にある（ドット、フラグ、`e` のプログラムカウンタとスタック）。左右のボタンはフレームの始まりでは分かっていませんが、このような終わりへのどの道も 0 を書きます。
* ほかのルーチン（死ぬ、パワーアップ、旗、横の土管、…）なら、それ以上はいらない。

表を作る探索は、ルーチンとして書かれる直前のアキュムレータを分けたままにします。そうしないと、死ぬときのルーチンとパワーアップのときのルーチンがまとめられて、110 の終わりでルーチンが分かりませんでした。

**`a₁` が最初の操作できないフレームであるわけ.** 歩きは終わりでモードとタスクを求めません。操作できるときの値を求めると、1 つの終わりで失敗します。ルーチンはプレイヤーのものですが、モードは 2、タスクは 0 です。これは城の終わりの斧です（`HandleAxeMetatile` はモードとタスクを書き、ルーチンはそのままです）。歩きは地図を知らないので、これを除けません。だから帰納法は、`seq (n+1)` で操作できることを `a₁` の選び方からとり、歩きは待ちの繰り返しだけを求めます。

**56 バイトが残るわけ.** 各バイトを 1 つずつ測りました（`entry-widen`、`entry-writers`、`entry-stores`、exit 0）。操作できるときから入るまでの本物のフレーム（TAS の 368 フレーム、基準の 440、操作できるときからの乱数の入力 60 走り 25,238 フレーム）で調べ、そのバイトも保つとした歩きの探索と、そのバイトを土管の終わりでだけ求める探索をしました。下のバイトはどれも、このどれかで失敗します。フレームが保つバイトは、どのフレームの始まりでも `e` の値で、1 フレームの歩きで保たれ、フレーム 0 で分かっていて、本物のフレームでインデックスを通して書かれない（書かれると本物のフレームで `upClean₁` が成り立たない）ものでなければなりません。

**土管のタイマー.** 入るフレームはタイマーを書きます: 縦の土管のコードは 48 を書きます。いくつかの終わりでは、同じフレームでそのあとに横の土管のコードも動き、表から読んだ値でタイマーを書き直します。表のどちらの場所を読むかは分かれ道で決まり、タイマーは 160 か 52 になります。前回までは探索がこの 2 つの道をまとめたので、歩きはタイマーのいくつかのビットしか知らず、値は 32、36、48、52、160、164、176、180 のどれかでした。今回は、タイマーのために表を読むところで番号を分けたままにし、タイマーをガードのバイトに入れ、ルーチンが土管のものである状態をタイマーについて知っていることで分けて表に入れます。すると土管のルーチンで終わるどの終わりも、タイマーのビットを 48 以上になるだけ知っています（`timerOK`: 分かっているビットとほかのビット 0 で 48 以上。するとそのビットをもつどの値も 48 以上）。

**確認.** ネイティブで（`entry-walk-check`、exit 0）`nearCheck` 1.3 秒、`keepCheck` 4.4 秒（1,176,662 ステップの探索と 53,437 状態の表、そのあとの歩き）、`listCheck` はすぐです。探索は失敗する終わりを見つけません。証明のビルドでは 3 つの確認で約 7 秒です。

## 仮定（Lean では証明していないこと）

* `entryRest₁`: 入るときの `Rest`。56 バイトです。今回の前は、土管のタイマーとさらに 5 バイトも仮定していました。その前の `entry₁` は、待ちの繰り返し、タイマー、128 バイトを仮定していました。
* `upClean₁`: 操作できるときから入るまでのフレームの各命令は `Clean`。インデックスやポインタを通す書き込みは、`held` の 70 バイトと土管のタイマーに触らない。入る前に次の枠を使う走りは定理の外です: 敵の枠 3 と 6 と枠 4 の種類と状態、ファイアボール、ブロック 2 と 3、その他の物 0〜7、大砲 0〜5、得点 3、4、6。ここで調べた本物の走りでは使いません。今回、枠 4 の種類、大砲 0 の場所、左右のボタン、土管のタイマーがこのバイトに加わりました。本物のフレームでは、インデックスを通す書き込みはこれらに触りません（`entry-keep-check`）。

`upClean₁` はここでは減らしていません。`entry-clean-use`（exit 0）は、歩きの状態では決まらないので歩きが命令を `Clean` に任せる場所を数えます。ドットの上限（`late`）は、歩きが通る 9,068 の場所すべてで使います。インデックスやポインタを通す書き込みで、行き先が分からないもの: 710 の場所。物、絵、つる、花火、橋、得点などの 324 のルーチンにあります。ポインタが分からない `LDA (zp),Y`: 47 の場所（エリアの解析、敵のデータ、音楽）。番号が分からないジャンプ: 1 つの場所。そのような書き込みのある 724 の場所のうち、どの訪問でも歩きが行き先を知っているのは 14 の場所だけです。だから、歩きが知らないところだけで `Clean` を求めても、減るのは 14 の場所です。
