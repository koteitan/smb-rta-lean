# 部屋を通る画面のバッファの制御

**主張.** 部屋のどのフレームも、部屋の最初の操作から横の土管に入るフレームまで、画面のバッファの制御が 0 か 6 で始まります。証明しました。ROM の確認は 2 つです。部屋のフレームの歩き 2 つ（ネイティブで合わせて約 8 秒）と、最初の切り替えの段の確認 1 つ（ネイティブで約 30 秒）です。フィールド `buffer₂` は残ります。今は値を 1 つだけ除きます。入るフレームの始めの制御 6 です。これはコインを消したフレームの後の値です。これが起きないことは証明していません。

名前は [横の土管の入口の画面のバッファ](d-2-5-5-EntryBuffer-ja.md) のものです。`c(m)` は機械 `m` の画面のバッファの制御（`VRAM_Buffer_AddrCtrl`）です。`r` は部屋の基準の機械で、`c(r) = 0` です。`r₆` は `c = 6` にした `r` です。`K_T` は部屋の条件が知るビットの表（地図のビット）で、`K_B := K_T ∪ { c のすべてのビット }` です。`seq(n)` は走りのフレーム `n` が始まるときの機械、`trₙ(j)` はフレーム `n` の `j` 命令目の機械です。`b₁` は部屋の最初の操作、`a₂` は横の土管の入口です。

## 主張の式

```
finK(B)        :=  B は c を知り、その値は 0 か 6
keepCheck      :=  K_T は c を挙げない,   c(r) = 0,
                   K_B での部屋の歩きは r から finK の状態で終わる,   r₆ からも

keep_frame     :  (r', K) からの歩きが finK で終わる,   RoomCond(r', K, m),   ∀ j, SiteOK(tr(j))     →   c(frame(m, i)) ∈ {0, 6}
cond0          :  RoomCond(r, K, m),   c(m) = c(r)                                    →   RoomCond(r, K ∪ {c}, m)
cond6          :  RoomCond(r, K, m),   K は c を挙げない,   c(m) = 6                  →   RoomCond(r₆, K ∪ {c}, m)
ctl_step       :  keepCheck,   RoomCond(r, K_T, m),   ∀ j, SiteOK(tr(j)),   c(m) ∈ {0, 6}     →   c(frame(m, i)) ∈ {0, 6}
ctl_run        :  [b, a) で RoomMap.map_of_rows の条件,   c(seq b) ∈ {0, 6}            →   ∀ n ∈ [b, a],  c(seq n) ∈ {0, 6}

startCheckC    :=  最初の切り替えの時間の段のどの状態も、K_B のビットを r の値で知る
start_ctl      :  startCheckC,   InRowsT(m),   m は操作できる                        →   c(m) = c(r)
ctl_of_rows    :  [b, a) で RoomMap.map_of_rows の条件,   keepCheck,   startCheckC     →   ∀ n ∈ [b, a],  c(seq n) ∈ {0, 6}

Run.ctl₂       :  c(seq(a₂ − 1)) = 0   ∨   c(seq(a₂ − 1)) = 6                          （定理、新しい）
Run.buffer₂    :  c(seq(a₂ − 1)) = c(r)   ∨   EntryAt(L₅, seq a₂)                        （フィールド、変わらない）
```

`Run.ctl₂` は `b = b₁`、`a = a₂` とします。`b₁` の機械は最初の切り替えの段にあり（`ChangesK.run₁`、`inRowsT`）、操作できます（`ChangesBase.ctl₁`）。`b₁` から `a₂` の前までの各フレームは `SiteOK` を満たし（`chg.roomSites`）、プレイヤーのルーチンで始まります（`ChangesBase.roomStay`）。`b₁ < a₂`（`Run.b₁_lt_a₂`）なので `b₁ ≤ a₂ − 1 ≤ a₂` です。確認 `keepCheck` と `startCheckC` はもう 1 つの引数（`BufferControl.Facts`）で来ます。`RoomChecks` のフィールドではありません。

## しくみ

**制御を書くもの.** 割り込みの処理は、制御が指すバッファを描き、制御を 0 にします。ゲームのコードでは、コインを消す処理が制御を 6 にします（次のフレームが 2 つ目のバッファを描くためです。消す処理はそこに空のタイルを書きます）。面の組み立ての列の出力と、その属性の描画も 6 にします。ほかの値にするのは、文字と色を書く作業だけです。部屋の実際のフレームでは、制御を書く命令は 2 つだけです。処理の戻しと、コインを消す処理です。

**歩き.** `EntryBuffer` の歩きです。フレームの始めに制御を知る部屋の歩きで、探索の鍵に制御があります。制御 0 からも制御 6 からも、どの道も制御が 0 か 6 と分かって終わります。制御 6 では処理は 2 つ目のバッファを描きます。歩きはそのバイトを知りません。歩きはそれを知らずにこの描画をたどり、失敗する道はありません。

**部屋の最初の操作.** 最初の切り替えの段は、そこで制御を基準の値 0 で知ります。そこで部屋のフレームの帰納は 0 から始まります。

**`buffer₂` がまだ求めること.** 入るフレームの始めに制御は 0 か 6 です。0 なら 1 つ目のバッファの 5 バイトは証明されています（`Run.buf₂`）。6 なら前のフレームがコインを消しました。そのとき処理は 2 つ目のバッファを描き、1 つ目の記録（コインの数字）を残します。5 バイトは基準のものになりません。そこで 6 を除くために `buffer₂` がまだ要ります。

## 測ったこと（定理ではない）

`buffer-ctl-check FM2 300 real`（終了コード 0）: ムービーの部屋と、ムービーの部屋のフレームからの自分の走りです。種類ごとに小さいプレイヤーで 300、大きいプレイヤーで 300 走ります。種類 0 は部屋のどのフレームからでも乱数の入力です。種類 1 はムービーの入口の前 60 フレームから始め、ジャンプが多い入力です（ブロックの右端の近くのコインを取ります）。

| 走り | フレーム | 入口 | 制御を立てて終わるフレーム | フレームの終わりの制御 | コインを消す位置の最大 | 入るフレームの始めの位置の最小 | 制御を立てた最後のフレームから入口までのフレーム |
|---|---|---|---|---|---|---|---|
| ムービー | 111 | 1 | 13 | 0, 6 | 163 px | 194 px | 16 |
| 種類 0、小さい | 125,891 | 102 | 1,019 | 0, 6 | 173 px | 193 px | 16 以上 |
| 種類 0、大きい | 113,761 | 126 | 1,229 | 0, 6 | 172 px | 194 px | 16 以上 |
| 種類 1、小さい | 66,202 | 218 | 1,178 | 0, 6 | 173 px | 194 px | 16 以上 |
| 種類 1、大きい | 69,677 | 208 | 1,245 | 0, 6 | 172 px | 194 px | 16 以上 |

どの走りでも: 制御を変える命令は処理の戻しとコインを消す処理だけです。ページは 0 です。消したコインは地図のコインの列にあり、いちばん近いものは口の列の 3 列左です。コインを消すフレームは消した位置で終わります。1 フレームは位置を、始めから移動の終わりまで −1 から 3 px、その後で −1 から 1 px 動かします。制御 6 で始まる入るフレームはありません。部屋の最初の操作で制御は 0 です（ムービー）。最初の切り替えの段のどの状態も、それを 0 と知ります（14,224 状態）。

歩き（`buffer-ctl-check FM2 0 walk`）: 制御 0 から 172,182 歩、失敗 0。制御 6 から 323,827 歩、失敗 0。どちらも制御 0 か 6 で終わります。確認（`buffer-ctl-check FM2 0 keep`）: `keepCheck` 8.1 秒、`startCheckC` 30.4 秒（ネイティブ、混んだ機械）。

## 測ったこと: 部屋の `SiteOK` の各部分

`chg.roomSites`（1-1-d-2-4-2）は部屋の各命令で `SiteOK` を求めます。`buffer-ctl-check FM2 100 sites`（終了コード 0）は、ムービーの部屋のフレームからの自分の走りの命令を全部たどります。小さいプレイヤーで 100 走り（42,438 フレーム）、大きいプレイヤーで 100 走り（42,452 フレーム）です。どの部分を外れる命令もありません。余裕は次のとおりです:

| 部分 | 実際のフレーム | 証明に要るもの |
|---|---|---|
| `late` | 処理はドット 42,656 までに終わる。上限は 83,342 | 歩きのどの道の時間の上限（歩きはこの部分で時計を抑える） |
| `reads` | ポインタを通す読みは 15 か所で 176 万回、すべて RAM か ROM | その読みごとにポインタの上のバイトを知ること |
| `read` | 読んだタイルは表にある。頭の読みは何もないかコインだけ。ブロックのバッファの外の読みはない | 各命令での地図のバイト（部 c の `RoomBlocks` が証明するが、`roomSites` から）。頭には位置: 届く頭の上にレンガがないこと |
| `erase` | 消す処理 695 回、すべてブロックのバッファの中 | 消す場所は読みの場所 |
| `off` | 画面バッファのオフセットは使う所で最大 46。上限は 64 | 1 フレームが書く記録の上限 |
| `xbit` | 横の土管の読みでの位置の下のビットは 3 か 4 | 入口での位置 |

## `buffer₂` をなくすには（していない）

部屋のどのフレームでも `Cls(m) := c(m) = 0 ∨ (c(m) = 6 ∧ x(m) < 176)` を証明すればよいです。`x` はページの上の位置で、176 px はいちばん近いコインの右の列の左端です。つまり、`c = 6` で終わるフレームは 176 px より左で終わり、176 px より左で始まるフレームは入りません（口の左端は 195 px）。測った余裕は大きいです（173 px と 193 px）。しかし抽象の機械の足し算は、バイトのビットを全部知るか何も知らないかです。そこで歩きは、衝突のルーチンが位置にずれを足すところと、移動が速さを足すところで、位置を値に分けなければなりません。2 つの作りをプログラムで試しました（証明の一部ではない）:

* ブロックのバッファの読みごとに位置を分ける（256 値 × ページのビット × 行）: 1,250 万歩、230 万状態、146 秒、失敗 1,004。
* 移動の終わりで位置を 174 px の左右の片に分け、その右の読み、横の読み、押し戻しでだけ値に分ける。`EntryHeightBig` の読み（知った場所の地図のバイト）を使い、ブロックのバッファの外を消す命令には機械がないとする: 制御 0 から 300 万歩、70 万 7 千状態、31 秒、2.5 GB、失敗 24、制御 6 で位置の片が 176 px より右のフレームの終わり 48（コインを消す処理を通らない道から）。制御 6 からは、3 つの組のうち 2 つが 5.5 GB を超えて止めました。残りの 1 つは入る終わりが 136 ありました（抽象の移動でページが回ります）。
