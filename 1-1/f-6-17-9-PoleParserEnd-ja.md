# 旗のタイル: エリアの解析、フレームの後半

[エリアの解析と画面の左の端](f-6-17-8-PoleParser-ja.md) は、操作の始まりの解析の不変式、1 フレームの決まりがそれを保つこと、本物のフレームでの決まりの前半（フレームの始まりから `UpdScrollVar` まで、`frame_toU`）を証明しました。後半（`ParseU`、`UpdScrollVar` からフレームの終わりまで）が残っていました。このページはそれを、残りのタスクの数 `N` が 0 から 8 のどの値でも、不変式を同じく保つ弱い形の決まりで証明します。フィールド `tilesCol` は変わりません。ルートはまだこれを使いません。

## 弱い決まり

[前のページ](f-6-17-8-PoleParser-ja.md) の言葉: `N` は残りのタスクの数、`S` はスクロールのカウンタ、`col` はページ込みの解析の列（1 ページ 16 列）、`edge` は画面の左の端（px）。

```
Step(a, b)    :=  if a.n = 0 then 32 ≤ a.s < 160 ∧ b.n = 7 ∧ b.s = a.s − 32 ∧ b.col = a.col
                  else b.n = a.n − 1 ∧ b.s = a.s ∧ b.col = a.col + [a.n ∈ {1, 5}]
ParseW(a, b)  :=  b.edge = a.edge ∧ ((b.n, b.s, b.col) = (a.n, a.s, a.col) ∨ Step(a, b))
RuleW(a, b)   :=  ∃ c, Scroll(a, c) ∧ ParseW(c, b)
```

`ParseW` はどちらの場合になるかを言いません（画面のバッファの制御のバイトが 6 ならバイトは保たれます）。どの場合も `Parse` の場合の一つなので:

* `parseW_of : Parse(ctl6, a, b) ⇒ ParseW(a, b)`、`ruleW_of : Rule(a, b) ⇒ RuleW(a, b)`;
* `inv_ruleW : Inv(L, a) ∧ RuleW(a, b) ⇒ Inv(L, b)`、ランのフレームについては `inv_runW`。

## フレーム全体

`rule_frame`: 操作できて、プレイヤーのルーチンに来るフレームは弱い決まりに従う。

```
RuleW(vals(m), vals(frame(m, i)))
```

条件は、始まりで `N ≤ 8`、解析の列（ページの中）が 16 より小さく、ページが 255 でないこと、そして `frame_toU` の条件（下）です。3 つの場合 `rule_zero`（`N = 0`）、`rule_col`（`N ∈ {1, 5}`: 列を進める）、`rule_six`（`N ∈ {2, 3, 4, 6, 7, 8}`）からなります。プレイヤーのルーチンに来ないフレームはバイトを保つので（前のページの `rule_of_noCut`）、`Rule` にも `RuleW` にも従います。

## しかた: `UpdScrollVar` からフレームの終わりまでの歩き

`PoleParser.uCheckP` の `UpdScrollVar` までの歩き（バイトごとに一つ、そのバイトを追う）が、そこから先に進みます（`atE`）。追うバイトは解析の 4 つと端の 2 つです（`pE`）。`UpdScrollVar` で各状態を `N` の値で分け（`SideFrame.fillB`）、値ごとに `EdgeStep` の歩き（`walkKP`）がフレームの終わりまで行きます:

* `N ∈ {2, 3, 4, 6, 7, 8}`（`atRkE`）: 歩きはバイトを追うので、バイトは保たれます。`N` 自身は値を知っていて、終わりで `v` か `v − 1` を求めます（`finE`）。
* `N ∈ {1, 5}`（`atRkV`）: 列を進めるところが列と、たぶんページを書くので、歩きはそれを追えません。ページの歩きをさらに列 `c`（16 より小さい）で分けます。`c < 15` ならページを追い、終わりで `N` と列が保たれるか、`N − 1` と `c + 1` を求めます（`finC`）。`c = 15` ならページ `p`（255 でない）で分け、`N` と列とページが保たれるか、`N − 1` と列 0 とページ `p + 1` を求めます（`finP`）。ほかのバイトは上と同じに追います。
* `N = 0`（`atRkZ`）: `UpdScrollVar` は `S` を 32 と比べ、`S − 32` を書きます。カウンタの歩きをその値 `s` で分け、表なしで、フレームの終わり（`N = 0` と `S = s` を求める、`fin0`）か、タスクの処理の呼び出し（`qR`、`RunParser`）まで行きます。そこでは `32 ≤ s < 160` と `S = s − 32` を求め、`S` を追う歩きがフレームの終わりまで続き、`N = 7` を求めます（`finT`）。`walkEQ` と `endEQ` が、このフレームの終わりか決まった場所までの歩きです。ほかのバイトは上と同じに追います。

`keep_eP`（`keep_uP` の歩きの鎖にこれらの歩きをつないだもの）と `frame_six`（`frame_toU` と同じ形のフレーム全体）がフレームの終わりの事実を出します。`parseW_six`、`parseW_col`、`parseW_zero` がそれを `ParseW` にし、`scroll_of` が `frame_toU` の結論と巻き戻らないことから `Scroll` を出します。

ROM の確かめは `eCheckP` です。非公開の証明 `pole_parser_e` が地上（エリアの種類 1）でそれを出します。非公開のファイル `Proof/PoleParserEnd.lean`（下の `pole_parser_col` も入る）はネイティブで 32〜85 秒でビルドされます（最後の全体の実行で 85 秒、機械にほかの仕事があるとき）。

**27 回目に見つからなかった輪。** 27 回目のこの種の歩きは燃料が尽きました。最初に失敗する歩きの道を返すプローブで分かりました: `DrawMTLoop`（`RenderAreaGraphics`）と `AttribLoop`（`RenderAttributeTables`）を何度もまわります。歩きのガードが `N` を守っていませんでした。`DrawMTLoop` の、行き先の分からない添字つきの書き込みで、歩きは `N` とゼロページの輪のカウンタを忘れ、`DEC N` の後の `N` が分からなくなり、道は `RenderAttributeTables` に入り、輪のどの状態も表に覆われませんでした（表の探索は `N` を守っていました）。ここでは終わりまでの歩きのガードが、そのバイトと `N` と列とページを守り（`guardN`）、表のキーがそれらの値を持ちます（`keyN`）。それで、待ちの輪で `N = v` の状態と `N = v − 1` の状態が一つにまとめられません。

## ページの中の列と、ランの上の不変式

列を進めるところは、フレームの始まりで解析のページの中の列が 16 より小さいことを求めます。これは操作の始まりで成り立ち（`col₀`、横の土管から出る変化の行から、`inv₀` と同じに。確かめ `colCheckK`、非公開の証明 `pole_parser_col`）、各フレームがそれを保ちます（`col_frame`。プレイヤーのルーチンに来ないフレームはバイトを保つ、`step_noCut`）。不変式が成り立ち `edge + L < 65280` ならページは 255 ではありません（`page_of_inv`。`L = 384` なら端が 64896 px より前）。なので帰納法で（`inv_runC`、`step_frame`、`step_noCut`）:

```
Inv(L, ms 0) ∧ ColOK(ms 0)  ∧  ∀ n, (フレーム n の条件、edge(ms n) + L < 65280)
  ⇒  ∀ n, Inv(L, ms n) ∧ ColOK(ms n)
```

すると `N ≤ 8` と列が 16 より小さいことはフレームの仮定ではなくなります: 帰納法から出ます。`step_frame` ではバイトの保護は各命令の一つの条件、`guardPar`（フレームのガードに解析の 4 バイト、端の 2 バイト、足場のスクロールへの力を守るものを足したもの）の `CleanK` です。これが歩きの条件（`cleanH_of_par`、`cleanN_of_par`）と `FrameKeep.guardF` の `CleanK` を出します。ランのフレームのフィールド `cleanE`（`FrameKeep.guardE` の `CleanK`。端のバイトを守る）があれば、新しいのは `guardPI` の `CleanK` だけです: 添字やポインタを通した書き込みは解析の 4 バイトを書かない（`cleanPar_of`）。

`inv_onFrames` は、この帰納法をランの触るフレームまでのフレーム（`FrameKeep.Frames`、操作の始まりの機械から）の上でしたものです: フレームが、待ちの輪で操作できる状態で始まること（`Frames.all_start`）、`cleanE`、`noStore`、時間を出し、各フレームはプレイヤーのルーチンに初めて来るか、まったく来ないかです（`arrival_cases`）。触るフレームより前の各フレームに求めるのは、エリアの種類 `v`、スクロールの処理から先のフィールド `posW`、巻き戻らないこと、端が `65280 − L` px より前であること、`guardPI` の `CleanK` です。`L = 384` なら、触るフレームまでのどのフレームの始まりでも `16·col + 16·p(N) + S = edge + 384`、`N ≤ 8`、列が 16 より小さい、が出ます。

## 条件

`frame_toU` の条件と:

* （`hN`）フレームの各命令が `pE` の各バイトについて `guardN` の `CleanK` を満たす: 添字やポインタを通した書き込みは、そのバイトも `N` も列もページも書かない;
* （`hw`、`NoWrap`）`UpdScrollVar` でスクロールが巻き戻らない: `S + Y < 256`、`edge + Y < 2¹⁶`;
* フレームの始まりで `N ≤ 8`（`Inv` の一部）、列が 16 より小さく、ページが 255 でない（列を進めるため）。ランの上では、はじめの二つは上の帰納法から、三つめは端が 64896 px より前であることから出ます。

どれも一つの命令か一つの状態の条件です。どれもフィールドではありません。ルートはまだこれを使いません。

## 証明していないこと

* ランのフレームでの解析のバイトの保護（`hH`、`hN`）: 測ると、添字やポインタを通した書き込みはそれらを書きません。`FrameKeep.guardE` には入っていません。
* 各フレームでスクロールが巻き戻らないこと、端が 64896 px より前であること（測ると解析のページは最大 13）。
* フレームをまたぐ `hslot`（解析は旗のタイルを旗の列にだけ描く）、触るフレームでの `hnear`、`hread`。

なので `tilesCol` は残ります。

29 回目: ルートがこれらの条件を与え、`tilesCol` は `TileSlot` だけを求めます（[ルートのフレームの上のエリアの解析](f-6-17-10-PoleParserRun-ja.md)）。歩きは、プレイヤーのルーチンに最初に来たところからだけ `posW` を求めます。

31 回目: `UpdScrollVar` での歩きを、画面のバッファの制御バイトが 6 でない 8 つの切れにも分けます（`ctlPats`）。各切れから厳しい歩きがフレームの終わりで `N − 1` を求めます（`N` = 0 でカウンタが 32 ‥ 159 なら、タスクの処理の呼び出し）。`keep_eP` と `frame_six` は最後にこの 2 つの事実を持ちます（[各フレームの厳しい規則](f-6-17-12-PoleStrict-ja.md)）。
