# 旗に触るフレームを本物のフレームで

**主張.** これは部分的な結果です。「触る」を本物の機械の上で定義します。あるフレームが触るなら、そのフレームの横の判定がページを読むとき、マリオの位置は旗の範囲の左端より左ではありません。ですから `PoleJoin.Run` の仮定 `inRange` はなくなり、定理 `Run.inRange` になります。証明は横の判定の 1 回の通過を抽象機械で追います。フレームの残りは追いません。残りは仮定 `Pass` と `pos` です。

**走りではもう使いません.** `PoleJoin.Run` はこの通過をもう使いません。[旗に触るフレーム: 1 フレーム全部](f-6-16-PoleFrame-ja.md) が触るフレーム全部を追います。ですから `Pass` と `pos` は走りの仮定ではなくなり、`Run.inRange` はその歩きから出ます。このページは 1 回の通過の証明として残します。そのプログラムは前の仮定を本物のフレームで確かめます。

`frame(m, i)` は入力 `i` の本物の 1 フレームです。`tr(n)` は、そのフレームの `n` 命令あとの機械です。`rt(m)` は `GameEngineSubroutine` です。`e_f` は旗のルーチンの番号です。`page(m)` は `Player_PageLoc`、`x(m)` は `Player_X_Position` です。`pg` は旗のページ、`col` は旗の列です。`w` は `RunFR` の中で `rt` を書く命令です。`T_b`、`T_s` は旗の玉と棒のタイルです。`d_C` はブロックバッファの中の旗の列の一番上の場所です。`R` はブロックバッファの行の数です。

```
WriteStep(n)    :=  rt(tr(n)) ≠ e_f  ∧  rt(tr(n + 1)) = e_f
Touches(m, i)   :=  ∃ n,  WriteStep(n)
EndsTouch(m, i) :=  rt(m) ≠ e_f  ∧  rt(frame(m, i)) = e_f
px(m)           :=  256·page(m) + x(m)
L_px            :=  256·pg + 16·col − 10

Start(m)        :=  pc(m) = DoPlayerSideCheck、スタックポインタは決まった値、足し算の番号のバイトは大きいマリオか小さいマリオの値、
                    ドットは vblank が終わったあとでフレームの終わりより前、NMI も vblank もなし、ストローブなし
AtEntry(m)      :=  pc(m) = BlockBufferCollision の中でページを読む命令  ∧  レジスタ Y は横の判定の番号  ∧  レジスタ X = 0
AtRead(m)       :=  pc(m) = このルーチンの `LDA (zp),Y`
RowOK(m)        :=  Y mod 16 = 0  ∧  Y < 16·R
TilesOK(m)      :=  ∀ ブロックバッファの場所 d,  mem(d) ∈ {T_b, T_s}  →  (∃ r < R,  d = d_C + 16·r)  ∧  pg ≤ page(m) + 1
Pass(n)         :=  pc(tr(n)) = w  ∧  ∃ n₀ ≤ n,  Start(tr(n₀))
                    ∧  (∀ j ∈ [n₀, n],  pc(tr(j)) ∉ {ExSCH, ExCSM, ExHC, ContSChk, VineCollision})
                    ∧  (∀ j ∈ [n₀, n),  AtRead(tr(j))  →  RowOK(tr(j)) ∧ TilesOK(tr(j)))
pos(P₂)         :=  ∀ n j,  WriteStep(n)  →  j < n  →  AtEntry(tr(j))  →  ∃ f ≥ 0,  P₂ = 256·px(tr(j)) + f
```

```
no_write            :  walkCheck,  s(j + 1) = step(s(j)) (j < n),  Start(s(0)),
                       (∀ j < n,  AtEntry(s(j)) → px(s(j)) < L_px),  (∀ j < n,  AtRead(s(j)) → RowOK ∧ TilesOK),
                       出口に行かない (j ≤ n)                                  →  pc(s(n)) ≠ w
touch_right_of_left :  ruleCheck,  Touches(m, i),  (∀ n,  WriteStep(n) → Pass(n))
                       →  ∃ n j,  WriteStep(n) ∧ j < n ∧ AtEntry(tr(j)) ∧ L_px ≤ px(tr(j))
inRange_of_pass     :  ruleCheck,  Touches(m, i),  (∀ n,  WriteStep(n) → Pass(n)),  pos(P₂)  →  P₀ ≤ P₂
Run.inRange         :  ruleCheck,  Run  →  P₀ ≤ P₂(g)          （前の回まで。今は 1 フレーム全部から、f-6-16）
touches_of_ends     :  EndsTouch(m, i)  →  Touches(m, i)
pole_rule_check（非公開） :  ruleCheck(sy, m₀) = true（native_decide）
```

**訂正.** 前の `Touches` は今の `EndsTouch` でした。フレームの終わりで旗のルーチンになる、という形です。これは直接つかむ全部の場合で成り立ちません。TAS もそうです。旗のルーチン（`FlagpoleRoutine`）は同じフレームのあとで動きます。マリオが `FlagGrabY` 以下にいると、すぐに面の終わり（`GiveFPScr`）を始めます。ですから TAS の触るフレーム（フレーム 1092）は、操作のルーチンから面の終わりのルーチンになり、`e_f` で終わりません。直接つかむときの高さは `FlagGrabY` 以下です（`IsDirect`）。なので直接つかむ走りは、どれも `Run` の `touches` を満たしていませんでした。プログラムは書き込みの命令で触るフレームを数えていたので、これに気づきませんでした。今の `Touches` は、そのフレームのある命令が `e_f` を書く、という形です。定理は変わりません。証明が使っていたのはその命令だけです。前の形からは今の形が出ます（`touches_of_ends`）。

`P₀ = 256·L_px` は `poleP` です。ROM のない定理が使う公理は `propext`、`Classical.choice`、`Quot.sound` だけです。

Lean: `Theorems/PoleEntryRule.lean`、非公開の `Proof/PoleEntryRule.lean`（`pole_rule_check`、`pole_rule_real`）。`Theorems/PoleJoin.lean` の `Run` は前の回までこれを使っていました。

`Run` のフィールドは次のように変わりました。

* なくなったもの: `inRange`。
* 増えたもの: `fm`、`inp`（フレーム `g` の始めの機械と入力）、`touches`（`Touches(fm, inp)`）、`pass`（`∀ n, WriteStep(n) → Pass(n)`）、`pos`（`pos(P₂(g))`）。
* そのあとなくなったもの: `fm`、`inp`、`pass`、`pos`。`touches` は `keep` のフレーム `g` の `Touches(fm g, pad g)` になりました。増えたもの: `tiles`、`edge`、`moved`（[旗に触るフレーム: 1 フレーム全部](f-6-16-PoleFrame-ja.md)）。

## しくみ

**抽象機械.** [地上への切り替えのはじめのフレーム](d-2-2-SideChangeBound-ja.md) の機械です。[縦の土管に入るフレームを本物のフレームで](a-5-1-PipeEntryRule-ja.md) と同じやり方です。`Start` の状態から始めます。わかっているのはスタックポインタと足し算の番号だけです。ほかの RAM、レジスタ、位置、高さ、速さ、ブロックバッファは全部わかりません。パッドもわかりません。

**3 つの場所で分けます.** どれも機械の変更ではありません。歩くときに状態を部分に分けるだけです（`preP`）。

* 位置の足し算の前: `x` の 256 通りに分けます。仮定はいりません。足した結果の列が旗の列でなければ、`x` はそのあと忘れます。
* ページを読む前: 仮定 `px < L_px` のもとで、ページの値ごとに分けます。`x` を覚えていれば `256·n + x < L_px` の `n` だけです。これでポインタの値がわかります。
* ブロックバッファを読む前: `RowOK` で行の値に分け、`TilesOK` で「読むバイトは `T_b` のあるビットと違う」という形に分けます。使うビットは、`T_s` も `T_b` と同じ値のビットだけです（`tilesCover` が確かめます）。ですから旗のどちらのタイルとも違います。分けるのは、どの行も旗の列でないか、タイルがまだそこにないとき（`page + 1 < pg`）です（`safe`）。

**分けられない読み.** ポインタが旗の列で、タイルがもうありうるときです。`px < L_px` なので、このとき右側の番号で `page = pg` です。`x` は、右側が旗の列に届いていて左端より左の値で、3 つあります。読んだ値はわかりません。しかし `x` の下 4 ビットは `ClimbLowNybble` より小さいので、`HandleClimbing` の比較で出口 `ExHC` に行きます。

**読んだ値のその後.** 読んだバイトのわかっているビットは一時的なバイトに入り、`A` に戻ります。`ChkForFlagpole` の 2 つの `CMP` がそのビットを見て、等しくないとわかります。ですから `w` に行く道はありません。全部の道が、出口に行くか、表の状態に入ります（`walkP`）。

**大きさ.** 82,604 ステップ、43,676 の枝分かれ（分けた部分を含む）、失敗 0、表 5,296。プログラムで約 3 秒、非公開の証明のビルドで 3 秒から 11 秒です（ほかのビルドが動いているとき）。

## `rt` に旗の番号を書く命令

コードから読みました。証明ではありません。`rt` を直接書く命令は 12 個です。

| 命令 | 書く値 |
|---|---|
| `SetPESub` | 登場のルーチン |
| `GameIsOn` の前 | はじめのルーチン |
| `PlayerRdy`、`DonePlayerTask` | 操作のルーチン |
| 死んだあとの命令 | 命を失うルーチン |
| `NoFPObj` の `INC` | 1 つ増やす。これは旗のルーチンの中なので、旗の番号の次になる |
| `GiveFPScr` のあと | 面の終わりのルーチン |
| `SetPRout` | 変身、けが、死 |
| `ChkGERtn` | 横の土管のルーチン |
| **`RunFR`（`w`）** | **旗のルーチン** |
| `VineCollision` | つるのルーチン |
| `HandlePipeEntry` | 縦の土管のルーチン |

ですから旗の番号を直接書くのは `w` だけです。`w` に来るのは `FlagpoleCollision` からだけで、そこに来るのは `HandleClimbing` からだけです。`HandleClimbing` は横の判定の中にしかありません。足の判定と頭の判定からは行きません。

**触るに入らないもの.**

* 旗をすべっているあいだは、フレームのあいだずっと `rt = e_f` です。`w` は同じ値を書き直します。これは `WriteStep` ではないので、このフレームは `Touches` ではありません。
* 添字つきの書き込みやポインタを通す書き込みで `rt` が `e_f` になるフレームは、`Touches` を満たします。しかし `Pass` の `pc(tr(n)) = w` を満たしません。ですから `Run` の仮定がこれを除きます。本物のフレームでは出ません。[縦の土管](a-5-1-PipeEntryRule-ja.md) のページのとおり、この書き込みの候補は 347 個あり、範囲は証明していません。

## 本物のフレームで確かめたこと

プログラムです（`pole-rule-check`）。

| 走り | フレーム | 横の判定（操作） | 読み | 触ったフレーム | 高さの数 |
|---|---|---|---|---|---|
| 動画の、最初の操作から 1239 フレーム | 1,239 | 707 | 2,861 | 1 | 1 |
| 動画のフレーム 1089 まで、そのあと `02808080` | 20 | 4 | 13 | 1 | 1 |
| 左、右、A、B の全部の入力を 6 フレーム、動画の 2 つのフレームから | 12,912 | 8,880 | 29,872 | 48 | 1 |
| 同じものを 5 フレーム、位置を 5 通り前にずらして（`touch-search-at` と同じ） | 4,688 | 4,240 | 16,960 | 2,873 | 4 |
| 旗へ向かう乱数の入力 | 10,940 | 10,768 | 40,619 | 87 | 20 |
| 同じ。大きいマリオに書き換え | 3,778 | 3,718 | 14,044 | 30 | 13 |
| 動画の 22 のフレームから 7 通りの長さのジャンプ | 10,192 | 9,874 | 37,824 | 14 | 9 |
| 列の近くの高さと位置ごとの 1 フレーム。書き換え | 6,864 | 5,901 | 17,301 | 936 | 39 |

* どの行でも、操作のフレームの横の判定はすべて `Start` を満たします。すべての読みは `RowOK` と `TilesOK` を満たします。
* 触ったフレームは全部 `w` で書き、全部 1 回の通過の終わりです。左端より左はありません。ページを読むときの位置は、判定のルーチンの始めの位置と同じです（`pos`）。
* 位置は、範囲の左端から 0 から 3 ピクセルと、16 から 19 ピクセルだけに出ます。これらの走りには、その全部の位置のフレームがあります。
* `pole-join-check` は `Run` の新しいフィールドも見ます。TAS は `f = 80`、フレーム 1089 のあと `02808080` の走りは `f = 64`、TAS で A を長く押した走り（ほかの触り方、`g = 234`）は `f = 112` です。
* 触るフレームの終わりのルーチン: TAS とフレーム 1089 のあと `02808080` の走り（どちらも直接つかむ）は面の終わり、A を長く押した走りは旗のルーチンです。`pole-frac-check` の 676 回の触り（操作できてからと、動画のフレーム 1002 から 1091 からの乱数の入力）のうち、17 回は `FlagGrabY` 以下で、ちょうどその 17 回が面の終わりで終わります。

## 前提（Lean では証明していない）

* **`Pass` の書き込みの部分.** `rt` を `e_f` にする命令は `w` だけ。そのフレームの中で、それより前に横の判定を始めている。そこから出口に行っていない。コードから読みました。上の表の本物のフレームで確かめました。フレームの残り（NMI、音、画面、敵）は追っていません。
* **`Start`.** スタックポインタ、足し算の番号、ドット、フラグです。水の中の大きいマリオの値は入れていません。スタックポインタは操作のルーチンのものです。登場のルーチン（`AutoControlPlayer` を通る）の中の値は入れていません。
* **`RowOK`.** コードの `AND`、`SBC`、`TAY` と、横の判定の始めの `CMP` から読みました。抽象機械の足し算がビットを失うので、確かめていません。
* **`TilesOK`.** 手で書いたブロックバッファと同じ、という前提より狭いです。旗の 2 つのタイルについてだけです。ページの条件は、2 つ前のページまでは旗の列がまだバッファにないことです。旗の列をバッファに書くコードは追っていません。
* **`pos`.** `P₂(g)` はページを読むときの位置です。本物のフレームから `Frame` を作る話の一部です。
* **範囲の右端と高さ.** ここでは左端だけを出します。`Run` が使うのは左端だけです。同じ歩き方で、ページで分ける条件を右側に変えれば右端も出るはずですが、試していません。高さは読みの行で決まりますが、この通過は高さを追いません。

**ファイル.** `Theorems/PoleEntryRule.lean`、非公開の `Proof/PoleEntryRule.lean`。
