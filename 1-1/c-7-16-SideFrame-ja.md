# 横の土管に入るフレーム: 1 フレーム全部

**主張.** 抽象機械が、待ちのループからフレームの終わりまで、1 フレームを追います。フレームのある命令がルーチンのバイトを横の土管のものにするなら、その書き込みより前の移動の終わり（`PlayerSubs`）で、位置は口の左端より左ではありません。ですから `RoomRun` の仮定が 3 つなくなります。`pass`（書き込みは横の判定の 1 回の通過の終わり）、`pos`（`P(E)` は横の判定がページを読むときの位置）、`edgeE`（書き込みまでに画面の端で位置を書かず、頭でブロックに当たらない）です。

抽象機械には 1 つの状態についての条件がいります。縦の土管と同じような条件です（[1 フレーム全部](a-5-2-PipeWrites-ja.md)、[移動の終わりの位置](a-5-9-MoveEnd-ja.md)）。そのうち 4 つは、[部屋のブロックの地図](c-7-12-RoomMap-ja.md) の抽象機械から、走りの本物の機械の上で証明します。フレーム `E` が部屋の画面のバイトを持って操作できる状態で始まること（`StartE`）、書き込みまでの各命令が `Clean` であること（`CleanE`）、読みでは横の土管のタイルが土管の列にしかないこと（`TilesE`）、頭がブロックに当たったときのルーチンに来ないこと（`HeadE`）です。1 つは仮定のままです。`movedE` です。

抽象機械は、スクロールのルーチンが画面の端で位置を書く命令（`w_edge`）も追います。部屋の画面のバイト（スクロールの固定、両端の位置とページ）を知っていて、スクロールのルーチンが画面の外かを調べるところで位置を値ごとに分けます。口より左では、書くのは左端（`x = 0`）だけで、そのとき書くのはもとと同じ位置です。ですから `edgeE` はなくなりました。

名前は [横の土管に入るフレームを本物のフレームで](c-7-3-SideEntryRule-ja.md) と、縦の土管の 2 つのページと同じです。`tr(j)` は、`fm(E − 1)` から入力 `pad(E)` で始まるフレーム `E` の、`j` 命令あとの機械です。`x₀` は右側が口に入る最初の `x`、`P₀ = 256·x₀` は口の左端です。`posP(m) = 256·(256·page(m) + x(m)) + 小数部(m)` です。

```
G_room                 1 フレーム全部 のガードに、画面の 5 バイト（スクロールの固定、左右の端の x とページ）を足したもの。始めに部屋の値でわかっていて、
                       行き先を知らない書き込みから守る。切る場所は h（roomG）
FrameStart, Clean      1 フレーム全部 のとおり。ガードは G_room（どちらもルーチンの番号によらない）
h                      移動の終わりの位置 のとおり: 頭がブロックに当たったときのルーチン
HypF(m)        :=  (pc(m) = PlayerSubs  →  px(m) < x₀)  ∧  (AtRead(m) → TilesOK(m))  ∧  pc(m) ≠ h

no_write_frame       :  frameCheck,  s(j + 1) = step(s(j)) (j ≤ n),  frame(s(j)) ≤ frame(s(0)) (j ≤ n),  FrameStart(s(0)),
                        (∀ j ≤ n,  Clean(s(j)) ∧ HypF(s(j)))                                 →  rt(s(n + 1)) ≠ e_s
entry_right_of_left  :  sideFrameCheck,  Enters(m, i),  FrameStart(m),
                        (∀ n,  WriteStep(n) → ∀ j ≤ n,  Clean(tr(j)) ∧ (AtRead(tr(j)) → TilesOK(tr(j))) ∧ pc(tr(j)) ≠ h)
                        →  ∃ n j,  WriteStep(n) ∧ j ≤ n ∧ pc(tr(j)) = PlayerSubs ∧ x₀ ≤ px(tr(j))
mouth_of_frame       :  同じ条件,  (∀ n j,  WriteStep(n) → j ≤ n → pc(tr(j)) = PlayerSubs → P = posP(tr(j)))   →  P₀ ≤ P
StartE     :=  FrameStart(fm(E − 1))                         （G_room で。画面のバイトも）
CleanE     :=  ∀ n,  WriteStep(n) → ∀ j ≤ n,  Clean(tr(j))     （G_room で）
TilesE     :=  ∀ n j,  WriteStep(n) → j ≤ n → AtRead(tr(j)) → TilesOK(tr(j))
HeadE      :=  ∀ j,  pc(tr(j)) ≠ h
InRoom     :=  TilesE ∧ StartE ∧ CleanE ∧ HeadE
RoomRun.mouth_of     :  Checks,  RoomRun,  InRoom                                                    →  P₀ ≤ P(E)
Route.Run.inRoom     :  部屋の確認,  Run                                                             →  InRoom
side_frame_check（非公開） :  sideFrameCheck(sy, m₀) = true（native_decide）
```

`sideFrameCheck` は `PlayerSubs ≠ 0` と、抽象機械の確認です。`Route.Run.inRoom` は [部屋のブロックの地図](c-7-12-RoomMap-ja.md) にあります。

ROM のない定理が使う公理は `propext`、`Classical.choice`、`Quot.sound` だけです。

Lean: `Theorems/SideFrame.lean`、`Theorems/RoomJoin.lean` の `RoomRun`、非公開の `Proof/SideFrame.lean`（`side_frame_check`）。

## しくみ

**抽象機械.** [1 フレーム全部](a-5-2-PipeWrites-ja.md) の抽象機械です。行き先を知らない書き込みと読みの手順があります（`Clean`）。始めにわかっているのは、ルーチンのバイト、ゲームのモードのバイト、画面の 5 バイト、`PPUCTRL` のビット 7、スタックポインタです。画面のバイトは ROM から見つけます（スクロールのルーチンと画面外のビットのルーチンの読み込み）。値は部屋の参照の機械のものです。部屋ではスクロールが固定されているので、スクロールのルーチンは画面を動かしません。

**分けるところ.** どれも機械を変えません。

* 移動の終わりで、`px < x₀` の仮定のもとに: ページは 0 で、`x` は `[0, x₀)` のいくつかの片のどれかに入ります。`x₀` の 1 のビットごとに片が 1 つあります。そのビットより上は `x₀` のとおり、そのビットは 0、下のビットはわかりません。`x₀` の 1 のビットは 4 つなので、片は 4 つです。`posCover` が 256 バイト全部を確かめます。
* ブロックバッファのルーチンが `x` を足すところで、横の判定のとき: `x` を、わかっているビットに合う値ごとに分けます。仮定はいりません。
* 高さと足す数の和をマスクするところで、横の判定のとき: `A` の上の 4 ビットで分けます（16 個、仮定はいりません）。すると読む行がわかります。ですから `RowOK` はいりません。
* 読むところで、横の判定のとき: 読む場所がわかっています。それがブロックバッファの中で土管の列でなければ、`TilesOK` から [横の土管に入るフレームを本物のフレームで](c-7-3-SideEntryRule-ja.md) の 8 個の片が出ます。そのバイトはどちらのタイルでもありません。
* 横の判定かどうかは、ルーチンが保存する番号でわかります。足し算の番号の値は 3 つあります。大きいマリオ、水の中の大きいマリオ、小さいかしゃがんだマリオです。`Start` の 2 つだけにすると、抽象機械は 94,639 回失敗します。水の番号での読みです。
* スクロールのルーチンが画面外のビットのルーチンを呼ぶところで: `x` を値ごとに分けます（仮定はいりません）。抽象機械の足し算は、両方の数がわかるときだけ和がわかるので、ここで位置は丸ごとわかっていないといけません。するとそのルーチンと端の書き込みをそのまま追えます。画面が最初のページにあるので、口より左で画面の外（左）になるのは `x = 0` だけで、書くのは左端の 0、ページ 0、つまり同じ位置です。`x < x₀` で右の外になるものはありません。
* `h` は切ります。[部屋のブロックの地図](c-7-12-RoomMap-ja.md) の抽象機械が、部屋のどのフレームもそこに来ないことを示します。`SiteOK` では、頭の読みは何もないかコインしか出さないからです。

**確かめること.** どの道でも、ルーチンのバイトは横の土管のものではありません。`ChkPBtm` の比較が見るバイトはどちらのタイルでもないので、書き込み `w` に来る道はありません。

**探索（証明の一部ではない）.** 移動の終わりから横の判定まで、位置の片を覚えています。スクロールのルーチンから戻るところと、読む列がわかったあとで、位置をその片に戻します。だから `x` の値だけが違う状態はまとまります。画面外のビットのルーチンで位置が丸ごとわかっている間は、レジスタもキーに入れます。そのルーチンはループで、2 回の通過をまとめると結果を忘れるからです。横の判定の始めでは、位置と `Clean` のバイトのほかは忘れます。

**大きさ.** 7,523,911 歩、分かれ 805,523、失敗 0、表 249,435。プログラムで探索が約 17 秒、確認が約 26 秒です。`w_edge` を前のように切ると 7,109,418 歩、表 233,700 でした。画面のバイトを知らないか、画面外かを調べるところで位置が片のままだと、抽象機械は書き込みに来ます（失敗 199,006 回）。位置を 195 個の値に 1 つずつ分けた最初の抽象機械は、43,422,222 歩、表 2,810,791 個（17 GB）で、大きすぎました。

## 本物のフレームで確かめたこと

プログラム（`side-frame-check`）です。走りは [横の土管に入るフレームを本物のフレームで](c-7-3-SideEntryRule-ja.md) の `side-rule-check` と同じです。

| 走り | フレーム | 操作できる | 命令 | 読み | 入る |
|---|---|---|---|---|---|
| TAS の部屋（最初の操作から入ったあと 3 フレームまで） | 113 | 111 | 431,592 | 728 | 1 |
| TAS の部屋のフレームから、右に寄せた乱数の入力（200 回） | 45,123 | 45,123 | 174,974,667 | 309,608 | 67 |
| 入る 12、8、5、3 フレーム前から、左、右、A、B のすべての入力を 5 フレーム | 11,072 | 11,072 | 43,110,571 | 76,496 | 352 |
| 口の近くで、高さ、位置、状態、向きごとに 1 フレーム（書きかえ） | 38,400 | 38,400 | 144,438,759 | 191,144 | 1,295 |

* どの行でも、操作できるフレームは全部 `G_room` で `FrameStart` を満たし（画面の 5 バイトは部屋の値）、その命令は全部 `G_room` で `Clean` を満たし、ブロックバッファのルーチンの読みは全部 `TilesOK` を満たします。`w_edge` にも `h` にも来る操作中のフレームはありません。いまは抽象機械が `w_edge` を追い、`h` は証明しています（`HeadE`）。
* プログラムは約 2 分です。
* 入る 1,715 回は全部 `w` で書きます。どれも書き込みの前に移動の終わりに 1 回だけ来ます。そこでの位置は 195〜216 px で、`x₀`（195）より左はありません。それはフレームの終わりの位置で（`movedE` は `read_P` と合う）、横の判定がページを読むどの時の位置とも同じです。

## `RoomRun` の欄

* なくなった: `pass`、`pos`（と `tiles`。[部屋のブロックの地図](c-7-12-RoomMap-ja.md) を見てください）。`Checks.sideRule` は `Checks.sideFrame` になりました。そのあと `edgeE`（書き込みまでに `w_edge` にも `h` にも来ない）もなくなりました。`w_edge` は抽象機械が追い、`h` は `HeadE` です。
* 残る: `movedE`（`P(E)` は書き込みより前の移動の終わりの `posP`）。フレーム `E` だけのことです。
* 欄でないもの: `StartE`、`CleanE`、`TilesE`、`HeadE`。`Route.Run.inRoom` が、部屋のフレームの抽象機械と定理 `Route.Run.roomEnter` から証明します。

## 仮定（Lean で証明していない）

* **`movedE`.** `P(E)` は移動の終わりの位置です。`t0` までのフレームは `P(n)` をフレームの終わりで読みます（`read_P`）。フレーム `E` は `t0` よりあとで、まだ機械から読んでいません。本物のフレームでは 2 つは同じです（上）。
* **`Route.Run.roomEnter`**（項目 1-1-0-4、定理）: `RoomRun` のフレーム `E` は、部屋の中の `Route.Base` のフレームです。`StartE`、`CleanE`、`TilesE`、`HeadE` はこれと、部屋のフレームの `SiteOK`（`chg.roomSites`）の上に立ちます。
* **口の右端.** 出てくるのは左端だけです。`RoomJoin` は左端だけを使います。

**ファイル.** `Theorems/SideFrame.lean`、`Theorems/RoomJoin.lean`、非公開の `Proof/SideFrame.lean`。
