# CPU の 1 ステップが RAM を書く場所

**主張.** Lean の CPU の 1 ステップは、命令が書き込む番地と、スタックに積むバイトのほかは RAM を変えません。これはどの機械、どのオペコードでも証明しました。これを使うと、抽象機械の歩きは、状態が知らないバイトについての事実を運べます。その事実とは「音のバイトは表のどれかの状態にある」です。これは一般の 1 ステップと一般の 1 フレームとして証明しました。ゲームのデータは使いません。地上への切り替えに使うと、音のバイトを忘れる行は、出口のポーズの音の 52 種類で閉じました。ここではそれを測り、[次のページ](d-3-4-2-SideChangeSound-ja.md) で証明しました。`chg.quiet₂`（1-1-d-3-4）は弱くなりました。`chg.noStart₂`（1-1-d-3-3）は残ります。

`step(m)` は CPU の 1 ステップです。`m[i]` は `m` の RAM のバイト `i` です。`trace(m, inp, k)` は、`m` のフレームを入力 `inp` で `k` ステップ進めた機械です。`Sim(A, m)` は `TaintRun` の抽象状態 `A` が `m` を覆うことです。

## 命題

```
ramIdx(a)    :=  a < 0x2000 なら [a & 0x7FF]、そうでなければ []
stk(s, k)    :=  ramIdx(0x100 | s) ++ ramIdx(0x100 | (s − 1)) ++ … 、k バイト
stepLocs(m)  :=  NMI が待っていれば       stk(m.s, 3)
                 止まっていれば           []
                 それ以外                 locs(w(op), m₁)
locs(no, m₁)   := []
locs(md c, m₁) := ramIdx(c(m₁))              c(m₁) は命令のモードの番地
locs(st k, m₁) := stk(m₁.s, k)

step_ram   :  ∀ m i,  i ∉ stepLocs(m)  →  step(m)[i] = m[i]
trace_ram  :  (∀ k < n,  i ∉ stepLocs(trace(m, inp, k)))  →  trace(m, inp, n)[i] = m[i]
keep_step  :  Sim(A, m)  ∧  keepOK(E, P, A)  →  ∀ i ∈ P,  step(m)[i] = m[i]
keep_frame :  どの状態でも keepOK(E, P, ·) を満たす 1 フレームの歩き  →  ∀ i ∈ P,  frame(m, inp)[i] = m[i]
```

`op` はプログラムカウンタのオペコード、`m₁` はオペコードを読んだあとの機械です。`w(op)` は 256 個のオペコードの表の項目です。`no`（書かない）、`md c`（モード `c` を通るストアか読み書き命令）、`st k`（`k` 回積む。`PHA` と `PHP` は 1、`JSR` は 2、`BRK` は 3）。`keepOK(E, P, A)` は `A` についての検査です。NMI なら積む 3 バイトが `P` の外にあること、積む命令なら積むバイトが外にあること、ストアなら `TaintRun` の抽象モードが `A` で出す番地が外にあることです。

**抽象状態の外の音のバイト.** `SB` は RAM のバイトの列（音のバイト）です。表の状態は、バイトと、そのわかっているビットの列です。`SIn(t, m)` は `m` が状態 `t` にあることです。`spent` は抽象状態のビットで、`TaintRun` の数え `rk` がオフのときは何も読みません。ここでは、このフレームでルーチンが戻ったかどうかを表します。

```
Ph(A, m)  :=  A.pc はルーチンの中
           ∨  (A.spent = false  ∧  ∃ t ∈ T₀,  SIn(t, m))
           ∨  (A.spent = true   ∧  ∃ t ∈ T₁,  SIn(t, m))

s_tsuccs       :  Sim(A, m)  ∧  Ph(A, m)  →  ∃ B ∈ tsuccs(A),  Sim(B, step(m))  ∧  Ph(B, step(m))
tframe_of_walk :  S から tsuccs で歩く 1 フレーム、Sim(S, m)  ∧  Ph(S, m)
                  →  ∃ B,  Sim(B, frame(m, inp))  ∧  Ph(B, frame(m, inp))
```

`tsuccs` は歩きの 1 ステップです。

* `spent` が偽でルーチンを呼ぶところ: `A` と食い違わない `t ∈ T₀` ごとに 1 つの小片を作り、`t` のバイトを `A` に入れます。呼び出しはバイトを保たなければなりません（`keepOK`）。
* ルーチンの中: ふつうのステップです。戻るところで、状態のバイトは `T₁` のどれかの状態になければなりません。そのあとバイトを忘れ、`spent` を立てます。
* それ以外: ふつうのステップです。バイトを保つか（`keepOK`）、いくつかを書いても表が閉じています（`writeOK`: 表のどの状態も、書いたバイトを抽象機械が知るとおりにすると、表のどれかの状態に入る）。

Lean: `Theorems/StepWrites.lean`（`NoWr`、`WrIn`、`wRows`、`AllW`、`w_op`、`stepLocs`、`step_ram`、`trace_ram`、`keepOK`、`keep_step`、`kwalk`、`kframe_of_walk`、`keep_frame`、`Rt`、`SIn`、`aLocs`、`aLocs_ok`、`writeOK`、`tsuccs`、`Ph`、`s_tsuccs`、`twalk`、`tframe_of_walk`）。定理が使う公理は `propext`、`Classical.choice`、`Quot.sound` だけです。ファイルにゲームのデータはありません。

## しくみ

**1 ステップ.** `NoWr f` は `f` が RAM を変えないこと、`WrIn w f` は `f` が `w(m)` のほかで RAM を変えないことです。少しの決まった補題で組み立てます。`PipeTransitionAll` の葉は書きません。読み込みは書きません。`a` への書き込みは `ramIdx(a)` に書きます。積む命令はスタックポインタに書きます。命令の種類ごとに補題があり（`w_opSTA`、`w_rmw`、`w_opJSR` など）、表 `wRows` は `PipeTransitionAll` がその関係を証明するのと同じく、行ごとに証明します。NMI は 3 バイトを積みます。止まった機械は動きません。待ちの繰り返しは書きません。

**抽象の側.** 項目 `md c` は `TaintRun` の抽象モードも持ちます。`TaintRun` の補題 `s_mZp`、`s_mAbx` などは、抽象モードの区間が番地を含むことを言います。なので覆われた機械のステップは、区間が言うところにしか書きません。`aLocs` は、区間が 1 つの番地か RAM の外のとき、その番号を出します。

## 測ったこと（定理ではない）

プログラム: `sound-check exits`、`sound-check keeprows`、`sound-check trows`。

**横の土管の本物の出口.** 43 の入り方、それぞれ 20 回、土管のフレームで Start をでたらめに押し、半分は出口のあとでも押します（860 回）。

| 出口での（`PauseSoundQueue`、`PauseSoundBuffer`、`PauseModeFlag`、`Squ1_SfxLenCounter`） | 回数 |
|---|---|
| (0, 0, 0, 0): `Quiet` が成り立つ | 275 |
| (0, 2, 2, c)、c は 1 から 41: ポーズ解除の音が鳴っている | 565 |
| (2, 0, 1, 0): 出口のフレームでポーズ解除を押した | 20 |

`Kx` のほかの音のバイトは、860 の出口すべてで `T` の値でした。2 つ目の矩形波と三角波の曲のバイトと、2 つ目の矩形波の効果音の数えは、出口ごとに違います。これらは `ExitCond` で自由です。

**音のルーチンの外で音のバイトに書くところ.** 出口のあとの本物のフレームでは、RAM の消去（16 の音のバイトを 0 に）と `AreaMusicQueue`（2 か所）です。Start があると `PauseSoundQueue`（ポーズのルーチン）も書きます。行 `rows0` の歩き（866,701 状態、うち 126,587 が音のルーチンの中）で `keepOK` が成り立たないのは 7 か所だけです。上のものと、`EventMusicQueue`（2 か所）、`Square1SoundQueue`（1 か所）です。ほかの状態はすべて `keepOK` を満たします。

**本物の音の状態からの呼び出し.** 呼び出しの歩きは、出口のあとの呼び出しでの 5,254 の音の状態（出口のあと Start なし。380,056 ステップ、失敗なし）と、出口のあとも Start を押す 32,325 の状態（1,388,838 ステップ、失敗なし）のどれからも閉じます。1 回の呼び出しは 255 から 3,291 ドットです。

**音のバイトを忘れる行.** 始めの状態は、`endBase` の状態の 38 の音のバイトを忘れたものです。`T₀` は 52 の状態です。`Kx` のうち音のバイトは `T` の値、4 つのポーズのバイトは上の 43 種類のどれか（数 c は 1 から 42）、またはポーズのフラグが 0、またはフラグの 1 ビットが 1（8 状態）です。フレームごとに表を探索で作り（戻るところのバイトと、書き込みを合わせたもの）、それから `tsuccs` でフレームを探索します。

| 出口での種類 | 失敗 | 探索のステップ | いちばん大きい表 | 時間 |
|---|---|---|---|---|
| フラグ 0 とその 8 ビット（`rows0` と `rows1` が覆うもの） | 0 | 1,103,905 | 15 | 14 秒 |
| 52 種類すべて | 0 | 2,740,068 | 507 | 44 秒 |

122 の行は閉じ、`left` は毎行 1 ずつ減ります。これまで `rows0` と `rows1` は、フラグ 0 と 0 でないときに 682,944 + 691,797 ステップでした。戻るところの状態を種類ごとに合わせると、曲のヘッダを探す音楽のルーチンが 0 かもしれないバイトで回り、終わりません（行 3）。なので表はそれらを別々に持ちます。時間には表を作る探索も入っています。

## これで何が言えるか

* `quiet₂`（1-1-d-3-4）。次の回にしました。行を証明し、道筋は今、出口のポーズの音の種類（`QuietK`）を仮定します。[地上への切り替えを、音のバイトを表にして](d-3-4-2-SideChangeSound-ja.md) を見てください。そこでは 1 組の時間の行で 52 種類すべてに足り、表は確認が作ります。
* 種類は、まだ出口の仮定です。証明するには、土管のフレームにも同じ表が要ります。そこでは Start が許されるので、ポーズの音の状態を入るときから運ぶ必要があります。
* `noStart₂`（1-1-d-3-3）。表を使うと、曲の遅れは害になりません。出口のあとで Start を押す 32,325 の状態はすべて閉じます。しかし Start はゲームを止め、止まったフレームは `left` を 1 減らしません。行は `left` の値ごとに 1 つなので、止まった状態には、その場にとどまれる行が要ります。していません。
* `quiet₁`、`noStart₁`（1-1-b-3-7、1-1-b-3-6）。部屋への切り替えでも同じです。`Quiet` は土管のフレームで Start を押すと成り立たず、同じ表でポーズの音の種類に置きかえられます。その行は `ScreenStart` と `RoomMap` が読みます。していません。
