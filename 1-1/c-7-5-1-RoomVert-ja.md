# 部屋でのジャンプの最初のフレームは `vstep` のとおり

**主張.** 隠し部屋で、床からのジャンプの最初のフレームは、上下の状態を `vstep` のとおりに変えます。これは [部屋をつなぐ](c-5-RoomJoin-ja.md) のフィールド `vframes` の空中の部分でした（項目 1-1-c-7-5）。今は走りの本物の機械の上の定理です。使うのは 1 フレームか 1 つの機械の条件です。フレームが部屋の条件で始まり、各命令が `SiteOK` を満たすこと（どちらも [ブロックの地図](c-7-12-RoomMap-ja.md) がすでに使います）、フレームが `clean` のすでに与える状態でプレイヤーのルーチンに来ること、そしてフレームの始まりの機械の条件 2 つ、`halt` と `prevA` です。この 2 つも今は定理です（[ジャンプを止める値と前のフレームの A](c-7-5-2-RoomPair-ja.md)、項目 1-1-c-7-5-2）。移動の間にフレームが終わらないこと（`longer`）はもう求めません。`SiteOK` とプレイヤーのルーチンへの歩きから出ます（項目 1-1-c-7-1-1）。`vframes` の床のフレーム（立つか跳ぶ）は、フィールド `vfloor` として仮定に残ります。

これらのフレームについて、項目 1-1-c-7-11 も出ます。空中では移動のルーチンは覚えている速さを読みません。ですから上下の動きは横の動きに左右されません。読むのは跳ぶときだけです。[部屋でのジャンプの各フレーム](c-7-11-1-RoomFall-ja.md) はこれを、床からのジャンプの着地までの各フレームに広げます。

`V` は `vsOf` の読むバイトです。高さとその端数、上下の速さとその端数、2 つの力、ジャンプの始まりの高さ、状態、A と B です。`V⁺` は `V` に、前のフレームの A と B、ジャンプを止める値、大きさの変化、当たりのビット、縦のページ（項目 1-1-c-7-5-13 から）、横の 8 バイトを足したものです（`vKeepA`）。`R` はプレイヤーのルーチン、`Q` はスクロールの処理（`PlayerSubs`）です。`tr(j)` はフレームの `j` 命令目の機械、`end` はフレームの終わりの機械です。`rt` はルーチンのバイトです。「上昇中」は、状態が 1 か 2 で、上下の速さのビット 7 が 1 のことです。

```
before_R :  RoomCond(M),  各命令が SiteOK
            →  pc(tr(j)) = R  となる j はフレームに高々 1 つ,
               (∀ j' < j, pc(tr(j')) ≠ R)  →  V⁺(tr(j)) = V⁺(M),
               そして  pc(tr(j)) = R  →  frame(tr(j)) = frame(M)        (フレームは R で終わらない)
after_Q  :  RoomCond(M),  各命令が SiteOK
            →  pc(tr(j)) = Q  となる j はフレームに高々 1 つ,
               そして  pc(tr(j)) = Q,  上昇中(tr(j)),  rt(end) = rt_部屋  →  V(end) = V(tr(j))
vert_air :  vertAirOK,  AtV(R),  st(R) ∈ {1, 2},  (st(R) = 1 → DTHJ(R) = 1),  PrevA(R) & 80 = A_B(R) & 80
            →  ∃ k ≤ 728,  pc(stepN(k, R)) = Q  ∧  vs(stepN(k, R)) = vstepV(vs(R), A(R), 0)  ∧  InFrameN(R, k)
bridge_of:  bridgeOK,  u ∈ arcSet(h, 8)  →  st(u) ∈ {1, 2}  ∧  ∀ a,  vstepV(u, a, 0) = vstep_m0(u, a, 0)
air_frame:  上のもの,  pc(tr(n)) ≠ idle → dot(tr(n)) ≤ dotsPerFrame − 64
            →  vs(end) = vstepV(vs(M), A(R), 0)          (vstepV で上昇中のままで、rt(end) = rt_部屋 なら)
varc_of  :  OnArc(T, n),  n + 1 − (T + 1) ≤ 8,  n < t0,  n + 1 < E
            →  vs(n + 1) = vstep(vs(n), a(n + 1), 0)
```

`a(n)` は今は機械から読みます。フレーム `n` の終わりの上下の状態の A です（`Frames.a`。`vstep` は与えられた A をここに入れます）。前は自由なデータでした。

`vstepV` は機械 `vmach` の上の `vstep` です。ジャンプを止める値が 1 で、スタックポインタがプレイヤーのルーチンのものです。`RoomJoin` のジャンプは、レベルの始まりの機械の上の `vstep`（`vstep_m0`）を使います。そこでは止める値は 0 です。ルーチンが止める値を読むのは、ジャンプ中に A を離して上昇しているときだけです。ジャンプの始まりからどれだけ上にいるかと比べます。`bridgeOK` は、床からのジャンプの跳んでから 8 フレームまでの 1533 の状態で、A の両方の値について 2 つが同じになること、そこで状態が 1 か 2 であることを確かめます。

Lean: `Theorems/RoomVert.lean`（`walkV`、`frame_of_walkV`、`before_R`、`after_Q`、`piecesQ_class`、`piecesQ_cover`、`erase_keep`、`air_frame`、`air_arc`）、`Theorems/VertAir.lean`（`AtV`、`vert_air`、`arcSet`、`bridgeOK`、`bridge_of`）、`Theorems/RoomJoin.lean`（`RoomRun.varc_of`、`RoomCore.varc`、`arc_step`、`t0_lt_E`）、`Theorems/RoomMap.lean`（`cond_of_rows`）、`Theorems/Route.lean`（`Run.roomVert`、`Run.inRoom`）。非公開の `Proof/RoomVert.lean`。

## 方法

**1 フレーム全部の歩き 2 つ.** どちらも [ブロックの地図](c-7-12-RoomMap-ja.md) の歩きです。抽象機械は部屋のバイトと、すべての書き込みの行き先を知っています。どちらも状態に 1 ビット（`AS.spent`。カウンタを追わない間は何も読みません）と、リスト（`AS.log`）を持ちます。歩きは、1 ステップでそれらが変わらないことを確かめます。表の状態が状態を覆うのは、ビットとリストが同じときだけです。

* `walkA`: ビットは、フレームが `R` に来たことを表します。ビットの立った状態が `R` にあると、歩きは失敗します。ですからフレームが来るのは 1 回です。ビットが立つ前は、各ステップが `V⁺` を保つ必要があります（`StepWrites.keepOK`）。[StepWrites](d-3-4-1-StepWrites-ja.md) の 1 ステップの補題から、`R` より前のステップは `V⁺` に書きません。フレームの終わりの状態は `R` にあってはいけません（`finR`）。ですからフレームは終わる前に `R` に来ます。
* `walkB`: `Q` で状態を分けます。空中で上昇中の部分はビットを持ちます。ほかの部分（落下中、状態 0、3、3 より上）はリスト `[2]` を持ちます。ビットのある状態は、ステップで `V` を保つ必要があります。ただしコインを消す書き込みは別です。これはブロックバッファにしか書きません。`V` に書くかもしれないステップは、ビットを落とし、状態に `[1]` の印を付けます。フレームの終わりで `[1]` の状態は、ルーチンのバイトが分かっていて、部屋のものでない必要があります。これは時間切れです。マリオを倒すルーチンは上下の速さを書き、そのあとルーチンのバイトを書きます。ビットかリストのある状態が `Q` にあると、歩きは失敗します。ですからフレームが `Q` に来るのは 1 回です。

2 つの歩きの証明は 1 つの補題です（`frame_of_walkV`）。`j` 命令目の機械についての事実 `Φ(j, ビット, リスト)` を、覆う部分の各ステップが保つなら、それはすべての命令とフレームの終わりで成り立ちます。

| 歩き | 探索のステップ | 表 | プログラムでの確認 |
|---|---|---|---|
| `walkA` | 468,180 | 22,016 | 6.9 秒（探索込み） |
| `walkB` | 443,657 | 19,547 | 5.9 秒（探索込み） |

`walkB` の最初の試みは、時間切れでマリオを倒すルーチンの上下の速さの書き込みで失敗しました。ビットを落とせるのはそのためです。

項目 1-1-c-7-1-2 から、`walkA` は `R` で `cutOK`（スタック、NMI、ルーチンのバイト、エリアの種類、ジャンプ台、泳ぎのフラグ）も求め、`R` までさらに 2 つのバイト（大きさの変化と当たりのビット）を保ち、NMI がモードのルーチンを呼ぶ前に一時停止のバイトを読むところで、その下のビットで状態を分けます。探索は 468,184 ステップ（4 増えた）、検査はプログラムで 6.2 秒です（[部屋のフレーム: プレイヤーのルーチンでの状態](c-7-1-2-RoomCut-ja.md)）。

**空中の移動のルーチン.** `VertModel.vert_model` は本物のルーチンと、本物の覚えている速さの `vstep` を結びます。条件は `AtCtrl0` で、覚えている速さが `|v|` であることを含みます。部屋の本物のフレームでは、当たったあとそれが成り立ちません。測った空中で上昇中の 25,114 フレームのうち 1,800 です（下）。`vert_model` の歩きはそれを使いません。`vert_air` は `vert_model` を 2 か所変えたものです。条件は `AtV`（覚えている速さのない `AtCtrl0`）で、`vstep` の機械の覚えている速さは 0、本物のものは分からないとします（`vTagsA`）。状態 1 か 2 では、ルーチンが覚えている速さを読むのは `X_Physics` だけで、これは歩きの寄り道です。ですから空中の 16 の場合が通ります（`vertAirOK`、0.4 秒）。

**フレーム.** 最初に `R` に来たところで `before_R` です。これはフレームの終わりより前です（歩きのフレームの終わりの状態は `R` にありません）。そこで `vert_air`、`FrameModel.trace_inFrame` でその機械をフレームの `k + kk` 命令目に置きます。ルーチンの各ステップは、フレームの終わりより 64 ドット以上前に走るならフレームを保ち（`InFrameN`）、`SiteOK` は 6000 を与えるからです。そこから終わりまで `after_Q` です。

**`RoomJoin` では.** フィールド `vframes` は 2 種類のフレームで使われていました。床のフレームは `vfloor` として残りましたが、これも今は定理です（`RoomRun.vfloor_of`、項目 1-1-c-7-5-14）。ジャンプの最初の 8 フレーム（`OnArc`）のフレームは `RoomCore.varc` です。`RoomRun.varc_of` がこれを、`InRoom.vert`（上のフレーム）、`read_vs`、`clean`（到着での状態 `AtV`）、`InRoom.pair`（`halt`、`prevA`）、ジャンプの弧から証明します。`InRoom.vert` はフレームがプレイヤーのルーチンで終わることを求めるので、`n + 1 < E` について述べます。そのために `low_by` とその上の補題は `t0 < E` を取るようになりました（`t0_lt_E`。かたまりからの離れ方と、新しい数の事実 `vf` から）。これらのフレームの入力 `AirIn` は、今はフィールド `air_in` から出ます。

## 本物のフレームで確かめたこと

プログラム `room-vert-check FM2 [N]`。部屋の各フレームを、最初の操作から命令ごとに走らせます。ムービーと、4 種類の自分の入力のそれぞれ `N` 回（120 フレームまで）です。

| 走り | フレーム | `R` より前に `V⁺` に書いた | `Q` で上昇中（終わりまでに `V` が変わり、プレイヤーのルーチンで終わる） | `vstep` で空中で上昇中（操作のときの機械の `vstep` でない） | `halt` が成り立たない | `prevA` が成り立たない | `C + 49` より前の床のフレーム（立つでも跳ぶでもない） |
|---|---|---|---|---|---|---|---|
| ムービー、最初の操作から入るまで | 111 | 0 | 36 (0) | 33 (0) | 0 | 0 | 1 (0) |
| でたらめ（200 回） | 24,000 | 0 | 7,505 (0) | 6,718 (0) | 0 | 0 | 573 (0) |
| B と右（200 回） | 24,000 | 0 | 6,427 (0) | 5,696 (0) | 0 | 0 | 968 (0) |
| B と左（200 回） | 24,000 | 0 | 6,641 (0) | 5,909 (0) | 0 | 0 | 1,117 (0) |
| 壁（200 回） | 24,000 | 0 | 7,519 (0) | 6,758 (0) | 0 | 0 | 667 (0) |

空中で上昇中の 25,114 フレームのうち 1,800 で、プレイヤーのルーチンでの覚えている速さは `|v|` ではありませんでした。そこで `vert_model` の条件は成り立たず、`vert_air` はそれを求めません。ROM の確認は真です。`checkA` 8.0 秒、`checkB` 7.5 秒、`vertAirOK` 0.1 秒、`bridgeOK` 0.2 秒です（歩きはそれぞれ探索込み）。

## 仮定（Lean で証明していないこと）

* `vfloor`（1 フレーム。今は項目 1-1-c-7-5-14 で証明）: `C + 34` から `C + 49` までのフレームで床から始まるものは、`VFrame` のとおり、入力とともに立つか跳びます。床のフレームでの前の `vframes` です。
* `halt` と `prevA` はもう仮定ではありません。[ジャンプを止める値と前のフレームの A](c-7-5-2-RoomPair-ja.md) が証明します。
* 部屋のフレームの各命令の `SiteOK`。[ブロックの地図](c-7-12-RoomMap-ja.md) と同じです。
* 項目 1-1-c-7-5 のほかのフィールド（`air_in`、`stand_wall`、`fall_long`、`stand_row`、`vfall`、`floor_at`、`low_at`）には、ここでは触れていません。

`walkA` は今は横の 8 バイトも保ち、フレームの終わりの状態は `R` にありません。これで `Clean.before` と、フレームの終わりより前の到着が出ます（[部屋のフレーム: `before`、`longer`、`far` の半分](c-7-1-1-FrameTime-ja.md)）。
