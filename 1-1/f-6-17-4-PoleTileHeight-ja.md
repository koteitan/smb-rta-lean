# 触るときの旗のタイル: 横の判定の高さを、当たり判定のルーチン自身の確認から

`PoleJoin.Run` のフィールド `ySide` をなくしました。これは、ルーチンの書き込みまで、横の判定の始まりごとに、高さが当たり判定のルーチン自身の高さの確認の境より下であることを求めていました。いまは触るフレームの歩きが、その確認から横の判定まで高さを覚えています。代わりに `posKeep` や `keep.cleanE` と同じ種類のフィールドがあります。一つの命令の条件です。

## 新しいフィールド

`y` は彼の高さ、`yI` はその RAM の場所とします。機械が*当たり判定のルーチンの中にある*（`InZone`）とは、スタックポインタがルーチンの足の判定のときの値以下で、スタックのそこにルーチンの戻り先があることです（歩きの `PipeWrites.inZone` と同じ）。`m` の命令について、`t` は添え字かポインタを通した書き込みの行き先（`wTarget`）です。

* `yKeep`（`YAt`）: 書き込みまで、`m` が当たり判定のルーチンの中にあり、命令が添え字かポインタを通した書き込みで `t < 0x2000` なら、`t mod 2048 ≠ yI`。

言いかえると、当たり判定のルーチンの中では、添え字やポインタを通して高さを書く命令はありません。彼自身の縦の移動は添え字を通して高さを書きます（重力のルーチンの `X = 0` の `STA zp,X`）が、それは当たり判定のルーチンより前です。

## 証明したこと

定理 `no_write_frameH`（ファイル `Theorems/PoleTileHeight.lean`）は、`PoleTileRead.no_write_frameU` の `YSide` を `YAt` に変えたものです。

```
frameCheckH ∧ FrameStart(s₀) ∧ ColMap(s₀) ∧ (∀ j ≤ n, s_j で CleanK ∧ PosAt ∧ YAt ∧ HypR ∧ BufAt ∧ TileFar)
  ⇒ rt(s_{n+1}) ≠ 旗のルーチン
```

歩きは `PoleTileRead` の歩きに次の変更を加えたものです（`walkH`）。

* **当たり判定のルーチンの中では、ガードが高さを守る**（`GY`）: `PoleFrame.Pole.GP`（位置の画素とページを守る）に `yI` を加えたものです。歩きが知らない添え字での書き込みで、歩きはガードが守らないバイトを全部忘れます。ルーチンの中では、いまは高さを覚えています。ルーチンの外では、ガードは前と同じ `GP` です。だから一歩（`kstepH`）は、移動のルーチンの位置の書き込みでは `PoleFrame.kstepT` の一歩、ルーチンの中では `GY` での `FrameKeep.kstep`、ほかでは `GP` でのものです。ルーチンの中にある歩きの状態が覆うのは、ルーチンの中にある機械だけです（`inZone_of`）。そこで `GY` の `CleanK` が `CleanK`、`PosAt`、`YAt` から出ます（`cleanK_GY`）。`s_kstepH` が一歩の補題です。
* **当たり判定のルーチンの最初の高さの読み**（`HP.band`、`PoleTileRead.bandAt`）で、ページが旗のページかその一つ前でありうるとき: 高さを、上のビットが分かっている 5 個のかけらに分けます。かけらは `0 ≤ y < 256` のすべての値を持ちます（`bandPieces`、切れ目は `hiR` = 208 px、境を行の 16 px に切り上げたもの）。仮定はいりません。かけらはどのバイトも覆います（`coverN`、`cov_splitP`）。続くルーチンの比較で、208 px 以上の二つのかけらは戻ります。
* **横の判定の始まり**で、旗の近くなら: 歩きは、高さのかけらの最大値が `hiR` より下であることを確かめます。確かめが通れば、高さを `PoleTileRead` の 7 個のかけら（`yPieces`）に分けます。これは `[0, hiR)` を覆います。覆うのに要るのは `y ≤ maxv < hiR` だけです（`cov_zoneH`）。確かめが通らなければ何も分けず、読みの確認（`readP`）が失敗します。
* 高さに `ADC abs,Y` で足す二つのところ（ブロックバッファのルーチンのものと、頭のルーチンのもの、`HP.wk`）では、旗の近くの横の判定の足し算でないとき、上の 4 ビットだけ分かっているアキュムレータを忘れます。これがないと、表のバイトに下のビットがあるとき、歩きの特別な足し算（`PipeWrites.aadcH`）が失敗します。バイトを忘れることはいつでも覆うことになります。

だから `YSide` は仮定していません。当たり判定のルーチンの確認から横の判定までのどの道でも、歩きは高さのかけらを知っています。読みの直後の `TileRead` は前と同じく `PoleTileRead.tileRead_afterU` から出ます。

確認 `poleCheckH`（`PoleFrame` の歩きの前の確認、かけらが覆うこと、この歩き、読みの ROM の事実、`SubsOnce` の確認、`PoleTileWalk` のフレームの歩き）はネイティブに証明しました（非公開の `Proof/PoleTiles.lean` の `pole_check_h`。`pole_check_u` の代わり）。`touch_right_of_leftH` と `inRange_of_frameH` は、`PoleTileRead` の定理を `YAt` で述べたものです。`PoleJoin.Run.inRange` はフィールド `yKeep` で `inRange_of_frameH` を使います。

表を探すときは、旗の近くの横の判定の始まりで高さのかけらを覚えます（`normH`）。ほかは `PoleTileRead` と同じです。これは探し方の選び方だけです。歩きがすべての状態を確かめます。

## 測ったこと

歩きの探索（`pole-height-search`）: 8,196,666 歩、表の状態 376,976、失敗 0、ネイティブで約 41 秒（`PoleTileRead` の歩きは 7,681,437 歩、345,444 状態）。確認 `poleCheckH` 全体はネイティブで約 106〜113 秒で真です（`pole-height-search`: 探索 43 秒、確認 106 秒）。

**歩きの中で偽だったもの:** 最初の探索は、ブロックバッファのルーチンの高さへの足し算で 15 回失敗し、それを直すと頭のルーチンの高さへの足し算で 810 回失敗しました。そこではアキュムレータが、上の 4 ビットが分かっている高さのかけらを持っていたので、歩きは特別な足し算（`PipeWrites.aadcH`）を使いました。これは表のバイトに下のビットがあると失敗します。この二つの足し算（`HP.wk`）でそのアキュムレータを忘れると、失敗は 0 になりました。

`YAt` は、15 回の触りの書き込みまでだけでなく、すべてのフレームのすべての命令で成り立ちました（bad 0）。`N = 400`（Start なし 200 回、Start あり 200 回、最初の操作からの 1,300 フレームを 100 回）でも、191,042 フレーム、682,242,273 命令（そのうち当たり判定のルーチンの中 58,789,122）、81 回の触りで書き込みまで 240,912 命令、失敗は 0 でした。横の判定の始まり 29,648 回で、高さはいつも境（207 px）より下でした。最大は 176 px です。

**本物のフレームで偽だったもの:** フィールドの最初の形は「添え字かポインタを通して高さを書くのは、重力のルーチンの添え字 0 の書き込みだけ」でした。これはどの触りでも書き込みまでは成り立ちましたが、ほかのフレームの 12 の命令で偽でした。どれも同じ一つの書き込みで、エリアを用意するときに RAM を消すルーチンの、ポインタを通した書き込みです（TAS では最初の操作のあとのフレーム 418 と 732: 二つのエリアの切り替え。残りの 10 回は最初の操作からの乱数の実行の中）。この書き込みは当たり判定のルーチンの外なので、いまの形はそこでも成り立ちます。どちらの形も `keep.cleanE` のガードには入れられません。操作中のどのフレームでも、重力のルーチンが添え字を通して高さを書くからです。

## 証明していないこと

* `yKeep` そのもの: 当たり判定のルーチンの中で、添え字かポインタを通して高さを書く命令がないこと。測ったすべてのフレームのすべての命令で成り立ちました（上）。
* `tilesFar`: 旗のページの二つ以上前にいる間に旗の列が描かれない理由には、フレームをまたぐ画面のスクロールとエリアの解析が要ります。旗のページの二つ前のページで、そのページの旗の列を読むと、ブロックバッファの旗の列と同じバイトを読みます。だから地図 `ColMap` だけでは決まりません。TAS と 48 回の乱数の実行（5,331 フレーム）で測ったこと: エリアの解析の列は、画面の左端から最大 384 px（1.5 画面）右です。ブロックバッファに旗のタイルがあるのは、解析の列が旗の列まで来たあとだけです。旗の近くでは、彼は画面の左端から少なくとも 56 px 右にいます。旗のページの二つ前で横の読みが旗の列に届くのは、彼がそこから 32 px 以内にいるときだけです。そのとき、彼が画面の左端より右にいれば、解析の列は旗の列まで少なくとも 96 px 足りません。だから `tilesFar` は、フレームをまたぐこの三つの事実から出るはずです。それには画面の端と解析の列のバイトの記号と、それらを保つフレームの歩きが要ります。
* `bufAll` は変わりません。操作の始まりからのフレームの歩き（表 46,576 状態）で測ったこと: 76 か所で、歩きはその一歩がブロックバッファのバイトを書かないことを示せません。どれも添え字かポインタを通した `A` の書き込み（`STA abs,X`、`STA abs,Y`、`STA (zp),Y`）です。物の番号のバイトも守ると 75 か所が残ります。触るフレームの歩きでも同じく 76 と 75 です。だからそのバイトを守っても、これらの添え字の範囲は決まりません。

**ファイル:** `Theorems/PoleTileHeight.lean`。非公開の `Proof/PoleTiles.lean`（`pole_check_u` の代わりに `pole_check_h`: `poleCheckH` は探索も含めてネイティブで約 106〜113 秒。ファイル全体は、ほかの場所も機械で構築していた最後の全体の構築で 196 秒、最大 3.1 GB。この歩きの最初の版は、すいた機械で 127 秒。`pole_check_u` は 104〜123 秒）。プログラム `pole-height-search`（探索と確認）と `pole-height-check FM2 [N]`（上の本物のフレーム）。
