# 低いフレームごとの上限

[地下の部屋をつなぐ](c-5-RoomJoin-ja.md) のフィールド `low_at` は、`C + 37` から `C + 43` までで、角かその先で、136 から 151 ピクセルで終わり、1 つ前のフレームも角かその先にあるジャンプのフレームに残っていました（[角より左のフレームのあとの、152 ピクセルより上のフレーム](c-7-5-19-BandStart-ja.md)）。測った走りでは、そのようなフレームは 8 個でした（大きなプレイヤーで 7 個、小さなプレイヤーで 1 個）。

このページも、その高さでの当たり判定は証明しません。`low_by` に、すべてのフレームに 1 つの上限ではなく、フレームごとの上限を与えます。低いフレームのあとの止まりの数は、1 フレーム後ろになるごとにちょうど最高速で 1 フレーム分減ります。なので後のフレームは、最高速で 1 フレーム分だけ右にあってかまいません。これで、フィールドが求めるのは `runF`（`C + 40`）より後だけで、しかも `C + 40` からのすべてのフレームが角かその先にあるときだけになります。測った 8 個のフレームは、どれもこれに当たりません。どれも `C + 41` で角より左のフレームがあります。

## 主張

`P(n)`、`y(n)` は、フレーム `n` の終わりの位置（1/256 ピクセル単位）と高さです。`c_P` は角（51 ピクセル）、`G_P` はゴール、`S_low = 415/256` ピクセル、`top` は最高速です。1 フレームで動くのは多くて `16·top = 640/256` ピクセル（2.5 ピクセル、`move_top`）。`cy = cornerY`（136 ピクセル）。`hitF = 37`、`runF = 40`、`fall + 1 + rise = 43`、`goalF = 98`。

```
lowB(j) =  c_P − 1 + 16·top·(j − (hitF − 1))   j ≤ runF のとき      （j − 36）
           c_P − 1 + 16·top·(j − runF)          j > runF のとき      （j − 40）

low_by（証明。前は  P(n) ≤ c_P + 16·top − 1）:
  C ≤ n ≤ C + 43 → n ≤ t₀ → P(n) ≤ lowB(n − C)

low_at（フィールド、狭めた）:
  NoWall → C + runF + 1 ≤ n ≤ C + 43 → n ≤ t₀ → cy ≤ y(n) < cy + 16 → ¬OnFloor(n) → c_P ≤ P(n)
    → (∀ k, C + runF ≤ k < n → c_P ≤ P(k))                 （前は  c_P ≤ P(n − 1) で、n は C + hitF から）
    → P(n) ≤ c_P − 1 + 16·top·(n − (C + runF))             （前は  P(n) ≤ c_P + 16·top − 1）

NumFacts（ROM の数、room_nums の中で native_decide。どれも前は c_P + 16·top − 1 での 1 つの不等式）:
  hit_J:     ∀ j, hitF ≤ j ≤ runF:        lowB(j) + dbound(stopPhi, goalF − j) < G_P
  hit_F:     ∀ j, runF < j ≤ 43:          lowB(j) + fastDist(stopPhi, goalF − j) < G_P
  hit_late:  ∀ j, 43 < j ≤ goalF:  min(lowB(43) + 16·top·(j − 43), c_P + stopSlack) + fastDist(stopPhi, goalF − j) < G_P
```

新しいフィールドは前のフィールドから出ます。求めるフレームは少なく、そこで求めることも少ないからです。

`low_by` が上限を得るしかた:

- `n < C + hitF`: 角より左です（`corner_late`）。
- `n ≤ C + runF`: 角より左の `C + hitF − 1` から、1 フレームごとに最高速で 1 フレーム分（`move_top`）。フィールドは使わず、壁の条件も要りません。
- `n > C + runF` で、`C + runF` から `n − 1` までに角より左のフレーム `k` があるとき: `k` から同じように。
- そうでなく、壁に触らないとき: 床の上で終わるフレームと、152 ピクセルかそれより下で終わるジャンプのフレームは `LowAt` です（`low_floor_at`、`low_jump`）。なので `P ≤ c_P + S_low ≤ c_P + 16·top − 1 ≤ lowB`。136 から 151 ピクセルのフレームはフィールドです。
- 壁に触ったとき: 壁からのポテンシャルで、前と同じく `P ≤ c_P + 16·top − 1`。

これを使うのは `stop_short` だけです。`C + 43` までの最後の止まり `h`（`runF` までは `hit_J`、そのあとは `hit_F`）と、それより後の止まりの前の `C + 43`（`hit_late`）で読みます。`dbound` と `fastDist` は、止まりからの残りの走りのポテンシャルの上限です。`C + 36` から `C + 43` で、どちらも 1 フレーム後ろになるごとにちょうど `16·top` 減ります。なので `lowB` は 1 フレームごとに `16·top` 増えてかまいません。

`C + 98` での余裕（ゴールまで足りない分、1/256 ピクセル。評価して、`native_decide` で確かめた）:

| 確認 | フレーム | 余裕 |
|---|---|---|
| `hit_J` | 37 から 40 | どれも 1 |
| `hit_F` | 41 から 43 | どれも 17 |
| `hit_late` | 44 から 98 | 44 から 46 で 17、そのあと 400、1040、1680、… |

このラウンドの前は、どのフレームでも `c_P + 16·top − 1` で、同じ確認の余裕は 1、17、1297 以上でした。

## 測ったこと

`room-approach-check FM2 300 1`（大きい。最初の操作で大きさのバイトを大きいにした、作った状態）と `… 300 0`（小さい）: それぞれ TAS と自分の入力の 2,700 の走り。

| 大きさ | ラウンド 26 のフィールドのフレーム（136 から 151 ピクセルで、1 つ前のフレームが角かその先） | そのうち新しいフィールドのもの（`C + 40` からのすべてのフレームが角かその先） | 新しい上限を越えるもの |
|---|---|---|---|
| 大きい | 7 | 0 | 0 |
| 小さい | 1 | 0 | 0 |

8 個のフレームはどれも `C + 43` で、`P(C + 41) < c_P`（角より左に 16/256 から 288/256 ピクセル）です。

ジャンプの中で `C + 40` に角かその先にいる走り（12 個を表示）では、そのフレームは 152 ピクセルかそれより下で、速さ 0 で押し戻されて終わり、`C + 41` は角より左です（176/256 から 256/256 ピクセル）。新しいフィールドのフレームに向けた山登り（`room-big band FM2 3000 BIG`: `C + 35` と `C + 36` の跳びごとに自分の入力を 3,000 回変える、大きさごとに。B と右、そのあと A、B と右）は、1 つも見つけませんでした。いちばんよい点は −64 でした（`min(P(C + 40), P(C + 41)) − c_P − 64·max(0, y(C + 41) − 151)`）。

フィールドがなくならない理由。`C + 40` で角の先にいることがあります。壁に触らない走りでの `P(C + 40) − c_P` の最大は 80/256 ピクセルで、床の上でも、`C + 38` までに跳んだジャンプでもそうです。なので `C + 40` での上限だけではフィールドは空になりません。角かその先の `LowAt` のフレームのあと、1 フレームのまとめ（`TopSpeed.Frame`。`FrameModel.Collide` は、移動の終わりで速さが 0 以下なら、そこから 1 ピクセル右で終わることを許す）は、次のフレームを `c_P + S_low + 256`、つまり角から 671/256 ピクセルまでしか抑えません。これは `C + 41` で `hit_F` の余裕が許す 655 より 16/256 ピクセル多いです。この上限はここでの議論で、プロジェクトの定理ではありません。

## 残っていること

- `C + 40` からのすべてのフレームが角かその先にあるときの、`C + 41` から `C + 43` までで 136 から 151 ピクセルで終わるフレームの `low_at`（測ったフレームは 0 個）。その高さでのブロックの左側の当たり判定が要ります。移動の終わりでの大きさのバイト、コインか空のセル、そこでの `RoomCorner` の歩きです。

**ファイル。** `Theorems/RoomJoin.lean`: 新しい `lowB`、フレームごとの `NumFacts.hit_J`、`hit_F`、`hit_late`、`low_by` の結論、`stop_short`、`RoomFields.low_at` を狭めた。非公開: `room_nums`（`Proof/RoomJoin.lean`、文面は同じ）の `hit_J`、`hit_F`、`hit_late`。プログラム `room-approach-check`（上の数）。

**再現。**
```
.lake/build/bin/smbrta room-approach-check FM2 300 1      # 大きい。最後を 0 にすると小さい
.lake/build/bin/smbrta room-big band FM2 3000 1          # 山登り。最後を 0 にすると小さい
```
