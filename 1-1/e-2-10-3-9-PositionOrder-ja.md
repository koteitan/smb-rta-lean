# スクロールの処理からあとの呼び出しの順序

**主張.** 操作中のフレームを考えます。仮定は `PositionWriters.writers_end` のものです。q をスクロールの処理 Q の命令とします。機械 R でスクロールの処理の呼び出しが「開いている」（`Ph0(R)`）とは、スタックが Q でのスタック sQ より 2 バイト以上下にあり、スタックのページの 4 つのバイトが、その呼び出しと、それがいるルーチンの戻り先をまだ持っていることです（`phQ`）。このとき:

```
ph_down          : q < j ≤ n,  Ph0(T n)  →  Ph0(T j)
clamp_before_push: q ≤ a, q ≤ a',  pc(T a) = 補正の入口,  pc(T a') = 押し戻しの入口  →  a < a'
clamp_once       : q ≤ a < b' ≤ a₂,  pc(T a) = 補正の入口,  s(T b') = s(T a) + 2  →  pc(T a₂) ≠ 補正の入口
chain_order      : a ≥ q からフレームの終わりまでの切れ目の列で、補正の入口の切れ目は 1 つだけで、押し戻しの入口のどの切れ目より前にある
```

添字はどれもフレームの中です。言葉で言うと、画面端の補正はどれも、どの押し戻し（`ImpedePlayerMove`）より前に来ます。補正が戻ったあと（スタックがまた 2 バイト上がったあと）は補正は来ません。`PositionDispatch` の列では補正は多くて 1 つで、押し戻しはそのあとです。押し戻しの回数はここでは抑えていません。

**証明.** `PositionWriters` の歩きが、状態と 1 歩ごとに 3 つのことを足して求めます（`okW`、`walkKW`）。`Ph0` について歩きが知っていること（`phK`: 開いていると知っている、`phN`: 開いていないと知っている）を使います。

- 補正の入口では、呼び出しは開いていると知られていて、スタックは sQ の 2 バイト下です（`AtW.phC`）。
- 押し戻しの入口では、開いていないと知られています（`AtW.phI`）。
- 開いているかもしれない状態への 1 歩は、開いていると知られた状態か Q から来ます（`FrameW.ph`）。

非公開の確認がこれを ROM で証明します（`position_writers_check`、約 11 秒）。なので呼び出しが開いている機械は、q のすぐあとから続けて並びます（`ph_down`）。押し戻しの入口は開いておらず、q と補正の入口のあいだの機械はどれも開いているので、押し戻しはあとに来ます。補正はスタックを sQ に戻して終わり、そこでは呼び出しは開いていないので、あとの機械はどれも開いておらず、あとに補正は来ません。

**うまくいかなかった最初の試み.** 呼び出し自身の戻り先の 2 バイトだけでは、ROM での確認は偽でした。ネイティブの診断で、失敗した 1 歩は 2 つでした。ゲームのエンジンがプレイヤーのルーチンと同じ深さで呼ぶルーチンで、歩きが知らないバイトを 2 回積むと、スタックが sQ − 2 になります。そこで `Ph0` はその上の 2 バイトも求めます。プレイヤーのルーチンがいるルーチンの戻り先です（`callerRet`）。その 1 歩では歩きはこの 2 バイトを知っていて、1 つが違うので、呼び出しが開いていないと知り、確認は真になります。

**証明していないこと.** 1 フレームの押し戻しの回数（コードを読むと、当たり判定のルーチンは多くて 1 回呼びますが、足場のルーチンがもう一度呼べます。どちらも証明していません）と、補正先とフレームの始まりの関係（d ≤ 0）。`CollideS.P` と `AfterP.stop` はまだこれを要ります。ここではフィールドは変わりません。本物のフレームでは、2 回呼ぶフレームはありませんでした（[1-1-e-2-10-3-8](e-2-10-3-8-PositionKeep-ja.md)）。
