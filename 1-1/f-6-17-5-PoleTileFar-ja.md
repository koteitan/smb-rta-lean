# 触るときの旗のタイル: 旗から遠い読みはブロックバッファにある

`PoleJoin.Run` のフィールド `tilesFar` をなくしました。これは、ルーチンの書き込みまで、ページが旗のページより二つ以上前のときの横の判定の読みの直後ごとに、読んだバイトが旗のタイルでないことを求めていました。いまは触るフレームの歩きが、そういう読みが RAM の中とブロックバッファの中にあることを知っています。そしてフレームの始まりの地図（`ColMap`、定理）が、そこの旗のタイルは旗の列にあると言います。だから仮定として残るのは旗の列での読みだけです。新しいフィールド `tilesCol` で、同じ条件をより少ない読みに求めます。

## 新しいフィールド

`pg` は旗のページ、`page` は彼のページ、`save` はブロックバッファのルーチンのオフセットのバイト、`read` はルーチンのブロックバッファの読み（`LDA (zp),Y`）、`readAt(m)` はその読みの RAM の場所（ポインタに `Y` を足したもの、`PoleFrame.readAt`）とします。`onCol(i)` は、場所 `i` がブロックバッファの旗の列にあることです（`PoleEntryRule.onCol`）。

* `tilesCol`（`TileCol`）: 書き込みまで、`pc(m) = read + 2` で、`save(m)` が横の判定のオフセットで、`page(m) + 1 < pg` で、`onCol(readAt(m))` なら、`A(m)` は旗の玉でも棒でもない。

前のフィールド `tilesFar`（`PoleTileRead.TileFar`）は、これから `onCol(readAt(m))` を除いたものです。だから `TileFar(m) ⇒ TileCol(m)` です（`tileCol_of_far`）。

## 証明したこと

定理 `no_write_frameF`（ファイル `Theorems/PoleTileFar.lean`）は、`PoleTileHeight.no_write_frameH` の `TileFar` を `TileCol` に変えたものです。

```
frameCheckF ∧ FrameStart(s₀) ∧ ColMap(s₀) ∧ (∀ j ≤ n, s_j で CleanK ∧ PosAt ∧ YAt ∧ HypR ∧ BufAt ∧ TileCol)
  ⇒ rt(s_{n+1}) ≠ 旗のルーチン
```

歩きは `PoleTileHeight` の歩きに次の変更を加えたものです（`walkF`）。

* **旗から遠いときのページのビット。** ページが旗のページより二つ以上前の横の判定で、ブロックバッファのルーチンがページのいちばん下のビットをキャリーに移す直前（和の `ORA` の一つ前の命令、`parAt`）に、アキュムレータのそのビットを二つの値に分けます（`PipeChangeEnd.bitA 1`）。このビットがブロックバッファを選びます。すると歩きは、ポインタの上のバイトと、下のバイトの上の 4 ビットを知ります。ルーチンは列に下のビットのないバイトを足し、歩きの特別な足し算 `PipeWrites.aadcH` がそれをたどります。列そのものは歩きは知りませんし、知る必要もありません。
* **どのページでも高さを分ける。** `PoleTileHeight` が旗の近くでだけしていた分け方を、どのページでもします。当たり判定のルーチンの最初の高さの読み（すべての値を持つ 5 個のかけら）、横の判定の始まり（高さのかけらが 208 px より下だと確かめたあと、208 px より下の 7 個のかけら）、高さの足し算のアキュムレータ（ビットごと、`fullA`）です。
* **読みの確認**（`readPF`）を、どのページでもします: 読みのかけらから、オフセットが横の判定のものだと知っている読みの直後の状態への一歩では、読みで `Y` が分かっていて、ポインタの分かっているビットが許すどの番地もブロックバッファの中にあります: `bufLo ≤ readMin` と `readMax < bufLo + bufBytes ≤ 2048`。`readMin` と `readMax` は、ポインタの二つのバイトの分からないビットをそれぞれ 0 と 1 にしたものです（`AB.minv`、`AB.maxv`）。読みの番地は `lo + 256·hi + Y` なので（`SideChangeEnd.ptr_toNat`）、読みは RAM の中とブロックバッファの中にあります。

新しい分け方はどれも仮定のない覆いです（`cov_zoneTF`、`cov_zoneHF`、`cov_preF`）。読みの直後に歩きは `TileRead` を証明します（`tileRead_afterF`）。読みはブロックバッファの中にある（`readPF`）ので、読んだバイトが旗のタイルなら、地図から `onCol(readAt)` が出ます。ページが旗のページより二つ以上前なら、`TileCol` がそのバイトは旗のタイルでないと言います。だからページは旗のページの一つ前以降です。

確認 `poleCheckF`（`PoleFrame` の歩きの前の確認、かけらが覆うこと、この歩き、読みの ROM の事実、`SubsOnce` の確認、`PoleTileWalk` のフレームの歩き）はネイティブに証明しました（非公開の `Proof/PoleTiles.lean` の `pole_check_f`。`pole_check_h` の代わり）。`touch_right_of_leftF` と `inRange_of_frameF` は、`PoleTileHeight` の定理を `TileCol` で述べたものです。`PoleJoin.Run.inRange` はフィールド `tilesCol` で `inRange_of_frameF` を使います。

表を探すときは、どのページでも横の判定の始まりで高さのかけらを覚えます（`normF`）。また、読みの直後の状態は表に入れません（`isCutF`。歩きはそこで覆いません）。これは探し方の選び方だけです。歩きがすべての状態を確かめます。

## 測ったこと

歩きの探索（`pole-far-search`）: 9,680,248 歩、表の状態 434,249、失敗 0（`PoleTileHeight` の歩きは 8,196,666 歩、376,976 状態）。探索は負荷が約 4 のときネイティブで 45〜49 秒で、プログラム `pole-far-search` の最大は 2.97 GB です。確認 `poleCheckF` 全体は、その負荷でネイティブで 135 秒、負荷 7〜10 で 148 秒で真です。`poleCheckH` は 106〜113 秒、負荷 7〜10 で 126 秒でした。当たり判定のルーチンの中の横の判定の始まりでは、いつも高さのかけらが 208 px より下でした。読みの直後の状態への一歩は、いつも `readPF` を通りました。

**最初は大きすぎた:** 最初の形の歩きは、ポインタを正確に知るために、旗から遠いとき横の和を書くところで和の上の 4 ビットも分けていました。その探索は約 100 秒で 5.8 GB を超え、止めました。ポインタの列は要りません。ページのビットを分ければ、歩きはポインタの上のバイトと下のバイトの上の 4 ビットを知ります。二つ目の形は、読みで下のバイトを 16 個の値に分け、そこで正確な番地を求めました。その探索は 10,837,288 歩（表の状態 438,423、失敗 0）、確認全体は 189 秒で、同じ負荷で `poleCheckH` は 126 秒でした。いまの形は、読みで分けずに番地の範囲を求めます: 9,680,248 歩、表の状態 434,249、失敗 0 です。

## 証明していないこと

* `tilesCol` そのもの: 旗のページより二つ以上前の横の判定の読みの直後で、旗の列での読みなら、読んだバイトは旗のタイルではない。そういう読みは旗の列より約 512 px（2 ページ）以上前です。それは、地形を読むルーチンが旗の列を描くときに旗の列を持つことになるブロックバッファのバイトを読みます。なぜ地形を読むルーチンがまだそれを描いていないかには、フレームをまたいだ画面のスクロールと地形を読むルーチンが要ります（ページ `f-6-17-4-PoleTileHeight-ja.md` の測定: 地形を読むルーチンの列は画面の左端より多くても 384 px 右です）。
* `yKeep` はこの回では変わりません（第 25 回でなくなりました: [当たり判定のルーチンの中で高さを守る](f-6-17-6-PoleTileKeep-ja.md)）。この歩きで測りました（`pole-far-stores`）: 当たり判定のルーチンの中に、添え字かポインタを通した書き込みで、歩きが行き先を高さから外せないところが 20 あります。16 はブロックの物の `STA zp,X` と `STY zp,X` です（頭の突き上げとレンガ）。その添え字はブロックの物のオフセットで、歩きは知りません。ゲームはそのオフセットをいちばん下のビットを反転させることでしか変えませんが、それが 0 か 1 のままであることはフレームをまたぐ事実です（ここでは測っていません）。3 は、歩きが知らないポインタでのブロックバッファへの `STA (zp),Y` です（頭の突き上げと、コインを消す二つのところ）。1 は得点の `STA abs,Y` で、`Y` が分からないとき範囲が一回りして高さの場所にかかります。高さを横の判定自身の比較に任せることもできません。小さい彼かしゃがんだ彼では、上の横の読みは 24 px 足すので、216 px から 227 px の高さは 14 行目、つまりブロックバッファの先を読みます。当たり判定のルーチン自身の境（207 px）が要ります。
* `bufAll` は変わりません。操作からのフレームの歩きで測りました（`pole-far-stores`、表の状態 46,576）: 76 のところで、歩きは一歩がブロックバッファのバイトを書かないことを示せません。そのうち 38 では、書くバイトのビットを歩きが十分に知っていて、旗のタイルではないと言えます。残りの 38 は、ブロックバッファのすぐ下の物の表への 27 の `STA abs,X` と 9 の `STA abs,Y`（添え字のどのビットも歩きは知りません）、旗の列を描く地形を読むルーチンの `STA (zp),Y`、突き上げたブロックのタイルを戻すブロックの物の `STA (zp),Y` です。38 を証明しても `bufAll` の主張は小さくなりません。旗のタイルでないバイトの書き込みは、もともとそれを満たすからです。
