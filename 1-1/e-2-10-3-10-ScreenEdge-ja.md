# フレームの始めの画面の左端

このページは、本物のフレームで偽だったフィールド（第 23 回）と、その直し方（第 24 回、[下](#第-24-回-直し方)）を報告します。第 23 回はフィールドを 1 つ狭くもしました（`clampR`、下）。

## 第 24 回: 直し方

新しいフィールド `collide` とパート e のフレームは、押し戻しの上限をフレームの始めからではなく**基点**から測ります。`left(m)` は前と同じに読みます。

```
edge(m) = 256·left(m) + 255        端のピクセルの最後の位置（SurfaceRead.edgeOf）
base(m) = max(P(m), edge(m))        （SurfaceRead.baseOf）

collide（CollideS.P）の 3 番目 :  P(Q) ≤ P(b) ≤ base(M) + 256  ∧  v(Q) ≤ 0          （第 23 回: P(b) ≤ P(M) + 256）
edge （新しい、各フレーム 1 ≤ j < g） :  edge(seq j) ≤ max(base(seq (j − 1)), P(seq j))
edge₀（新しい、操作の始め）           :  edge(seq 0) ≤ P(seq 0)          （第 25 回: 定理、1-1-e-2-10-3-11）
wide つきの TopSpeed.Frame           :  impedeP の 3 番目 P′ ≤ B + 256 ∧ v₂ ≤ 0、B = base(seq (j − 1))
```

**何を足すか.** 新しい 3 番目の場合が前より弱いのは、ちょうど edge(M) > P(M) のフレームだけです。つまり彼が端のピクセルの上（その最後の位置ではない）か、それより左で始まるフレームです。そこでは P(b) を P(M) + 256 ではなく edge(M) + 256 まで許します。ほかのどのフレームでも前と同じ場合です。

**なぜ成り立つか（コードから読み、測った。証明していない）.** スクロールの処理で左へ動くか動かないとき、画面はスクロールしません。なので端は M の端です。補正は彼を端のピクセルに置き、端数を保ちます。なので補正のあと P ≤ edge(M) です。そのあとに来る押し戻しは多くて 1 回、1 px です（補正はどの押し戻しより前: [1-1-e-2-10-3-9](e-2-10-3-9-PositionOrder-ja.md)。1 フレームに押し戻し 2 回は測ったことがない）。なので P(b) ≤ max(P(Q), edge(M)) + 256 ≤ base(M) + 256 です。端は画面がスクロールするときだけ動き、画面は彼が画面の中央より右にいるときだけスクロールします。なので端は彼の後ろにとどまります: `edge`。操作の始めに彼は端より 56 px 右にいます: `edge₀`。

第 23 回の偽のフレーム（`edgeJump`、フレーム 190）で: P(b) = 730096、edge(M) = 256·2851 + 255 = 730111 なので P(b) ≤ base(M) + 256 = 730367 です。乱数の走り 188（補正のあと右への押し戻し）で: P(b) = 685984 ≤ 256·2678 + 255 + 256 = 686079 です。

**これで証明したこと.** max(P, B) は 1 フレームに前と同じ上限しか増えません（`TopSpeed.Frame.posB`、`Frame.advB`）。基点は続いていきます（`TopSpeed.ChainB`、`edge` から。`Surface.links`）。なので最初の当たりのあとのフレームの列で max(P, B) は多くても `reach` しか動きません（`SurfaceRun.chainB_reach`、`hit_boundB`）。最初の `N + E` フレームでは 1 フレーム多くても `16·top` です（`PoleJoin.early_leB`）。端は彼が前にいた位置の後ろにとどまります（`OnFrames.edge_behind`）。なので最初の当たりとその次のフレームはモデルの位置で抑えられます（`Surface.hit`、`Surface.base`）。位置の範囲も基点を使います（`OnFrames.readAllB`）。ルートの数は変わりません: 表も `farN` もパート e の数も変わらず、フレーム 233 での余りは前と同じ 16 です。

**列からの `edge₀`（測った。つないでいない）.** 非公開の機械での native のチェック（あとで消した一時ファイル）は、土管から出る変わり目の列（[1-1-d-2-3](d-2-3-SideChangeEnd-ja.md)）が、操作のあるどの状態でも端の 2 バイトを操作の始めの機械の値で知っていて、そこで edge ≤ P であることを示します。ルートは操作の始めの状態を音の表つきの列（[1-1-d-3-4-2](d-3-4-2-SideChangeSound-ja.md)、[1-1-d-3-4-3](d-3-4-3-SidePause-ja.md)）からほかのパートのファイルとチェックを通してとります。なので第 24 回は `edge₀` はフィールドのままでした。第 25 回にこれをつなぎました: `edge₀` は定理 `SurfaceFrames.edge_zero` です（[1-1-e-2-10-3-11](e-2-10-3-11-EdgeStart-ja.md)）。

## フレームの始めの関係は left(M) ≤ pixel(M) ではない

第 21 回は、どのフレームの始めでも left(M) ≤ pixel(M) と測りました。`clampR`、`Moves.stop`、`CollideS.P` の計画はこれを使いました。これは本物の走りで偽です。測ったフレームでは:

```
left(M) − 1 ≤ pixel(M) ≤ left(M) + 120
pixel(M) = left(M) − 1  →  v(M) = 0  ∧  衝突のビットの bit 0 が 0（右が塞がれている）
right(M) − left(M) = 255
```

**起こり方.** 彼は画面の左端に立ち、右に壁があります（ここでは階段の前の土管）。各フレームで、画面の端の補正が彼を端に置きます（+1 px）。次に衝突のルーチンが右側の壁を見つけ、押し戻し（`ImpedePlayerMove`）が彼を 1 px 左へ動かし、速さを 0 にし、右を塞ぎます。なのでフレームは端より 1 px 左で終わります。次のフレームも同じです。このようなフレームは clean に始まりません（衝突のビットが右を塞ぐ）。なので clean なフレームを見る `surface-frames-check` は、そこで `collide` を確かめません。

## 本物のフレームで偽のフィールド: `collide`

このようなフレームの次のフレームで、押し戻しが止まることがあります（ジャンプで土管の上へ出る）。そのフレームで左へ動き、位置の端数が 0 より下になると、Q は端より 2 px 左にあります。補正はその端数のまま彼を端へ戻します。`edge-real` の走り `edgeJump`（ムービーのフレーム 996 からの自分の入力。そのフレーム 190）では:

```
M : pixel 2850、left 2851、端数 0、v = 0
Q : P(Q) = P(M) − 16       （v(Q) = −1: pixel 2849、端数 240）
    補正があり、押し戻しはない（フレームは補正を呼ぶ: Calls）
b : P(b) = P(Q) + 512 = P(M) + 496、v(b) = 0
```

`CollideS.P` は、呼び出しがあり右への速さを保たないフレームで次を求めます。

```
P(b) = P(Q)  ∨  P(b) = P(Q) − 256  ∨  (P(Q) ≤ P(b) ≤ P(M) + 256  ∧  v(Q) ≤ 0)
```

ここでは P(b) − P(M) = 496 > 256 です。なので `OnFrames`（したがって `Route.Run`）のフィールド `collide` はこの本物のフレームで偽で、`route_1_1` はこの走りを含みません。この走りは最後まである走りです: そのあと右へ走り階段を跳んで上る自分の入力で、`route-check`（フレーム 996 までのムービー、そのあとこの入力）は、フレーム 1396 で旗に触り、フレーム 2063 で面が変わることを見つけ、ルートの数はすべて成り立ちます（終了コード 0）。上のフレームはフレーム 1187 で、触る前の数えるフレームです。触るのは操作から `farN` フレームより前（フレーム 852 から 544 フレーム）なので、ルートはこのフレームで `collide` を使います。`OnFrames.readE` が `collide` から作る `TopSpeed.Frame` の動き（`impedeP`: P' = P₂、P₂ − 256、または v₂ ≤ 0 で P' ≤ P + 256）もそこで偽です。遅いフレームの `Frame.adv_le` の上限（256）も偽です。

**もう 1 つの起こり方.** 乱数の走りは、同じ種類のフレームを別の起こり方でも見つけました: `edge-real 256` の乱数の走り 188（ムービーのフレーム 904 から）のフレーム 190 は、ジャンプのいちばん上で端より 1 px 左から始まり、端数は 176、v(Q) = −1 なので Q は端より 1 px 左です。補正が彼を端に置き、そのあと押し戻しが左側の壁を見つけて彼を 1 px 右へ動かします。やはり P(b) = P(Q) + 512 = P(M) + 496 です。ほぼ Left を押す乱数の走り（2 つめの組の走り 188）は 1 つめの起こり方を見つけました。

**成り立った上限.** 補正のあと P = 256·left + f(Q) です（f は端数）。このようなフレームでは P(M) = 256·(left − 1) + f(M) です。補正のあとの押し戻しは、どちら向きでもさらに 1 px 動かします。端より左で始まる測った 5,440 フレームでは P(b) − P(M) ≤ 496 で、そのフレームとその前のフレームを合わせて P は多くて 496（< 2·256）動きました。前のフレームは押し戻しのフレームで、彼を右へ動かしません。

## 部分 e のフィールドにとっての意味

- `clampR`: 端より 1 px 左で始まるフレームでは v(M) = 0 で、衝突のビットが右を塞ぎます。なのでそこで右を押しても右への速さは出ません（コードから読んだことで、証明はしていません）。`ClampR` は v > 0 のときだけ何か言います。`pos-keep-real` の走りと、5 つの終わり方の `edgePipe` で、v > 0 のどの補正でも `ClampR` は成り立ちました。第 23 回は、`PositionKeep.keep_frame` が使うところだけで求めます: スクロールの処理で右へ動き、その速さで終わるフレーム（[1-1-e-2-10-3-8](e-2-10-3-8-PositionKeep-ja.md)）。
- `Moves.stop` は clean なフレームだけで求めます。端より左で始まるフレームは clean ではありません。測ったどのフレームでも成り立ちました。
- `CollideS.P`（`collide`）は上のフレームで偽です。第 24 回に基点で直しました（[上](#第-24-回-直し方)）。P(b) ≤ P(M) + 512 では足りません: 当たりのあとの最初の 17 フレームで `reach` に 3,248 足し、当たりの表にはその余地がありません（256 でもフレーム 8 からの最初の当たりで表は成り立たない）。また 1 フレームで端数の借り、補正、右への押し戻しが重なると、コードは P(b) − P(M) を 752 まで許します。
- 指示書の計画（部分 e のフレームでの left(M) ≤ pixel(M) の帰納法）は、代わりに上の関係が要ります: left(M) − 1 ≤ pixel(M)。pixel(M) = left(M) − 1 は、端での左への押し戻しのあとだけです。

**証明していないこと（第 23 回）.** ここから下の節のことはすべて測ったことです。フレームの始めの関係、端より左で始まるフレームの上限、補正の規則（左端の補正は pixel ≤ left のときだけ来る）は証明していません。
