# 地上への切り替えの最後のフレーム

**主張.** これは部分的な結果です。出口の 1 つの状態についての条件を満たす機械は、次の 121 フレームのあいだ操作できません。入力は、ゲームコアのフレームで Start を押さないものなら何でもかまいません。切り替えのはじめのフレームと合わせると、仮定 `fallAfter` がなくなります。そのような入力の走りは、入ってから操作できるまで、数えるフレームで 282 以上かかります。切り替えのあいだ、ポーズで終わるフレームは `left` を減らしません。出口でゲームタイマーが 000 でなければ、音のポーズのフラグが何でも、入ってから最初に操作できるまで `left` は 0 になりません。

`m₀`、`run`、`ctl`、`0^k`、`E`、`T = run(E, 0^160)` は[地上への切り替えの長さを決めるもの](d-2-1-SideTransitionAll-ja.md)と同じです。`EntryCond`、`During`、`left`、`frame(m, i)` は[地上への切り替えのはじめのフレーム](d-2-2-SideChangeBound-ja.md)と同じです。`m[b]` は `m` のバイト `b` です。

**出口の条件.** `ExitCond(m)` は、フレームの終わりの状態 `m` についての条件です。

* フレームは待ちの繰り返しの中で終わっています。プログラムカウンタとスタックポインタは `T` と同じです。ドットは 9 以下です。vblank と NMI のフラグはドットに合っています。スプライト 0 のフラグは立っています。PPU 制御で NMI はオンです。コントローラはストローブ中ではありません。
* 29 バイトの `Kx` は `T` と同じ値です。下に挙げます。
* ゲームはポーズしていません。`GamePauseStatus` の下のビットは 0 です。

ほかのバイトは何でもかまいません。マリオの `x`、大きさ、状態、速さ、コイン、スコア、ゲームタイマーの数字、フレームカウンタ、インターバルタイマー、乱数、音のポーズのフラグ `PauseModeFlag`、音の状態の残り、スプライト、一時的なバイトです。

**リスト `Kx`**（名前）:

| まとまり | バイト |
|---|---|
| モード | `OperMode`、`OperMode_Task`、`GameEngineSubroutine`、`ScreenRoutineTask`、`DisableScreenFlag`、`Sprite0HitDetectFlag` |
| 面 | `WorldNumber`、`AreaNumber`、`AreaPointer`、`EntrancePage`、`AltEntranceControl`、`PrimaryHardMode`、`CurrentPlayer`、`JoypadOverride`、`GameTimerExpiredFlag` |
| 画面 | `VRAM_Buffer1`、`VRAM_Buffer_AddrCtrl` |
| 音 | `NoiseSoundBuffer`、`AreaMusicBuffer`、`EventMusicBuffer`、`MusicData`（2）、`MusicOffset_Square1`、`NoteLengthTblAdder`、`AreaMusicQueue`、`EventMusicQueue`、`NoiseSoundQueue` |
| 音のポーズ | `PauseSoundBuffer`、`PauseSoundQueue` |

**`During` の終わりがこの条件にどうつながるか.** `Entry2(M)` は `EntryCond(M)` と、さらに 8 バイト `X` が `E` と同じ値であることです。`AreaPointer`、`EntrancePage`、`CurrentPlayer`、`JoypadOverride`、`GameTimerExpiredFlag`、`AreaNumber`、`PrimaryHardMode`、`NoteLengthTblAdder` です。`During2(m)` は、これらのバイトも知っている `During(m)` です。土管のフレームがこれらを変えないことは確認が示します。タイマーが切れるフレームは、音のポーズの 2 バイトを除く `Kx` の全部と、`GamePauseStatus` の下のビットを出します。`Quiet(m)` は、その 2 バイトが `T` の値（0）であることです。Start を押すと、ポーズの音が鳴るあいだこれらは変わります。`Quiet` は証明していません。出口の状態についての仮定です。

`NoStart(m, i)` は、`m` がゲームコアで土管以外のルーチンなら入力 `i` に Start がないことです。`InRows(m)` は、`m` が下の段の抽象状態のどれかに含まれることです。`InRowsT(m)` は、`m` が下の「時間の段」の抽象状態のどれかに含まれることです。`InRowsTF(m)` は、`m` が下の「フラグが 0 でないときの時間の段」の抽象状態のどれかに含まれることです。`InTime(m) := InRowsT(m) ∨ InRowsTF(m)` です。

```
Timer(m)   :=  ( m[GameTimerDisplay], m[GameTimerDisplay + 1], m[GameTimerDisplay + 2] ) ≠ ( 0, 0, 0 )
Time(m)    :=  m[PauseModeFlag] = 0  ∧  Timer(m)
Paused(m)  :=  m[GamePauseStatus] & 1 = 1
```

`Timer` は、出口でゲームタイマーが 000 でないことです。`Time` は、それに音のポーズのフラグが 0 であることを足したものです。`Paused` は、フレームがポーズで終わることです。

## しくみ

**フレームの終わりをまたぐ時間.** 土管のあとのフレームは RAM を消し、その繰り返しの中でフレームが終わります。[はじめのフレーム](d-2-2-SideChangeBound-ja.md)の抽象機械はここで失敗します。`xtick` は時間の進め方に 3 つの場合を足します。フレームの最初のドット、フレームの終わり、ドットの区間が vblank フラグの消える時刻の両側にあるときです。フレームの終わりでは状態は 3 つまでに分かれます。フレームが続く、ドット 0 で終わる、もっと先のドットで終わる、です。分岐命令もまたぐことがあります（`xbr`）。`xtick` と `xbr` は `tick` と `branch` に対して証明してあります（`s_xtick`、`s_xbr`）。

**RAM を消すフレーム.** 出口の状態からは、消す繰り返しに着くときのドットは区間でしかわかりません。音のルーチンの時間が、わからないバイトで変わるからです。ですから、フレームが終わる場所は繰り返しの中に 1,904 か所あります（フラグが 0 でなければ 774 か所）。どの場所でも `left` のキーはその段の値です。繰り返しは `ScreenRoutineTask` を消し終え、`GameEngineSubroutine` にはまだ着いていません。次のフレームはこれらすべての場所から始まります。探索は繰り返しの回の順に進むので、道は 1 つにまとまります。このフレームは 6,905 ステップです。

**段.** 消したあとは 2,048 バイトのうち 1,769 バイトがわかっています。消されないバイトは `ExitCond` から来るか、自由です。1 フレームは 1 つの段の状態から次の段の状態へ進みます。全部で 123 段で、`left` は 122 から 0 まで減ります。最後の段には、操作できる状態と、タイムアップの道の状態があります。ゲームタイマーの数字が自由だからです。どちらも `left` は 0 です。

**時間の段.** 最後の段の時間切れの状態をなくすため、もう 1 組の段 `timeRows` を作ります。始まりはフラグ 0 の段の状態で、`dg` は「ゲームタイマーの 3 つの数字は全部 0 ではない」を表します。最後のフレームで時間を確かめる命令は、数字の 1 つのビットが 1 の 24 個に分けます。ですから時間切れの道はなくなります。入るときの準備のフレームは、`FetchNewGameTimerFlag` が 0 でなければタイマーを面の値にします。この道は数字に書くので `dg` がなくなります。探索はこのフラグを分けたままにします。フレームの終わりでは、1 と知っているビットを持つ数字から `dg` を戻します（`normD`、`sim_normD`）。ですから 2 つの道はまた 1 つになります。この段の確認は `chainOKD` です。`left` が 0 の段の状態はどれも操作できます（`zeroCtl`）。出口の状態が `Quiet` と `Time` を満たせば、この段に入ります（`stepT`）。

**フラグが 0 でないときの時間の段.** フラグが 0 でなければ、そのビットのどれかが 1 です。ポーズの 2 バイトが 0 のあいだ、音のルーチンはポーズの道を通り、フラグに書きません。ですからそのビットは 1 のままで、曲は始まりません。ビットごとに 1 組、時間の段を足しました（`timeRowsF`、8 組）。始まりは `timeBase` の状態で、フラグを 0 とする代わりに、そのビットを 1 とします。これは `TaintRun.splitDg` の 1 つの部分で、`D` をフラグにしたものです（`cov_dg`）。8 組とも、`left` が 0 の段の状態はどれも操作できます（`flagCheck`）。出口の状態が `Quiet` と `Timer` を満たせば、フラグが 0 なら `timeRows` に、0 でなければフラグの 1 のビットの組に入ります（`stepTT`）。ですから `EndRun.firstF` はフラグを仮定しません。

**ポーズで終わるフレーム.** ポーズで終わるフレームは、タイマーもモードのルーチンも動かしません。土管のフレームを、ポーズのビットを分けて読み、ポーズのバイトを分けたままにして、もう一度歩きます（`pauseCheck`）。カウンタが減った終わりの状態は、どれもビットが 0 と知っています（`finRkP`）。ですから、ポーズで終わる土管のフレームはカウンタを減らさず、`left` も減りません（`pause_keeps`）。段の状態はどれもビットが 0 と知っています（`notPausedRows`）。ですから段のフレームはポーズで終わりません。`lag` のフレームがポーズで終わるなら、`lag` のフレームは `left` を減らしません（`st_step_paused`）。

**わからないポインタを通した読み.** 状態が知らないポインタを通した `LDA (zp),Y` は、`TaintRun` の機械では失敗します。ポインタの上のバイトの既知のビットから、それが `0x1E` 以下か `0x80` 以上だとわかれば、どの番地 `p + y` も RAM か ROM にあり、レジスタではありません（メモリの終わりを越えた番地はゼロページとスタックに回ります）。このとき読みはわからないバイトを与え、ほかは何も変えません（`aIzyHi`、`wide_ok`、`s_aIzyHi`）。`xstep1` はほかの規則が失敗するところでだけこの規則を使います。ここの確認も、`xstep1` を使うほかのファイルの確認も前と同じく通ります。`rows0` は前と同じ 682,944 ステップです。

**音のポーズのフラグの 2 つの場合.** RAM を消しても `PauseModeFlag` は変わりません。0 でなければ、次に Start を押すまで音のルーチンは動かず、曲も始まりません。ですから段は 2 組あります。2 組目は、フラグが 0 でないという事実（`dg`）を使います。

**確認の大きさ.**

| フレーム | 抽象ステップ |
|---|---|
| 土管の 1 フレーム、タイマー ≥ 2 | 106,156 |
| 土管の 1 フレーム、タイマー = 1 | 90,308 |
| 段、フラグ 0 | 682,944 |
| 段、フラグ 0 でない | 691,797 |
| 時間の段 | 684,535 |
| 時間の段、フラグのビット 1 つが 1（8 組、1 組あたり） | 691,694 |
| 土管の 1 フレーム、タイマー ≥ 2、ポーズのビットを分ける | 252,566 |

フラグが 0 でないときの時間の段は、1 組約 1.6 秒、8 組で約 12 秒です。プログラムで約 21 秒（前は約 9 秒）、非公開の証明のビルドで約 29 秒（前は約 11 秒。ほかの証明と並べてビルドしたときの値）です。

## Start を除く理由

ゲームコアのフレームで Start を押すとゲームはポーズします。ポーズの音が鳴るあいだ曲は止まり、ゲームは止まりません。ですからポーズのあと、曲はゲームから何フレームでも遅れます。段と遅れの組ごとに状態が要ります。その段にとどまるフレームと先へ進むフレームをまとめると、曲のポインタと位置がわからなくなります。Start を許すと、確認はゲームコアの最初のフレームで失敗します。音楽のルーチンで 4 回の失敗です（23,695 ステップ）。ですから、これは証明していません。

上の読みの規則を入れて、一時的なプログラムで測りました（残していません）。

* `rows0` の段を `left` が 62 のところまで進め、曲の 23 バイト（ポインタの下のバイト、位置、音の長さの数えとバッファ、効果音の数え。ポインタの上のバイトは知ったまま）をわからないことにしました。規則は効きますが、次の 7 フレームはどれも 22 から 116 回失敗し、12 万 6 千から 40 万 5 千ステップかかります（今の段は 1 フレーム約 5,500 ステップです）。曲の 1 節が終わると、ルーチンは次のポインタを、わからない位置で表から読みます。ですから上のバイトもわからなくなり、`LDA (MusicData),Y` がまた失敗します。また、面の曲の見出しを探すループ（`iny`、`lsr`、`bcc`）が 0 かもしれないバイトで回り、終わりません。
* 出口から、フラグの 2 つの場合と `Quiet` の代わりに `PauseModeFlag`、`PauseSoundBuffer`、`PauseSoundQueue` をわからないことにした段。4 フレーム目から同じループで失敗します。曲が始まるフレームからは、フレームの終わりが 207,531 か所まで増え、400 万ステップの上限に達します。
* フラグだけをわからないことにした時間の段（ポーズのバイトは `Quiet` のとおり）。同じ失敗です。

理由は 3 つとも同じです。抽象機械は、曲が始まった状態と始まっていない状態をまとめます。まとめたあとは、「キューは 0 でない」ことを、それで分かれる分岐のあとまで持てません。ですから曲がわからなくなると、段はすぐ失敗します。場合を分けたままにする段は、場合ごとに 1 組要ります。フラグが 0 でない時間の段の 8 組（既知のビット 1 つずつ）は作りました（上の「フラグが 0 でないときの時間の段」）。ポーズを解いたあとの曲の遅れに 41 組要ります（下を見てください）。これはしていません。音のルーチンを 1 歩とみなす試みは次の節にあります。

## 音のルーチンを 1 歩とみなす試み

**考え.** 音のルーチンの 1 回の呼び出し（入口から戻りまで）について、次のことを ROM で 1 度だけ示します。音のバイトと APU のレジスタだけに書き、ほかの RAM のバイトを保ち、スタックを元に戻して呼び出し元に戻り、かかるドットが区間 `[lo, hi]` に入る。これが音のバイトのどんな値でも成り立てば、段の歩きは呼び出しを 1 歩で越えられ、曲を知らないまま進めます。

**音のバイト.** 38 バイトです（`SoundWalk.soundNames`）。キュー、バッファ、曲のポインタと位置と数え、効果音の数え、ポーズの 3 バイトです。ルーチンが読むほかのバイトは `OperMode` だけです。RAM への書き込みはどれも決まった番地（ゼロページか絶対番地）への書き込みです。番地に添字を足す書き込みは APU のレジスタへだけです。Lean の機械は APU を持たないので、APU への書き込みは何も変えません。

**測った数**（`sound-check`。出口から 200 フレームの、本物の呼び出しの場所から。そのほかのバイトはその機械の値）:

| 呼び出しの始まりの状態 | 抽象ステップ | 失敗 | 呼び出しのドット |
|---|---|---|---|
| 曲を知っている | 115 | 0 | 1,179 |
| 音の 38 バイトを知らない | 260,322 | 2,025 | 240 〜 87,237（フレームの終わりまで） |
| 同じ。キューとバッファを、いちばん下の 1 のビットで分けて読む | 294,803 | 2,136 | 同じ |
| 同じ。さらに `MusicData` の上のバイトのビット 7 が 1 | 上限の 2,000,000 | 15,630 | 同じ |

失敗するのは、4 つの音の `LDA (MusicData),Y`（ポインタがわからない）、曲の見出しを探すループ、そしてフレームの終わりに届く時間の進め方です。「いちばん下の 1 のビットで分ける」は、バイト `x` を `x & mask = 0` の部分と、`mask` のビット `j` ごとに「`j` より下の `mask` のビットは 0、ビット `j` は 1」の部分に分けることです（`SoundWalk.ctzPieces`。分け方はプログラムだけで使い、証明にはしていません）。これで見出しのループは終わりますが、ポインタと位置がわからないので、曲のデータを読むループが終わりません。

**「どんな値でも」は成り立ちません.** Lean の機械で、本物の呼び出しの場所から確かめました。

* 終わらない呼び出し。ポインタを ROM の中に、ノイズの戻りの位置を曲のデータが 0 の位置にすると、ノイズのデータを探すループ（`FetchNoiseBeatData`）は同じ位置に戻り続けます。200,000 ステップで戻りません。
* レジスタを読む呼び出し。ポインタの上のバイトを PPU のレジスタの範囲にすると、矩形波 2 のデータを読む `LDA (MusicData),Y` が PPU の状態のレジスタを読みます。この読みは vblank のフラグを消します。

ですから、まとめは音のバイトのある集まりの上でしか成り立ちません。その集まりはポインタと位置の組で決まり、バイトごとの既知のビットでは表せません。

**本物の曲の状態の表.** 出口から入力なしで 123 フレーム動かしました。出口の状態は 44 通りです。`Quiet` の場合、ポーズを解く音の数えが 1 から 42 の場合、出口のフレームでポーズを解いた場合です。呼び出しは 5,412 回、音の状態は 207 個でした。どの状態からも、抽象機械の歩きは戻りで閉じます。合わせて 16,940 ステップ、失敗 0、呼び出しのドットは 303 〜 3,291 です。本物の呼び出しは 101 〜 1,097 サイクルでした。

**段に使えない理由.** 段の状態は音のバイトを知りません。ですから「機械の音のバイトは表の中にある」を、抽象状態の外で、フレームからフレームへ運ぶ必要があります。それには、1 歩が書かないバイトを変えないことを、機械について示す補題が要ります。いまの抽象機械の証明はこれを出しません。`Sim` は 1 つの抽象状態と 1 つの機械の関係で、2 つの時点の機械を結びません。ですから、呼び出しのあとの状態が、呼び出しの前の状態の音でないバイトを知っていることも出せません。表の状態ごとに段を分ける道は、遅れごとに 1 組の段（上の 41 組）と同じ大きさです。これはしていません。`Quiet`（1-1-d-3-4）と `NoStart`（1-1-d-3-3）は残ります。

## 前提（Lean では証明していない）

* 本物の走りの入る状態での `Entry2`、または出口での `ExitCond`。ルートでは `Entry2` を部屋のフレームと入るときの 16 バイトから出します（[部屋の画面のページ](d-2-4-ScreenPage-ja.md)、`ScreenPage.entry_rest`）。この 16 バイトの 1 つ `NoteLengthTblAdder` は、急ぎの音楽のあとは成り立ちません。項目 1-1-d-2-5 です。
* `Quiet`。出口でポーズの音が鳴っていないことです。測った走りでは、土管の最後のほうのフレームで Start を押すと成り立ちません。そのような走りでも `left` はちょうど 1 ずつ減ります。これは測っただけです。段と入るときの条件からは出ません。条件は土管のフレームで Start を押すことを許すので、土管のあいだの状態はポーズの音のバイトを知りません。土管の最後のほうのフレームで押した音は、出口でもまだ鳴っています。曲を知らないまま進む段が要ります（「Start を除く理由」を見てください）。土管のフレームで Start を乱数で押した 880 回（44 の入る状態から 20 回ずつ）の出口はこうでした。`Quiet` が成り立つのが 280 回。ポーズを解く音がまだ鳴っているのが 584 回（`PauseSoundBuffer` にあり、`PauseModeFlag` は 0 でない）。出口のフレームでポーズを解いたのが 16 回（`PauseSoundQueue` にあり、フラグは 0 でない）。ポーズ中のものはありません。2 つ目の場合、曲はポーズの音の数えによって 1 から 41 フレーム遅れて始まるので、遅れごとに 1 組の段が要ります。3 つ目の場合だけなら段は 1 組増えるだけですが、`Quiet` が成り立たない 600 回のうち 16 回です。項目 1-1-d-3-4 です。
* `NoStart`。土管のあとのゲームコアのフレームで Start を押さないことです。
* `lagPaused`。`lag` のフレームがポーズで終わることです。`lag` は `Frames` の記号で、機械とつながるのはこのフィールドだけです。本物の走りでは、土管のフレームでタイマーが動かないフレームはどれもポーズで終わりました。出口のあとでタイマーが動かないフレームは `setup` のフレームだけで、これは `lag` ではありません。ほかの理由でタイマーが動かない `lag` のフレームは、このフィールドに合いません。`TimerControl` が 0 でないフレームと、ハンドラがフレームからはみ出したあとのフレームです。土管のフレームについては、確認がどのフレームも待ちの繰り返しで終わることを示すので、はみ出しはありません。測った走りには、どちらもありませんでした。段からは出ません。段は、出口のあとの状態がどれもポーズでないこと、ポーズで終わる土管のフレームが `left` を保つことを示しますが、`lag` の記号を機械に結ぶものはありません。項目 1-1-d-3-2 です。
* `Timer`。出口でゲームタイマーが 000 でないことです。音のポーズのフラグは仮定でなくなりました（フラグが 0 でないときの時間の段）。000 の走りは 400 秒を使っています。これは、切り替えと部屋だけからは出ません（コードから読みました）。土管のフレームはゲームタイマーを動かさないので、出口の数字は入るときの数字です。けれども入るときにタイマーが 000 のことがあります。操作できるフレームで 001 から 000 になり、時間切れは `GameTimerCtrlTimer` がもう一度切れる 24 フレームあとです。そのあいだにプレイヤーは土管に入れます。ですから 1-1 全体のタイマーの数えが要ります。項目 1-1-d-3-5 です。
* `b` は入ってから最初に操作できる状態であること。ルートでは `chg.b₂` の定義からこれが成り立ちます（`Changes.ctlFirst₂`）。
* [1-1 全体](0-1-Route-ja.md) はこの定理を使います。`Changes.run₂` は `EndRun` です。
