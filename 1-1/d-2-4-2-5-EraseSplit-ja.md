# 最初のブロックのバッファでのコインの消去

**主張.** 部屋のすべてのフレームで、コインを消す `STA (zp),Y` は、そのポインタが 2 つのブロックのバッファの最初のものの中なら、ブロックのバッファの中に書く。ポインタが 2 つめのブロックのバッファの始め以降の消去だけを、ブロックのバッファの終わりより前に書くことをまだ求める。

これは証明した。ROM の上の検査は 1 つ（部屋のフレームの 4 つの歩き）。ラウンド 30 まで、フィールド `roomErase` はすべての消去に、ブロックのバッファの終わりより前に書くことを求めていた（`EraseEnd`）。今はこれを、ポインタが 2 つめのブロックのバッファの始め以降の消去だけに求める（`EraseTwo`）。測ったすべてのフレームで、消去はすべて最初のブロックのバッファへのポインタを通った（ラウンド 30: ムービーで 13、自分の走りで 4,802 と 5,541）。

`tr_n(j)` はフレーム `n` の `j` 命令あとの機械。`pc(m)` はそのプログラムカウンタ。`erase` はその `STA (zp),Y` の場所。`ptr(m)` はそれがゼロページから読む 16 ビットのポインタで、`addr(m)` = `ptr(m) + Y` は書くアドレス。`bufLo` はブロックのバッファの始めで `bufN` はその長さ。2 つめのブロックのバッファは `bufLo + bufN/2` で始まる。抽象状態のバイト `b` について、`min(b)` と `max(b)` は、知っているビットのもとでの最小と最大の値。

## 命題

```
EraseTwo(m)    :=  pc(m) = erase  →  bufLo + bufN/2 ≤ ptr(m) & 0x7FF  →  addr(m) & 0x7FF < bufLo + bufN
eraseOK2(A)    :=  eraseOK(A)  ∧  ( pc(A) ≠ erase
                                    ∨  256 · h + max(l) + 255 < bufLo + bufN
                                    ∨  bufLo + bufN/2 ≤ 256 · h + min(l) )
                   （l, h: A の中のポインタの下と上のバイト。eraseOK はラウンド 30 と同じ: h を知っていて、6 以下で、256 · h ≥ bufLo）
erase_of_ok2   :  Sim(A, m) ∧ eraseOK2(A) ∧ EraseTwo(m)  →  Erase(m)
eraseTwo_of_end:  EraseEnd(m)  →  EraseTwo(m)

splitK(p, A)   :=  pc(A) = p で、A と Y の知らないビットが合わせて 6 以下なら:
                     そのようなビットを A と Y のそれぞれで 0 と 1 にした状態
                   ほかは [A]
cov_splitK     :  Sim(A, m)  →  ∃ B ∈ splitK(p, A), Sim(B, m)          （B は A のフレームの数とカウンタのフラグを保つ）
```

`chg` の変わったフィールド（すべての `n ∈ [b₁, a₂)` とすべての `j` について）:

```
roomErase  :  EraseTwo(tr_n(j))          前（ラウンド 30）: EraseEnd(tr_n(j))、 pc = erase → addr & 0x7FF < bufLo + bufN
```

`EraseTwo` は `EraseEnd` より少なく求める: 最初のブロックのバッファへのポインタを通る消去には何も求めない（`eraseTwo_of_end`）。

[ループの後ろへのジャンプ](d-2-4-2-4-LoopTime-ja.md) の `RestU`、`RestB`、`rec_frame1B` から `rec_frame4B`、`loop_sites_of_rows` は、`EraseEnd` の代わりに `EraseTwo` を使うほかはラウンド 30 と同じ。`recCheckB` は 4 つの歩きを分割つきで歩く。

## しくみ

**消去のアドレス.** ブロックのバッファのルーチンは位置からポインタを作る: x から列 `c`（0 から 15）、ページのビットからバッファ `t`（0 か 1、最初か 2 つめのブロックのバッファ）。アドレスを作るルーチンは、ポインタの上のバイトを `t` で表から読み（2 つの行で同じ: ブロックのバッファのページ）、バッファの始めの下のバイトに `c` を足す（`Y = t` の `ADC abs,Y`）。消去はポインタに行のオフセット `Y`（0 から 255）を足したところに書く。

* 最初のブロックのバッファではポインタはその始めから 15 以内なので、アドレスは `bufLo + 15 + 255` 以下で、どの `Y` でもブロックのバッファの終わりより前。
* 2 つめのブロックのバッファではポインタは 2 つめのバッファの始めから 15 以内で、アドレスが終わりより前なのは行のオフセットが 192 以下のときだけ。それにはプレイヤーの高さがいるが、歩きはそれを知らない。

**なぜ歩きは知らなかったか.** 抽象機械の `ADC` は、両方の値のすべてのビットを知っているときだけ結果を出す。その足し算で、歩きはアキュムレータの上の 4 ビット（0）を知っているが下の 4 ビット（列）は知らない。`Y` の上の 7 ビット（0）を知っているがビット 0（バッファ）は知らない。だから下のバイトはまったく知られず、歩きは 0 から 255 のどの下のバイトも許していた。

**分割.** その足し算の前で、歩きは状態を A と Y の知らないビットごとに分ける（`splitK`）: 2⁵ = 32 の状態。どれも機械の状態なので、分割は正しい（`cov_splitK`、`PipeChangeEnd.cov_bitA`、`cov_bitY` から）。それぞれの状態で足し算は正確で、下のバイトがわかる。探索は同じキーの状態を合わせる。そのキー（`EraseSplit.keyK`）はポインタの下のバイトのビット 7 も取る（足し算のすぐあとの格納ではアキュムレータのビット 7）。だから 2 つのブロックのバッファは別のまま。合わせても、最初のバッファの状態は下のバイトの上の 4 ビットを知っているので、ポインタがそのバッファの始めから 15 以内だと知っている。

**測定**（`buffer-ctl-check FM2 1 splitcheck`、ネイティブ）:

| 歩き | 探索: 状態 | 表（ラウンド 30） | 失敗する状態 | 時間 |
|---|---|---|---|---|
| (i) | 261,565 | 148,250 (141,625) | 0 | 77 秒 |
| (ii) | 143,770 | 66,917 (60,571) | 0 | 43 秒 |
| (iii) | 757,358 | 357,129 (325,399) | 0 | 349 秒 |
| (iv) | 422,531 | 265,619 (255,489) | 0 | 137 秒 |

時間はほかの 3 つの仕事が走っているときのもの。消去のところで歩き (i) と (ii) は 12 の状態に会う（`buffer-ctl-check FM2 3 splitcheck`。ラウンド 30: 6 で、どれもポインタの下のバイトを知らない）: ポインタが最初のブロックのバッファの始めから 15 以内の 6（どの `Y` でも `eraseOK2` が成り立つ）と、2 つめのブロックのバッファの始めから 15 以内の 6（フィールドを求める）。どれも `Y` を知らない。ブロックのバッファの読み出しでも同じ: 36 の状態で、18 と 18。

## 仮定（Lean で証明していないもの）

ラウンド 32: ここに残した場合は証明し、`roomErase` はなくなった。歩きは衝突のルーチンでプレイヤーの高さを分け、各フレームの始めで大きさのビット 1 から 7 を知るので、どの消去でも行のオフセットを知る（[コインの消去の行](d-2-4-2-6-EraseRow-ja.md)）。下の文はラウンド 31 のもの。

* **`roomErase`**、ポインタが 2 つめのブロックのバッファの始め以降の消去についてだけ: ブロックのバッファの終わりより前に書くこと。証明には行のオフセットが 192 以下であること（ブロックのバッファのルーチンを呼ぶ前のプレイヤーの高さのコードのテストから）、つまり歩きの中のプレイヤーの高さか、部屋では 2 つめのブロックのバッファを使わないこと（プレイヤーがページ 0 で左の端から 242 px 以下にいる。フレームをまたぐ上限）がいる。 測定（`buffer-ctl-check FM2 4 splitcheck`）: 歩き (i) と (ii) の表は、プレイヤーの衝突のコードの中に 5,302 の状態（65 の場所）を持ち、どれもプレイヤーの高さを知らない。それを値に分けると（コードの最初のテストより下で 207 まで）、歩きごとに約 110 万までの状態が増える。このラウンドでは試していない。
* `roomRead` と `roomXbit` は変わらない。分割はこれらを助けない: `roomRead` にはブロックのバッファの中身（フレームをまたぐ上限）がいり、`roomXbit` には横の土管のコードが x を読むとき x が 207 px 以下（プレイヤーが土管の中にいない: フレームをまたぐ上限）がいる。
