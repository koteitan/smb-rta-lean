# コインの消去の行

**主張.** 部屋のすべてのフレームで、コインを消す `STA (zp),Y` はブロックのバッファの中に書く。

これは証明した。ROM の上の検査は 1 つ（部屋のフレームの 4 つの歩き）。フィールド `roomErase` はなくなった。ラウンド 31 まで、それはポインタが 2 つめのブロックのバッファの始め以降の消去に、ブロックのバッファの終わりより前に書くことを求めていた（`EraseTwo`）。測ったすべてのフレームで、消去はすべて最初のブロックのバッファへのポインタを通った（ラウンド 30: ムービーで 13、自分の走りで 4,802 と 5,541）。だから本物の走りでこのフィールドを使うことはなかった。

`tr_n(j)` はフレーム `n` の `j` 命令あとの機械。`pc(m)` はそのプログラムカウンタ。`erase` はその `STA (zp),Y` の場所。`ptr(m)` はそれがゼロページから読む 16 ビットのポインタ、`Y` は行のオフセットで、`addr(m)` = `ptr(m) + Y` は書くアドレス。`bufLo` はブロックのバッファの始めで `bufN` はその長さ。`y` は画面の上のプレイヤーの高さ、`size` は大きさのバイト（0 が大きい、1 が小さい）、`crouch` はしゃがみのバイト。抽象状態のバイト `b` について、`max(b)` は知っているビットのもとでの最大の値。

## 命題

```
eraseOK4(A)    :=  eraseOK(A)  ∧  ( pc(A) ≠ erase  ∨  256 · h + max(l) + max(Y) < bufLo + bufN )
                   （l, h: A の中のポインタの下と上のバイト。eraseOK はラウンド 30 と同じ: h を知っていて、6 以下で、256 · h ≥ bufLo）
erase_of_ok4   :  Sim(A, m) ∧ eraseOK4(A)  →  Erase(m)

splitR2(A)     :=  yAt で:  y を ySteps の段で分ける（0–7、8–15、16–31、32–63、64–127、128–191、192–207、208–223、224–255 px の切れ）、
                            size のビット 0、crouch をいちばん下の立っているビットで分ける（いちばん下でありうるビットごとに 1 つと、すべて 0 の 1 つ）
                   adcY と adcAt で:  A と Y を知らないビットごとに分ける（splitK、ラウンド 31）
cov_splitR2    :  Sim(A, m)  →  ∃ B ∈ splitR2(A), Sim(B, m)          （B は A のフレームの数とカウンタのフラグを保つ）

knownS         :=  knownMC のビットと、size のビット 1 から 7
```

`yAt` は衝突のルーチンの最初の `y` の読み込み、`adcY` はブロックのバッファのルーチンの行の足す数の足し算（`ADC abs,Y`）、`adcAt` はラウンド 31 のポインタの下のバイトの足し算。3 つとも ROM のバイトから見つける。

`LoopTime.recCheckB` の 4 つの歩きは、今は `knownS` を知っている状態から始め、各ステップの前に `splitR2` で分ける（`EraseRow.walkG`、`frameG`）。フレームの定理 `rec_frame1B` から `rec_frame4B` は、フレームの始めの条件を 1 つ多く取る:

```
hz  :  size(m) & 0xFE = 0                              （大きさのビット 1 から 7 が 0）
```

`loop_sites_of_rows` は部屋の各フレーム `n` でそれを、その前のフレームから証明する: それらは `SiteOK` を満たす（帰納法）ので、大きさのバイトを保つ部屋の歩き（`SizeKeep.byte_all`、ラウンド 22）から `size(seq n) = size(seq b₁)` で、それは参照の値（小さい）か 0（`SizeKeep.size_of_rows`）。`loop_sites_of_rows` の新しい条件は `SizeKeep` の 2 つの歩き（`RoomChecks.height.keepR`、`keep0`）と、部屋の最初の操作のときの大きさ。これらにはフィールドを使わない。

`chg` のなくなったフィールド:

```
roomErase  :  ∀ n ∈ [b₁, a₂), ∀ j,  EraseTwo(tr_n(j))
              EraseTwo(m) := pc(m) = erase → bufLo + bufN/2 ≤ ptr(m) & 0x7FF → addr(m) & 0x7FF < bufLo + bufN
```

新しいフィールドはない。`ChangesBase.roomRest` は今は `Read ∧ Xbit` を与える。`RestU` と `RestB` は部分 `erase` を失う。

## しくみ

**行のオフセット.** ブロックのバッファのルーチンは高さから行のオフセットを計算する: `Y = ((y + adder) & 0xF0) − 32`（8 ビット）。`adder` は呼び出しのオフセットで表から読む。2 つめのブロックのバッファへのポインタ（その始めから 15 以内）では、消去がブロックのバッファの終わりより前なのは、ちょうど `Y ≤ 192` のとき。衝突のルーチンは各呼び出しの前に `y` を調べる:

* 始めで `y < 207`。
* 頭の呼び出しの前で `y ≥` 上の端。上の端は `size`（しゃがんでいれば 1 を足す）で表から読む: しゃがんでいない大きいプレイヤーで 32 px、小さいプレイヤーとしゃがんだ大きいプレイヤーで 16 px（しゃがんだ小さいプレイヤーはゲームが作らないが、表の次のバイトを読むことになる）。
* 足の呼び出しの前でもう一度 `y < 207`。足の足す数は 32。
* 最初の横の呼び出しの前で `32 ≤ y < 228`、2 つめの前で `8 ≤ y < 208`。足す数は 8 か 24。

ルーチン全体で `y < 207` で、足す数はどれも 32 以下なので、`Y > 192` になるのは `y + adder < 32` のときだけで、テストはそれを除く。だから歩きが `y`、`size`、`crouch` を十分に知っていれば、どの呼び出しでも `Y ≤ 192`。

**歩きが知らなかったこと.** 歩きが知らないフラグでの分岐は、フラグだけを分ける: 歩きは調べたバイトを知ることにならない。`ADC` は両方の値のすべてのビットを知っているときだけ結果を出す。部屋の歩きは `y` も `size` も `crouch` も知らなかった。また探索は足の検査のところでブロックのバッファのルーチンの足す数のオフセットを忘れていたので、歩きはそこで `Y` を知らなかった。

**分割.** `yAt` で歩きは `y` を 9 つの切れに分ける。切れの知っているビットでルーチンのすべてのテストが決まる: 境 8、16、32、207、208、228 はそれぞれ切れの端にあるか、テストのどちらの側も害がない。`size` のビット 0 を分け、`crouch` をいちばん下の立っているビットで分ける。だから `crouch` のテストはどれも決まり、頭の上の端も決まる。行の足す数の足し算の前で、アキュムレータ（`y`）を知らないビットで分けるので、和は正確で `Y` がわかる。分割は状態のすべての機械を覆う（`cov_splitR2`、`TaintRun.cov_bit` から）。

**大きさのビット 1 から 7.** `size` がどのバイトでもありうると、頭の上の端は表のあとのバイトから読まれ、小さい `y` が頭の呼び出しに届きうる。だから歩きは、`size` のビット 1 から 7 が 0 だと知って始める。各フレームの始めはこれをその前のフレームから得る。ラウンド 22 の、部屋のフレームで大きさのバイトを保つ歩きによる（それはそのフレームの `SiteOK` を要るので、フレームの同じ帰納法の中で使う。だから循環はない）。

**探索**（証明の一部ではない: 歩きが表を検査する）は、`y` の上のビットを知っているあいだ、切れを別にしておく: `y` のビット 3 以上の知っているビット、`Y` の上の 2 ビット、`crouch` と `size` のビット 0 の種類で（`EraseRow.rowKey`）。ルーチンの検査のところで足す数のオフセットを保つ（`EraseRow.aidsR`）。ルーチンの戻りと消去のあとで `y`、足す数のオフセット、`Y` を忘れ、頭のテストのあとで `crouch` と `size` を忘れる（`EraseRow.forgetAt`）。上の 2 ビットが同じオフセットを合わせても上限が残る（00、01、10 でそれぞれ 48、112、176 以下）。歩きは通るので、どの消去でも状態は `256 · h + max(l) + max(Y)` がブロックのバッファの終わりより前だと知っている。

**測定**（`buffer-ctl-check FM2 31 rowcheck` から `34`、1 つずつの歩き、ネイティブ、4 つを同時に。時間は探索と歩きの検査）:

| 歩き | 表（ラウンド 31） | そのうち `y` の上のビットを知る衝突のルーチンの中のもの | 失敗する状態 | 時間 |
|---|---|---|---|---|
| (i) | 320,474 (148,250) | 183,921 | 0 | 187 秒 |
| (ii) | 239,141 (66,917) | 183,921 | 0 | 162 秒 |
| (iii) | 1,218,249 (357,129) | 919,605 | 0 | 901 秒 |
| (iv) | 337,408 (265,619) | 183,921 | 0 | 200 秒 |

時間のほとんどは探索（歩き (iii): 901 秒のうち 803 秒）。最初の 2 つの試みは高くつくか失敗したので使っていない: `y` の上の 4 ビットを分けて行のオフセットを正確に保つと、歩き (ii) の探索は 569,234 の状態（ラウンド 31: 143,770）で、歩き (iii) のものは 5.6 GB を超えた。また歩き (iv) は最初 5 つの表の状態で失敗した。探索がフレームの始め（ドット 0）を、大きさを忘れたゲームの処理のあとのアイドルループと合わせたので、合わせた状態は同じフレームの中の 2 回目の割り込みを、大きさを知らないまま許した。探索は今は、最初のドットが 10 より前の状態を別にしておく。

## 仮定（Lean で証明していないもの）

* 新しいものはない。`roomRead` と `roomXbit` は変わらない（下）。
* `roomRead` には、すべての命令でのブロックのバッファの中身（フレームをまたぐ上限: `RoomBlocks` はそれを `Run.roomSites` から出すので、同じ帰納法の中で使う必要がある）と、頭の読み出しでは頭の上のタイル（部屋の形）がいる。新しい分割はバッファの中身を与えない。
* `roomXbit` には、横の土管のコードが `x` を読むとき `x ≤ 207` px であること（プレイヤーが土管の中にいない: フレームをまたぐ上限）がいる。歩きは `x` を知らない。
