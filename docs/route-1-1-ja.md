# 1-1 の道筋: 1-2 が始まるフレームの下界に向けて

**目標.** 1-1 で操作できるようになった最初のフレームを 0 として、1-2 が始まる（面の番号が変わる）のは
1748 フレーム目より前にはならない、を示すこと。1748 は HappyLee の TAS の値。

このページは途中経過の記録です。パートごとに、**Lean の定理**、**エミュレータでの確認**（Lean ではない）、
**未解決** を分けて書きます。数はフレームと、TAS との距離の差（ピクセル、または 1/256 ピクセル）で書き、
ROM の番地や表の値は書きません。

## TAS の道筋

| フレーム | 出来事 |
|---|---|
| 0 → 368 | 出だし（32 フレームで最高速）、最高速で走る、4 本目の土管に入る |
| 368 → 459 | 土管を下りる、場面の切り替え、地下の部屋に天井から入る |
| 459 → 570 | 地下の部屋: 床に落ちる、レンガのかたまりに跳び乗る、横の土管に着地で入る |
| 570 → 852 | 横の土管、場面の切り替え、地上の土管から上がる |
| 852 → 1092 | 土管の上で加速、最後の階段を越える、旗の土台の横に降りて小さく跳び、上昇中に旗をつかむ |
| 1092 → 1218 | 旗の上で待つ、城まで自動で歩く（城に入る） |
| 1218 → 1748 | 残り時間の点数化、旗を上げる、21 フレームの格子に合わせた待ち |

## パートごとの結果

### a. 走って土管に入る（0 → 368）: 最短

- 32 フレーム目までの距離は、[出だしの最適性](../1-1/a-3-Opening-ja.md) の定理から TAS 以下。
  そのあとは [最高速の上限](../0-0/0-1-TopSpeed-ja.md) から、1 フレーム 2.5 ピクセル以下。
  TAS はこの 2 つの上限ぴったりに走る（32〜362 フレーム目まで、毎フレームちょうど上限）。
- 土管に入れるのは、両足が土管の上面にあり、下を押していて、着地のコードを通るフレームだけです。つまり上面に落ちるか、立っているときです（[縦の土管に入る](../1-1/a-4-PipeEntry-ja.md)）。地面で左か右といっしょに下を押しても数えません。フレームのコードが消すからです。上限によると、フレーム 367 でマリオはその範囲に 112/256 ピクセル（0.44 ピクセル）足りません。なので 368 より前には入れません。
- 状況: 上限、土管の上面の近くの全部の状態での判定ルーチンと規則の比較、その結合は、規則に従うフレームについての Lean の定理です。前提: 本物のフレームが規則と上限に従うこと（ルーチンは単独で確かめています）。368 で実際に入るのは、エミュレータでの TAS です。

### b, d. 土管と場面の切り替え: 長さ

```
地下で操作できるフレーム = 土管に入ったフレーム + 91
地上で操作できるフレーム = 横の土管に入ったフレーム + 282
```

入力、土管の上での位置や速さ（パート d では、入るときに届くピクセルの範囲で。下を参照）、21 フレームの格子のどれにもよらない（それぞれの処理は入力を読まないか
上書きする。21 フレームの格子で待つ処理は、この 2 つの切り替えでは飛ばされる）。何もしないフレームを
はさむと、ちょうどその分だけ遅れる。一時停止は長くするだけ。

パート b の最後のフレームの状況: [一部のバイトがわからない走り](../1-1/b-2-3-TaintRun-ja.md) は、最後の 41 フレームを、走りごとに違うバイトのすべての値で、フレーム 50 での条件のもとで証明します。フレーム 48 からだと同じ主張は偽です。音楽の状態によってはゲームが止まります。条件を全部の走りについては証明していません。

パート b の状況: [地下への切り替え](../1-1/b-1-PipeTransition-ja.md) は、そこに挙げた入る状態についての Lean の定理です。本物の走りの 1 つの入る状態からは、Start と
Select を除くすべてのフレームのすべての入力で、ちょうど 91 フレーム目に操作できます。これには仮定 `Merge`（ボタンをそのまま写すバイトだけが違う状態は同じように動く）を使います。
入力なしなら仮定なしで、範囲のほかのピクセル、ほかの速さ、大きいマリオ、本物の走りで続けてずらした 21 個の入るフレームで同じです。

長さを決めるものは [地下への切り替えの長さを決めるもの](../1-1/b-2-1-PipeTransitionAll-ja.md) にあります。切り替えは、土管のタイマーの 48 フレームと、そのあとの 43 フレームです。43 フレームのほうは、リスト R の外のすべてのバイトのすべての値について Lean の定理です。敵、物、マリオの位置と速さ、画面の位置は、これを変えられません。R の値は、動かした状態の値だけです。48 フレームのほうは、挙げた 77 個の入る状態だけです。すべての入る状態は、そのページの仮定 (H1) から (H4) のもとでだけ定理です。

+91 には例外があります（どれも値を書き換えた状態）。`HalfwayPage` や `AreaPointer` を書き換えると 75 フレームです。コードでは、マリオがこの土管に入れるときにこれらの値にはなりません（Lean では証明していません）。6 個の物が近くにあるとフレームがはみ出し、92〜96 フレームです。ゲームタイマーが 000 だと操作できず、着いたときに死にます。走りの中で早く操作できる例外は見つかっていません。

Start を押すと一時停止しますが、切り替えの一部のフレームでは無視されます（コードから読み、エミュレータで試した）。

パート d の状況: [横の土管から地上への切り替え](../1-1/d-1-SideTransition-ja.md) は、そこに挙げた入る状態についての Lean の定理です。本物の走りの 1 つの入る状態からは、Start と Select を除くすべてのフレームのすべての入力で、ちょうど 282 フレーム目に操作できます。これには仮定 `GMerge` を使います。入力なしなら仮定なしで、口のほかのピクセル（入る 1 フレーム前に書き、入るフレームは本当に動かす）、ほかの端数と速さ、大きいマリオ、`x₀ + 1` と `x₀ + 2` での本物の入り方、続けてずらした 21 個の入るフレームで同じです。例外が 1 つあります。入るフレームの終わりで `x` が 16 の倍数だと、タイマーが設定されず 378 フレームかかります。このピクセルには歩いても落ちても届きません（コードから読んだことで、Lean にはしていません）。そこでも切り替えは短くならないので、852 の下限は変わりません。コードには画面が最初のページにないときの短いタイマーがあります。書き換えた状態で動かすと 174 フレームです（[地上への切り替えの長さを決めるもの](../1-1/d-2-1-SideTransitionAll-ja.md) の Lean の定理）。部屋では画面は最初のページにあり、スクロールロックはオンです（本物の走りの全部のフレームで測りました）。ですから、コードから読むと走りでは届きません。これは Lean にしていません。852 の下限はこのことに頼っています。

長さを決めるものはそのページにあります。切り替えは土管のタイマーの 160 フレームと、残りの 122 フレームです。122 フレームについては、リスト R の外のすべてのバイトのすべての値を Lean の定理が含みます。敵、物、マリオの位置と速さはこれを変えられません。R の値は、動かした状態についてだけです。160 フレームは、挙げた 20 個の入る状態についてだけです。すべての入る状態は、そのページの仮定 (H1) から (H4) のもとでだけ定理です。`HalfwayPage` と `WarpZoneControl` は、縦の土管と違い、この長さを変えません。6 個の物が近くにあると 284 フレームまで長くなります。ゲームタイマーが 000 だと操作できません。どの走りのどの入る状態でも同じになることは証明していません。

### c. 地下の部屋（459 → 570）: 570 より前には入れない

入るのに必要なこと（コードから）:

- 横の土管には、入口の前の床で入る。早くても、そこに着地するフレームで、右を向いているとき（[横の土管に入る](../1-1/c-4-SidePipe-ja.md)）。空中では土管に止められる。
- その床へは、レンガのかたまりの右端を上から越えるしかない。右端を越えた最初のフレームを `t` とする。落ちる時間は、かたまりからの
  離れ方で決まる（[ジャンプの高さ](../1-1/c-2-Jump-ja.md)）。

  | かたまりからの離れ方 | 床に着くのは |
  |---|---|
  | 1.5625 ピクセル／フレーム以上のジャンプ | `t` の 12 フレーム以上あと |
  | それより遅いジャンプ | `t` の 1 フレーム前から 12 フレーム以上、空中で 1 フレームに 1.5 ピクセル以下: 557 から 569 で 18 ピクセルまでで、口は端の 22 ピクセル先 |
  | 歩いて落ちる | `t` の 16 フレーム以上あと |

  （速いジャンプはちょうど 1 フレームに 4 ピクセル落ちる。遅いジャンプは約 4.2 ピクセル落ちるので、別に扱う。）
  TAS は 558 で越えて 570 で入る。なので 569 に入るには 557 で右端を越えている必要があり、それは TAS より 592/256 ピクセル（2.31 ピクセル）先。

557 フレーム目の上限（全部の入力について）:

1. 天井からの落下は入力によらないので、床に着くのは 493。最初のジャンプは 494。
2. 足がかたまりの上面より低いあいだ、右に動いているか止まっていて、角かそれより先にいると、ぶつかって速さがほぼ 0 になる。左に動いていると止められない。かたまりに乗る前の、そういう最後のフレームを `s` とする。TAS は `s` = 504 で、ぶつかるまで 15/256 ピクセル。
3. 1.5625 ピクセル／フレームより遅く跳ぶとき: `s` から [空中の速さの上限](../1-1/c-1-AirCap-ja.md) が使える。全部の
   跳ぶ速さと A の押し方（[ジャンプの高さ](../1-1/c-2-Jump-ja.md)）で、いちばん早い組（`s`、かたまりに乗るフレーム）は (504, 511)（TAS）と (505, 510)。
   ほかは乗るのが遅い。定理から `s` から 557 までは 121.75 ピクセル以下。なので 557 に TAS より先に行けるのは 527/256
   ピクセルまでで、65/256 ピクセル（0.25 ピクセル）足りない。
4. 1.5625 ピクセル／フレーム以上で跳ぶとき: 速く上がるが、`s` は跳んでから 8 フレーム以上あと。[速いジャンプ](../1-1/c-3-FastTakeoff-ja.md) は、459 から横のフレーム `hstep` を
   全部の入力でたどる。右に動いていると、500 までのジャンプは 8 フレームのあいだ角より左にとどまれない。左に動いていると、500 までのジャンプはモデルの中にあるが、とても後ろにいるので、
   そのあと何をしても 557 で目標に届かない。500 より後に跳ぶと、角から最高速でも間に合わない。
5. 496 以降に、止められて速さがほぼ 0 のフレームがあれば、そのあと何をしても 557 で目標に足りない。そこからのポテンシャルの上限で 225/256 ピクセル以上足りない。これに入るのは、床か空中で角にぶつかる場合、ぶつかったあとの古い速さで速く跳ぶ場合、足の判定（かたまりの上面の少し下で頂点になるジャンプは、足がかたまりの上にあると止められ、毎フレーム 1 ピクセル戻される）、かたまりの横から跳ぶ場合（足がかたまりの上にあって落ちていて、段に入っている深さが 5 ピクセル未満なら、その段に着地し、同じフレームで横の判定に止められ、次のフレームでそこから跳べる）。496 より前は角より左にいる。

左の壁に着地して跳び、床に触らずにかたまりへ行く走りも、その定理に入ります。壁に触ると、ジャンプを見ずに端に着くのは C + 98 より後です。本物の走りでは E = C + 134 でした。

状況: [地下の部屋をつなぐ](../1-1/c-5-RoomJoin-ja.md) は Lean の定理。走りのフレームの構造体 `RoomRun` と上の定理の確認から、最初の操作からの相対で `E ≥ C + 111`。構造体のフィールドは仮定で、本物のフレームが `hstep` に従うか止められること、`vstep` に従うこと。TAS と、ランダムな操作の本物の走り 1400 回で成り立つ（どれも境目の近くではない）。部屋の左の壁は手順 4 のモデルにない。定理は、500 までの速いジャンプでは壁に触っていないことを仮定する。`hstep` は 460 から 558 の全部のフレームで TAS と一致する。大きいマリオは定理に入っていない。

### e. 地上（852 → 1085）: 旗の範囲に早く届かない

- 地上で操作できるとき、マリオは止まっていて、横方向の状態は 1-1 の最初と同じ（[地上](../1-1/e-1-SurfaceRun-ja.md)）。
- どのフレームでも地面か空中かを自由に選べるモデルで、全部の入力について、892 フレーム目に TAS より先に行けるのは 464/256 ピクセルまで。892 以降は、最高速の上限から 1 フレーム 2.5 ピクセル以下。TAS はここでも上限どおりで、損は 980 フレーム目の 16/256 ピクセルだけ。なので 1085 フレーム目に TAS より先に行けるのは 480/256 ピクセルまで。
- 旗をつかめる範囲に入るには、1085 フレーム目に TAS より 528/256 ピクセル先にいる必要がある。なので 1085 までには入れない。[旗を下からつかむ](../1-1/f-1-PoleGrab-ja.md) の 32/256 ピクセルを足しても 16/256 ピクセル余る。
- 最初にぶつかるのが 9 フレーム目以降なら、同じ上限を超えない（そのあとは最高速の上限のフレームなら何でもよい）。1 から 8 フレーム目は、衝突の処理がまわりで横にぶつからない。
- 状況: `hstep` と最高速の上限のフレームの走りについての Lean の定理。仮定: 本物のフレームがそのとおりに動く（`hstep` は 853 から 1085 の全部のフレームで TAS と一致）。1 から 8 フレーム目は確認した箱の中にいる。最初の状態は本物の走り 1 つから読む。
- モデルにはマップがないので、本物の走りにとってこの上限はちょうどではない。エミュレータの探索 `seg-search`（定理ではない。動かし直していない）では 892 で 144/256 ピクセル、なので 1085 で 160/256 ピクセルまで。

### f. 旗をつかんで城に入る: 城に入るのは 1218 より前にはならない

旗のまわりの仕組み（コードから）:

- 旗に触れるのは、マリオの右側が旗の柱に 3〜6 ピクセル入る 4 ピクセルの範囲に、旗の土台より上の高さでいるとき。地面の高さで走ってくると、
  その手前で土台のブロックに止められる。この範囲の左端を `x₀` とする。
- 上昇中に土台に近い高さで、範囲の左の 2 ピクセルで触ると、旗をすべり降りずに、その場で終わりの処理に入る。
  遅いジャンプで、前のフレームで左に動いていれば、城に入るのは**触ったフレーム + 126** か + 127（[旗に触ってから城まで](../1-1/f-4-CastleWalk-ja.md)）。左に動いていなくて端数が 176/256 ピクセル以上なら + 125。
  速いジャンプでは、次のフレームで足が土台の中にあり、土台が右をふさぐので、城に入るのは触ったフレーム + 1 か + 2（エミュレータ、位置を書き換えた）。なので下界には、どのフレームでも速いジャンプでつかめないことが要る。
  それ以外で触ると、旗が下りきるのを待つ。測った最小は触った + 153 で、本物の走りが 1086 に触って 1239 に城に入る。パート e から 1086 より前には触れない。定理に要るのは + 132 だけ。

なので 1217 以前に城に入るには、どのフレームかで速いジャンプでつかむか、1092 までに遅いジャンプでつかみ、1092 ちょうどなら上の + 125 であることが要る。遅いジャンプの場合を除く理由（コードから。どの速さ、どの落下の速さ、どの入力でも成り立つ）:

1. **上昇中だけ。** その高さで落ちているときは、土台の上に着地するか、横の判定の前に止められる。その高さで上昇するのは、
   地面からフレーム `T` に跳んだときだけで、`g = T + 2`（1.5625 ピクセル／フレーム以上で跳ぶと `g = T + 1`）。地面に着く
   フレームを `L` とすると `T ≥ L + 1` なので、`L ≤ 1088`。
2. **小さなジャンプでは進まない。** 土台の横で、上面より低いあいだは、右に動いているか止まっていると、速さが 0 になって
   1 ピクセル左に押される。左に動いていれば何も起きない。もっと左からは `x₀` の手前で止まる。なので `x(g) ≤ x(L)` で、
   `x(L) ≥ x₀` で着地する必要がある。土台の左の端より先なので、上から来るしかない。
3. **端を越える。** `L` の前に、最後に土台の上の位置（`x ≥ x₀ − 2`）に入るフレームを `e`、`k = L − e` とする。その前の
   フレームはそれより左なので、当たる前の `x(e) < x₀ + 0.5`。
   - フレーム `e`: 1 ピクセル戻り、速さ 0。
   - `e` と `L` のあいだ: 1 フレームに 1 ピクセルまで進む。それには左を押して、押し戻しを右向きにする（下の TAS の技）。
   - フレーム `L`: 1/8 ピクセルまで進んだあと（右を押す。TAS の 1089）、1 ピクセル戻る。右への押し戻しがあると次のフレームの
     左ボタンが効かないので、左に動いていない。この押し戻しを避けられるのは `k ≤ 1` のときだけ。

   ```
   x(L) ≤ x(e) + k − 3 + 1/8   (k ≥ 2)
   x(L) ≤ x(e) − 1             (k ≤ 1)
   ```
4. **時間が足りない。** `L ≤ 1088` から `e ≤ 1088 − k`。パート e から `x(1085) ≤ x₀ − 0.1875` で、それより前は 1 フレームごとに
   2.5 ピクセル少ない。

   | k | e の最大 | x(L) の最大 |
   |---|---|---|
   | 0, 1 | どれでも | `x₀ − 0.5` |
   | 2 | どれでも | `x₀ − 0.375` |
   | 3 | 1085 | `x₀ − 0.0625` |
   | 4 | 1084 | `x₀ − 1.5625` |
   | それ以上 | | 1 フレームごとに 1.5 ピクセル少ない |

   どれも `x₀` に届かない。TAS は `e` = 1086、`k` = 3、`L` = 1089、`g` = 1092 で、ちょうど 1 フレーム遅い。
5. **速いジャンプ**（[旗の横の速いジャンプ](../1-1/f-3-FastHop-ja.md)）。着地の次のフレームなら、覚えている速さが高いままでなければならないので、`e` から `L` まで左右を押せず、毎フレーム押し戻される。もっとあとなら、直前に 1.5625 ピクセル／フレーム以上の地面のフレームが要るので、土台の横より左にいた。どちらでも、どのフレームでも `x(g) < x₀`。

エミュレータで確かめたこと:

- 1084 フレーム目の状態（まだ土台に触れていない）の高さ（13 通り）、横の位置（TAS より 1 ピクセル後ろから 160/256 ピクセル
  先まで、10 通り）、向き（3 通り）を変えた 390 通りで、8 通りの入力で 8 フレーム: 1217 以前に城に入れるものはなかった。
- 遅い落下、遅い速さ、左だけの入力: 160/256 ピクセル先（1 系列は 0）で、高さ 15 通り、速さ 2.5 か 1.5 ピクセル／フレーム、
  落下の速さ 4、2、0 ピクセル／フレームの 135 通りで、左右と A、B の全部の入力を 1091 まで: 上昇中のつかみはなかった。
- 式は実際にほぼ一致する。1084 で TAS より 4 ピクセル低い位置で、全部の入力のとき、544/256 ピクセル先にすると 1091 に上昇中の
  つかみができ、540/256 ピクセルではできない。式では 496/256 ピクセル以上が必要で（残りの 48/256 は左を押すフレームと小さな
  ジャンプの分）、パート e から届くのは 480/256 ピクセルまで。上の 2 つのエミュレータの確認は 160/256 ピクセル先までで、これは パート e のエミュレータの探索の値です。Lean の上限はこの確認に頼っていません。

TAS の細かい技: 土台の横で左右同時押しをすると、右がふさがっているので左を押した扱いになり、進む向きが左に
なる。すると土台からの押し戻しが右向きになり、旗の範囲にとどまれる。

状況: パート e と f をつなぐことは Lean の定理（[操作から城まで](../1-1/f-5-PoleJoin-ja.md)）。本物のフレームとのつながりは全部、名前をつけた仮定（`Run`）で、TAS とほかの本物の走りでプログラムで確かめた。土台の高さの落下、触ったあとの長さ、城の旗は測定で、証明していない。旗の近くに敵がいないと仮定している。

1093 に触る場合が別に必要になる。そこで + 125 だと城は 1218 のままでタイマーが 1 回多く減り、1-2 は 1727 になる。定理は、1092 と 1093 の触りでは前のフレームで左に動いていて端数が 176/256 ピクセルより小さいことを示すので、+ 126 以上。TAS の 1085 の状態から位置を 16/256 から 160/256 ピクセルまで動かし、A、B、左、右の全部の入力で調べたが、+ 125 はなかった。

### g. 城から 1-2 まで: 1748 より前にはならない

```
L = E + T + D + 107 + ((c − T − D) mod 21)
  E: 城に入るフレーム   T: ゲームのタイマー（触ってから止まっている）
  D: 33。T の一の位で 1 → 34、3 → 98、6 → 194
  c: E でのインターバルタイマーの位相
```

最後の待ちは 21 フレームの格子の点で終わる。レベルは `E + T + D + 107` 以後で最初の格子の点で変わる。ファンファーレの終わりも待つ。`T` が小さいと、レベルは式より遅く、格子の外で変わる。なので式は下界。確かめた道筋では `T ≥ 125` で等号。

タイマーはプレイの 24 フレームごとに 1 減る。エリアの切り替えのあいだサブカウンタは 1 ずつ減って 0 で止まり、数字は変わらない。なので、あるエリアでプレイ `p` フレームのあいだに `⌈p/24⌉` 減る。決めるのは `E` だけでなく `E + T`。`368 + 91 + 111 + 282 + 240 + 126 = 1218` で `T = 370` なので `E + T = 1588`。地上で 1 フレーム多いと 1 回多く減るので、和は同じ。走りの一部が長くなっても `E + T` は減らない。

格子はフレーム番号だけでは決まらない。エリアの切り替えごとに、タイマーが動かないフレームが 1 つある。2 回の切り替えのあとで位相は `(3 − f) mod 21`。そのあとタイマーが動かないフレームがあれば、その分ずれる。そのフレームは走りも 1 遅らせるので、結論も同じだけ動く。ポーズは 45 フレーム以上で、この場合。ゲームが動くのにタイマーが止まるのは、パワーアップ、敵に当たる、死ぬ、のときだけ。小さいマリオはまずパワーアップが要り、そのときゲームは 59 フレーム止まる。

TAS の和は 1728 で、格子の点は 1727 と 1748。なので 20 フレーム多く待つ。和が 1 小さければ 1727 になる。

状況: [城から 1-2 まで](../1-1/g-1-CastleToLevel-ja.md) は、長さ、タイマー、格子、レベルの変化についての名前をつけた仮定から、`L ≥ 1748` を Lean で示す。式、タイマーの規則、格子は、挙げた状態について本物のフレームで確かめた。すべての走りがこれに従うことは証明していない。

## まとめ

```
1-2 の開始 ≥ 1748                                     （全体の定理、Run の全部のフィールドを仮定）
  ⟸ E + T ≥ 1588、D ≥ 33、格子                       （城から 1-2 まで）
  ⟸ 触ることと城の 3 つの場合                         （操作から城まで。パート e、f）
  ⟸ 地上で操作できるのは横の土管の +282 以降          （パート d。仮定）
  ⟸ 横の土管は地下で操作できてから +111 以降          （地下の部屋をつなぐ。パート c）
  ⟸ 地下で操作できるのは土管の +91 以降               （パート b。仮定）
  ⟸ 土管は 368 以降                                   （パート a）
```

この全体が 1 つの Lean の定理です: [1-1 全体](../1-1/0-1-Route-ja.md)。遅く着いても得にならないことは、タイマーと格子については定理です。残っているのは、定理の仮定を本物のフレームについて証明すること。

## 再現

TAS の映像ファイル（fm2）を用意して、`git/` で:

```
.lake/build/bin/smbrta route-check FM2                  # 全体の数: パートの長さ、タイマー、格子、1-2 の開始
.lake/build/bin/smbrta touch-search-at FM2 1085 DELTA 8 # 位置を DELTA/256 ピクセル動かして、触ったフレームごとの城までの長さ
.lake/build/bin/smbrta tas-trace FM2                    # 道筋と、上限との比較
.lake/build/bin/smbrta tas-seg FM2 A B                  # A〜B フレームの位置、速さ、高さ
.lake/build/bin/smbrta tas-insert FM2 AT K              # AT に何もしないフレームを K 個はさむ
.lake/build/bin/smbrta seg-search FM2 852 40            # パート e の探索（10 分以上）
.lake/build/bin/smbrta end-poke FM2 1084 Y DX FD 8      # パート f の 1 通り（Y: 高さ、DX: 横のずれ、FD: 向き）
.lake/build/bin/smbrta pole-check                      # 旗の近くの当たり判定のルーチンと規則の比較
.lake/build/bin/smbrta jump-table                      # 地面とかたまりからの全部のジャンプ
.lake/build/bin/smbrta pipe-check                      # 土管の上面の判定のルーチンと規則の比較
.lake/build/bin/smbrta pipe-change-check               # 地下への切り替え
.lake/build/bin/smbrta takeoff-check                   # 地下の部屋の速いジャンプの探索
.lake/build/bin/smbrta side-check                      # 横の土管の口の判定のルーチンと規則の比較
.lake/build/bin/smbrta abs-check                       # 覚えている速さを書き換えるもの
.lake/build/bin/smbrta castle-check                    # 触ったフレームから城まで
.lake/build/bin/smbrta pipe-all-check                  # 地下への切り替えの長さを決めるもの
.lake/build/bin/smbrta side-change-check               # 横の土管から地上への切り替え
.lake/build/bin/smbrta surface-check                   # 地上の上限と、ぶつかりありの探索
.lake/build/bin/smbrta flag-poke FM2 1084 Y DX V VY FD 7 GY   # 上に速さと落下の速さを足し、全部の入力で（GY: つかむ高さ）
.lake/build/bin/smbrta room-bound FM2 459 493 557 CX CY WLO WHI TX
    # 地下の部屋: ジャンプの表と 557 の上限。CX, CY: 角（y ≥ CY のあいだ x ≥ CX で当たる）。WLO..WHI: 落ちてきて
    # かたまりに乗る高さ。TX: かたまりの右端を越える x。どれも部屋のブロックと当たり判定のコードから読む。
```
