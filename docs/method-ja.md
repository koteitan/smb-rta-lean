# しくみ

**ゲームのコードを動かすモデル.** モデルの 1 ステップは、モデルの状態を本物の RAM の
スナップショット（1-1 で操作できるようになった最初のフレーム）に書き込み、ゲームのコードの
ある範囲をエミュレータで実行して、状態を読み戻すものです。手で書き直したところはありません。

**どのバイトが状態か.** RAM の読み書きの記録をとります。フレームが「書く前に読み」、かつ
「書く」（そのフレーム自身か、周りのまねた部分、たとえば毎フレームのタイマーが書く）バイトが、
フレームをまたいで引き継がれるバイトです。モデルの状態はちょうどそれで、関係しないと確かめた
バイトだけを除きます。

**たどり着ける状態の証明書**（`Smbrta/Cert.lean`。`native_decide` を使わずに証明）。

```
L_0 = [s0],   L_{k+1} = next(L_k) = { step(s, i) | s ∈ L_k, i ∈ I }   （重複は消す）
run_mem :      ∀ w ∈ I^k,  run(s0, w) ∈ L_k
lower_bound :  checkUpTo(P, n, [s0]) = true  →  ∀ w ∈ I^{≤ n},  P(run(s0, w))
```

`native_decide` で計算するのは `checkUpTo`（どの段でも P が成り立つか）だけです。違う入力列が
同じ状態になることが多いので、入力列は約 36^33 通りあっても、段は小さく（多くても数十万状態）
収まります。

**緩めたモデル.** ジャンプでは、縦の状態を「地面か空中か」のフラグに置き換え、着地は
どのフレームの終わりでもよいことにします。本物の動きはどれも緩めたモデルの動きになるので、
緩めたモデルでの下限は本物の下限です。

**絞り込んだ正確な探索.** 緩めたモデルの下限が本物の入力列で届くかを決めるには、正確な
モデルで `n` フレームを探します。そのとき、緩めたモデルに写して「残りのフレームでまだ届く」
状態だけを残します。`n` フレームの本物の入力列はそういう状態しか通らないので、見落としません。

**前提の確かめ方**（Lean ではなくプログラム）: ランダムな入力でモデルと本物のエミュレータを比べる。
捨てたバイト（位置、縦のバイト）を探索の全ステップで変えてみる。違いは 0。数字は各定理の
ページにあります。
